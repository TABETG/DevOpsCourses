32.1 Monitoring et observabilitéBon à savoir

Le monitoring répond à des questions connues d'avance : « le CPU dépasse-t-il 80 % ? », « le service répond-il ? ». L'observabilité est la capacité à répondre à des questions qu'on n'avait pas prévues, à partir des données émises par le système : « pourquoi les utilisateurs de l'organisation X voient-ils des lenteurs depuis le déploiement de 14 h 12 ? ». Elle repose sur trois signaux corrélés : les logs (événements discrets), les métriques (valeurs agrégées dans le temps) et les traces (le parcours d'une requête à travers les services). Le lien entre eux (identifiants de trace dans les logs, exemplars dans les métriques) est ce qui rend l'ensemble utile.

32.2 Produire de bons logsPar cœur

  • Structurés en JSON : un champ par information, jamais de texte à parser par regex. Un log est une donnée, pas une phrase.
  • Sur stdout : la plateforme collecte (12 facteurs). Pas de fichier, pas de rotation à gérer.
  • Corrélés : trace_id et span_id dans chaque ligne, plus un identifiant de requête et, si pertinent, l'identifiant de l'utilisateur ou de l'organisation (pseudonymisé si nécessaire).
  • Niveaux avec discipline : ERROR = quelqu'un doit agir ; WARN = anomalie tolérée ; INFO = événement métier notable ; DEBUG = jamais en prod par défaut, activable à chaud.
  • Sans données sensibles : jamais de mot de passe, de jeton, de numéro de carte, de données de santé. Masquage à la source ; c'est un sujet RGPD et un vecteur de fuite classique.
  • Un événement par ligne, et les stack traces sur une seule ligne JSON (sinon le collecteur les découpe).
// Spring Boot 3.4+ : logs JSON natifs, sans dépendance
// application.yaml
logging:
  structured:
    format:
      console: ecs        # Elastic Common Schema ; ou logstash, gelf
  level:
    root: INFO
    fr.crisisshield: INFO
management:
  tracing:
    sampling:
      probability: 1.0    # les identifiants de trace sont injectés dans le MDC automatiquement

// Un log métier structuré
log.atInfo()
   .addKeyValue("incident_id", incident.id())
   .addKeyValue("zone", incident.zone())
   .addKeyValue("priority", incident.priority())
   .log("Incident créé");

// Sortie
{"@timestamp":"2026-09-18T10:12:03.412Z","log.level":"INFO","message":"Incident créé",
 "service.name":"crisisshield-api","trace.id":"4bf92f3577b34da6a3ce929d0e0e4736","span.id":"00f067aa0ba902b7",
 "incident_id":"INC-2041","zone":"Nord","priority":"HIGH","process.thread.name":"http-nio-8080-exec-3","log.logger":"fr.crisisshield.incident.IncidentService"}

Pour le front : envoyer les erreurs JavaScript à un collecteur (Sentry, Grafana Faro) avec le même identifiant de session ; ne pas laisser les logs dans la console du navigateur.

Règle Loki : peu de labels, à faible cardinalité (jamais un identifiant d'utilisateur ou de requête en label : ça explose l'index). Tout le reste se filtre dans la requête.

Elastic / OpenSearch : index par jour, ILM (hot, warm, cold, delete), mappings explicites (sinon un champ change de type et casse l'index), Kibana/Dashboards. Choix courant en France pour les logs de sécurité et les SIEM.

OpenTelemetry Collector : un seul agent pour les trois signaux, avec des pipelines (receivers → processors → exporters). Il remplace de plus en plus les agents spécialisés ; le chapitre 34 le détaille.

32.4 Coût, rétention, conformitéBon à savoir

  • Le volume de logs est le premier poste de coût d'observabilité. Mesurer les Go/jour par service ; un service bavard en DEBUG coûte plus cher que son calcul.
  • Échantillonner les logs de succès (garder 100 % des erreurs, 10 % des 200 sur les endpoints à fort trafic), agréger à la source (un log par lot plutôt qu'un par élément).
  • Rétention par type : applicatifs 14 à 30 jours en accès rapide, puis archivage S3 Glacier ; audit et sécurité 1 an ou plus selon obligations (LPM, PCI, ISO 27001) ; jamais « infini par défaut » (CloudWatch le fait si tu n'y touches pas).
  • Accès aux logs = accès à des données personnelles : RBAC sur le backend, journalisation des consultations, pseudonymisation.
Techno de nichePour sortir du lot — Vector

Agent de logs et métriques en Rust (Datadog, open source) : ultra performant, avec le langage VRL pour parser, transformer, enrichir et surtout masquer les données personnelles à la source avant tout stockage.

Pourquoi ça différencie : Le masquage RGPD à la collecte, prouvable, est un argument fort pour un profil DevSecOps ; Vector remplace Fluent Bit et Promtail.

À essayer en une heure : docker run --rm -v "$PWD/vector.yaml:/etc/vector/vector.yaml:ro" timberio/vector:latest-alpine avec une transformation VRL qui remplace les adresses e-mail par un hachage avant envoi vers Loki.

En entretien — « Comment tu mets en place les logs sur un cluster ? » Applications en JSON sur stdout avec trace_id, agent DaemonSet (Alloy ou OTel Collector), Loki sur S3 avec peu de labels, Grafana pour interroger, rétention par type, coût mesuré par service, données sensibles masquées à la source. Et le pont vers les métriques et traces : le trace_id qui permet de cliquer d'un log vers la trace.
Exercice 32.1

Une requête Loki sur 24 h met 2 minutes et échoue par manque de mémoire. Le développeur cherche user_id=42. Que s'est-il passé et comment faire ?

Corrigé
La requête ne filtre par aucun label (ou par un label trop large) : Loki décompresse et lit tout. Ajouter les labels namespace et app, réduire la fenêtre, filtrer avec |= avant | json. Ne pas transformer user_id en label pour autant : c'est de la haute cardinalité. Si ce type de recherche est fréquent, c'est un cas pour Elasticsearch, ou pour une trace (les traces sont indexées par attribut).
Exercice 32.2

Trouve trois problèmes dans ce log : 2026-09-18 10:12 ERROR Login failed for user jean.dupont@mail.fr password=Azerty123 from 82.14.3.9

Corrigé
Non structuré (texte à parser), un mot de passe en clair (fuite majeure), une adresse e-mail et une IP en clair (données personnelles ; à pseudonymiser ou justifier par la sécurité avec rétention limitée). Et ERROR est probablement excessif pour un échec de connexion isolé (WARN, avec une alerte sur le taux).
Travail pratique 32 — Logs structurés de bout en bout
  1. Passe le backend CrisisShield en logs JSON ECS avec trace_id (Spring Boot 3.4 natif, ou Logback + logstash-encoder). Ajoute trois logs métier structurés (création, escalade, clôture d'incident). Masque tout champ sensible avec un filtre.
  2. Installe Loki (chart loki en mode SingleBinary avec stockage MinIO, ou loki-stack) et Grafana Alloy en DaemonSet qui collecte les Pods du cluster avec labels namespace, app, container. Grafana connecté à Loki.
  3. Écris cinq requêtes LogQL utiles pour CrisisShield (erreurs par service, incidents HIGH par zone, latence extraite d'un champ, logs d'une trace, top des messages d'erreur) et sauvegarde-les dans un dashboard.
  4. Alerte : règle Loki (ruler) qui déclenche si plus de 10 ERROR en 5 minutes sur l'API.
  5. Mesure : Go/jour par namespace (métriques de Loki), puis réduis de moitié en échantillonnant les logs d'accès à 10 % dans Alloy.
  6. Rétention : 7 jours en staging, 30 jours en prod, configuration de compaction et de suppression vérifiée.
  7. Bonus : la même collecte vers OpenSearch (Helm) avec Fluent Bit, un index par jour et ILM ; compare la mémoire consommée par les deux piles.

Livrable : configuration Loki/Alloy dans le dépôt de config (GitOps), dashboard exporté en JSON, mesures dans tp32.md, docs/cours-logs.md.

En 30 secondes
  1. Counter, gauge, histogram ; rate, histogram_quantile ; jamais de moyenne de latence.

33.1 Le modèlePar cœur

Prometheus tire (scrape) périodiquement un endpoint /metrics exposé par chaque cible, stocke des séries temporelles identifiées par un nom et des labels, et les interroge en PromQL. Sur Kubernetes, le Prometheus Operator découvre les cibles via ServiceMonitor/PodMonitor.

TypeSémantiqueExempleRequête typique
CounterNe fait que croître (remise à zéro au redémarrage)http_server_requests_seconds_countrate(x[5m])
GaugeValeur qui monte et descendjvm_memory_used_bytes, kafka_consumer_lagvaleur brute, avg_over_time
HistogramRépartition en buckets cumulés + somme + comptehttp_server_requests_seconds_buckethistogram_quantile(0.95, sum by (le) (rate(x_bucket[5m])))
SummaryQuantiles calculés côté client (non agrégeables)À éviter en général

Cardinalité : chaque combinaison de labels est une série. Un label user_id ou url avec des identifiants crée des millions de séries et tue Prometheus. Labels autorisés : service, méthode, route templatée (/incidents/{id}), code de statut, instance, zone.

33.2 PromQL essentielPar cœur

# Taux de requêtes par seconde, par service
sum by (service) (rate(http_server_requests_seconds_count[5m]))

# Taux d'erreur (5xx) en %
100 * sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
    / sum(rate(http_server_requests_seconds_count[5m]))

# Latence p95 et p99
histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket{uri!~"/actuator.*"}[5m])))

# Saturation : CPU d'un conteneur en % de sa request
sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="crisisshield"}[5m]))
  / sum by (pod) (kube_pod_container_resource_requests{resource="cpu", namespace="crisisshield"})

# Mémoire proche de la limite (OOM imminent)
container_memory_working_set_bytes / container_spec_memory_limit_bytes > 0.9

# Pods non prêts, redémarrages
kube_deployment_status_replicas_unavailable > 0
increase(kube_pod_container_status_restarts_total[1h]) > 3

# JVM : GC et pool de connexions
rate(jvm_gc_pause_seconds_sum[5m]) / rate(jvm_gc_pause_seconds_count[5m])
hikaricp_connections_active / hikaricp_connections_max > 0.8

# Kafka : lag du consumer group
sum by (group, topic) (kafka_consumergroup_lag)

# Prédiction : disque plein dans 4 h ?
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*3600) < 0

Les quatre signaux d'or (Google SRE) pour tout service : latence, trafic, erreurs, saturation. La méthode RED (Rate, Errors, Duration) pour les services, USE (Utilization, Saturation, Errors) pour les ressources.

33.3 InstrumenterImportant

Java : Micrometer est intégré à Spring Boot et Quarkus ; /actuator/prometheus expose HTTP, JVM, HikariCP, Kafka, cache sans code. Métriques métier :

// Compteur et timer métier
private final Counter incidentsCreated;
private final Timer escalationTimer;

public IncidentService(MeterRegistry registry) {
    incidentsCreated = Counter.builder("crisisshield_incidents_created_total")
        .description("Incidents créés").tag("channel", "api").register(registry);
    escalationTimer = Timer.builder("crisisshield_escalation_duration_seconds")
        .publishPercentileHistogram().register(registry);
}
// registry.gauge("crisisshield_open_incidents", openIncidents, AtomicInteger::get);

Nommage : préfixe applicatif, unité de base en suffixe (_seconds, _bytes, _total pour les counters). Exporters pour ce qui n'expose rien nativement : node-exporter (machines), kube-state-metrics (objets Kubernetes), postgres-exporter, blackbox-exporter (sondes HTTP/TCP/ICMP depuis l'extérieur), kafka-exporter.

33.4 DashboardsBon à savoir

Un dashboard répond à une question pour un public. Trois niveaux : service (RED + SLO, pour l'équipe), ressources (USE, pour l'exploitation), métier (incidents ouverts, temps de traitement, pour le produit). Règles : un dashboard par service avec la même structure, les variables Grafana ($namespace, $service) pour réutiliser, les dashboards en code (JSON dans Git, provisionnés par ConfigMap ou par l'opérateur Grafana), jamais construits à la main en prod et perdus. Les dashboards communautaires (Grafana.com : node-exporter, JVM Micrometer, Kubernetes) sont un bon départ.

Anti-patterns : le mur de 40 graphiques que personne ne lit, les moyennes de latence (toujours des percentiles), les couleurs sans seuil.

33.5 À l'échelleBon à savoir

Un Prometheus garde ses données localement (15 jours par défaut) et ne se réplique pas. Pour la haute disponibilité et la rétention longue : Thanos ou Cortex/Mimir (stockage objet, requêtes globales sur plusieurs clusters, déduplication), ou remote_write vers un service géré (Grafana Cloud, Amazon Managed Prometheus). Les recording rules précalculent les requêtes lourdes ; l'agent mode collecte sans stocker.

Techno de nichePour sortir du lot — VictoriaMetrics

Base de séries temporelles compatible Prometheus (remote write, PromQL étendu en MetricsQL) qui consomme jusqu'à dix fois moins de mémoire et de disque, avec un mode cluster simple ; alternative à Thanos et Mimir, très répandue en Europe de l'Est et chez les gros volumes.

Pourquoi ça différencie : Savoir dimensionner et comparer Thanos, Mimir et VictoriaMetrics est une question de plateforme d'observabilité à l'échelle.

À essayer en une heure : docker run -p 8428:8428 victoriametrics/victoria-metrics, remote write depuis ton Prometheus, puis compare la consommation mémoire à charge égale.

En entretien — « Quelles métriques tu regardes en premier sur un service qui va mal ? » RED : le taux d'erreur et la latence p99 par route, puis la saturation (CPU vs request, mémoire vs limite, pool de connexions, lag Kafka), puis les événements Kubernetes (redémarrages, Pending). Précise : percentiles et pas moyennes, et le piège de la cardinalité.

En 30 secondes

34.1 ConceptsPar cœur

Une trace représente une requête de bout en bout ; elle est composée de spans (une opération : requête HTTP entrante, appel SQL, publication Kafka, appel sortant), chacun avec un début, une durée, des attributs, un statut, et un parent. La propagation du contexte (en-tête W3C traceparent, ou en-têtes Kafka) transmet l'identifiant de trace d'un service à l'autre ; sans elle, chaque service produit des traces orphelines.

trace 4bf92f35... (2 340 ms)
└── GET /api/incidents/INC-2041/escalate        api          2 340 ms
    ├── SELECT incident WHERE id = ?              postgres      12 ms
    ├── POST http://notification/send             api → notif  2 180 ms   ◄── le problème est ici
    │   └── POST /send                            notification 2 170 ms
    │       └── SMTP connect                      notification 2 100 ms   ◄── timeout SMTP
    └── kafka.publish incidents                   api            8 ms

Ce que les traces montrent que rien d'autre ne montre : où le temps passe entre services, les appels en cascade (N+1), les timeouts en chaîne, les retries invisibles.

34.2 OpenTelemetryImportant

OpenTelemetry (OTel, CNCF) est le standard unique pour produire et transporter traces, métriques et logs : API et SDK par langage, conventions sémantiques (noms d'attributs standardisés : http.request.method, db.system), protocole OTLP, et le Collector. Il remplace OpenTracing, OpenCensus et les agents propriétaires : instrumenter une fois, envoyer où l'on veut (Tempo, Jaeger, Datadog, Honeycomb...).

Application ─OTLP─► OTel Collector ─► Tempo / Jaeger      (traces)
                    (receivers,     ─► Prometheus / Mimir  (métriques)
                     processors,    ─► Loki                (logs)
                     exporters)     ─► fournisseur SaaS

# collector-config.yaml
receivers:
  otlp: {protocols: {grpc: {endpoint: 0.0.0.0:4317}, http: {endpoint: 0.0.0.0:4318}}}
processors:
  batch: {}
  memory_limiter: {limit_mib: 512, check_interval: 1s}
  k8sattributes: {}                          # ajoute namespace, pod, deployment aux signaux
  tail_sampling:
    policies:
      - {name: errors, type: status_code, status_code: {status_codes: [ERROR]}}
      - {name: slow, type: latency, latency: {threshold_ms: 1000}}
      - {name: baseline, type: probabilistic, probabilistic: {sampling_percentage: 10}}
exporters:
  otlp/tempo: {endpoint: tempo:4317, tls: {insecure: true}}
  prometheusremotewrite: {endpoint: http://mimir:9009/api/v1/push}
  loki: {endpoint: http://loki:3100/loki/api/v1/push}
service:
  pipelines:
    traces:  {receivers: [otlp], processors: [memory_limiter, k8sattributes, tail_sampling, batch], exporters: [otlp/tempo]}
    metrics: {receivers: [otlp], processors: [memory_limiter, k8sattributes, batch], exporters: [prometheusremotewrite]}
    logs:    {receivers: [otlp], processors: [memory_limiter, k8sattributes, batch], exporters: [loki]}

Déploiement : un Collector en DaemonSet (agent, proche des Pods) qui envoie à un Collector en Deployment (gateway, échantillonnage, export). L'OpenTelemetry Operator gère cela et l'injection automatique.

34.3 Instrumenter en JavaImportant

  • Sans code : l'agent Java OTel (-javaagent:opentelemetry-javaagent.jar) instrumente automatiquement Spring MVC/WebFlux, JDBC, HikariCP, Kafka, RestTemplate/WebClient, gRPC, Redis... Sur Kubernetes, l'annotation instrumentation.opentelemetry.io/inject-java: "true" et une CRD Instrumentation font injecter l'agent par l'opérateur, sans toucher à l'image.
  • Spring Boot natif : Micrometer Tracing avec le bridge OTel (micrometer-tracing-bridge-otel) et l'exporter OTLP ; les identifiants arrivent dans le MDC pour les logs. Quarkus : extension quarkus-opentelemetry.
  • Avec code, pour les spans métier :
@WithSpan("escalate-incident")                 // annotation OTel
public void escalate(@SpanAttribute("incident.id") String id, Priority to) {
    Span.current().setAttribute("incident.priority.to", to.name());
    ...
    Span.current().addEvent("notification-sent");
}

Variables d'environnement standard : OTEL_SERVICE_NAME, OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_RESOURCE_ATTRIBUTES=deployment.environment=prod, OTEL_TRACES_SAMPLER.

34.4 Backends et corrélationBon à savoir

  • Tempo (Grafana) : stockage objet, pas d'index sauf par identifiant et TraceQL, très économique, s'intègre à Grafana (logs → trace → métriques en un clic, exemplars reliant un point de latence à une trace).
  • Jaeger : le pionnier, interface dédiée, stockage Elasticsearch ou Cassandra ; accepte OTLP.
  • SaaS : Datadog, Honeycomb, New Relic, Dynatrace : puissants, chers, fréquents en grands comptes.
# TraceQL : les traces lentes de l'escalade avec une erreur SMTP
{ name = "escalate-incident" && duration > 1s } >> { span.db.system = "smtp" && status = error }

La corrélation est le but : depuis une alerte sur la latence p99, cliquer sur un exemplar → la trace → les logs de cette trace → le Pod et sa mémoire. Grafana avec Loki, Tempo, Prometheus/Mimir (la « pile LGTM ») le fait nativement.

34.5 ÉchantillonnageBon à savoir

Tracer 100 % des requêtes coûte cher à fort trafic. Head sampling : décision au début de la trace (probabiliste, 10 %), simple mais on perd des erreurs. Tail sampling : décision après la trace complète dans le Collector (garder toutes les erreurs et les lentes, 10 % du reste), ce qu'il faut viser ; il exige que tous les spans d'une trace arrivent au même Collector (load balancing par trace id). Commencer à 100 % en staging, ajuster en prod.

Techno de nichePour sortir du lot — Grafana Beyla

Auto-instrumentation par eBPF : métriques RED et traces OpenTelemetry de n'importe quel processus (Java, Go, Node, binaire inconnu) sans agent, sans changement de code ni d'image, legacy compris.

Pourquoi ça différencie : Observer une application qu'on n'a pas le droit de modifier est un cas de mission fréquent ; Beyla y répond en dix minutes.

À essayer en une heure : DaemonSet Beyla sur kind avec les métadonnées Kubernetes activées ; observe les traces du service « legacy » du TP 50 sans y toucher.

En entretien — « Comment tu mets en place le tracing distribué ? » OpenTelemetry comme standard, agent Java injecté par l'opérateur (zéro changement d'image), propagation W3C incluant Kafka, Collector en agent + gateway avec tail sampling, Tempo derrière Grafana, corrélation avec logs et métriques par trace_id et exemplars. Un exemple concret de ce que tu as trouvé avec une trace (le SMTP ci-dessus) vaut plus que la liste.

35.1 SLI, SLO, SLAPar cœur

  • SLI (indicateur) : une mesure de ce que l'utilisateur vit. Disponibilité = requêtes réussies / requêtes totales ; latence = requêtes sous 300 ms / total ; fraîcheur des données ; taux de succès d'un parcours. Mesuré au plus près de l'utilisateur (ingress, ou sonde externe), pas sur le CPU.
  • SLO (objectif) : la cible sur une fenêtre. « 99,9 % des requêtes de l'API réussissent sur 30 jours glissants » ; « 95 % des requêtes sous 300 ms ».
  • SLA (accord) : l'engagement contractuel avec pénalités, toujours plus lâche que le SLO interne (SLA 99,5 % si SLO 99,9 %).
  • Budget d'erreur : 100 % − SLO. À 99,9 % sur 30 jours : 43 minutes d'indisponibilité, ou 0,1 % des requêtes en erreur. C'est un budget à dépenser : déploiements, expérimentations, maintenance. Épuisé → on gèle les changements et on travaille la fiabilité ; largement disponible → on peut prendre des risques.
SLOIndisponibilité autorisée par anPar 30 joursCe que ça implique
99 %3,65 jours7,2 hRedémarrage manuel possible
99,9 %8,76 h43 minAstreinte, automatisation du rollback
99,95 %4,38 h21 minMulti-AZ, déploiements progressifs
99,99 %52 min4,3 minMulti-région, aucune intervention humaine dans la boucle

Chaque neuf multiplie le coût. Le SLO se choisit avec le produit à partir de ce que les utilisateurs tolèrent, pas à partir de ce que la technique permet. Une application de gestion de crise a des exigences plus fortes sur la disponibilité que sur la latence ; un dashboard interne, l'inverse.

35.2 Alerter sur les symptômes : le burn ratePar cœur

Une alerte doit signifier : « un humain doit agir maintenant ». Les alertes sur les causes (CPU à 80 %, un Pod redémarré) réveillent pour rien ; les alertes sur les symptômes (le SLO est en train d'être consommé anormalement vite) réveillent quand ça compte. Le burn rate = vitesse de consommation du budget par rapport au rythme qui l'épuiserait exactement à la fin de la fenêtre. Burn rate 1 = tout le budget en 30 jours ; 14,4 = tout le budget en 2 jours.

# Recording rules : SLI d'erreur sur plusieurs fenêtres
- record: sli:api_error_ratio:rate5m
  expr: sum(rate(http_server_requests_seconds_count{job="api",status=~"5.."}[5m])) / sum(rate(http_server_requests_seconds_count{job="api"}[5m]))
- record: sli:api_error_ratio:rate1h
  expr: ... [1h] ...
- record: sli:api_error_ratio:rate6h
  expr: ... [6h] ...

# Alertes multi-fenêtres, multi-burn-rate (Google SRE Workbook), SLO 99,9 % → budget 0,001
- alert: APIErrorBudgetBurnFast          # 2 % du budget en 1 h : page immédiate
  expr: sli:api_error_ratio:rate1h > 14.4 * 0.001 and sli:api_error_ratio:rate5m > 14.4 * 0.001
  for: 2m
  labels: {severity: page, service: api}
  annotations:
    summary: "L'API consomme son budget d'erreur 14x trop vite"
    runbook_url: https://runbooks.crisisshield.example/api/error-budget
- alert: APIErrorBudgetBurnSlow          # 10 % du budget en 3 jours : ticket, pas de réveil
  expr: sli:api_error_ratio:rate6h > 1 * 0.001 and sli:api_error_ratio:rate1h > 1 * 0.001
  for: 1h
  labels: {severity: ticket, service: api}

La double fenêtre (longue pour la signification, courte pour ne pas alerter après la fin du problème) évite les faux positifs et les alertes qui durent. Des outils génèrent ces règles à partir d'une définition de SLO : Sloth, Pyrra, Grafana SLO.

Quelques alertes de cause restent utiles en ticket (pas en page) : disque plein dans 4 h, certificat expirant dans 14 jours, sauvegarde absente depuis 26 h, nœud NotReady, Pod en CrashLoopBackOff depuis 15 min.

35.3 AlertmanagerImportant

route:
  receiver: slack-general
  group_by: [alertname, service]
  group_wait: 30s          # attendre d'autres alertes du même groupe avant d'envoyer
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers: [severity="page"]
      receiver: pagerduty-astreinte
      continue: true                     # aussi vers Slack
    - matchers: [severity="page"]
      receiver: slack-incidents
    - matchers: [severity="ticket"]
      receiver: gitlab-issues
inhibit_rules:
  - source_matchers: [alertname="ClusterDown"]
    target_matchers: [severity="page"]
    equal: [cluster]                     # si le cluster est down, taire tout le reste
receivers:
  - name: pagerduty-astreinte
    pagerduty_configs: [{routing_key_file: /etc/secrets/pd, severity: critical}]
  - name: slack-incidents
    slack_configs: [{api_url_file: /etc/secrets/slack, channel: "#incidents", title: '{{ .CommonAnnotations.summary }}'}]
  • Regroupement : 50 Pods en erreur = une notification, pas 50.
  • Inhibition : une panne amont tait les alertes aval.
  • Silences : pendant une maintenance, avec durée et auteur.
  • Escalade : dans l'outil d'astreinte (PagerDuty, Opsgenie, Grafana OnCall) : non acquitté en 5 min → personne suivante.
  • Chaque alerte de type page a un runbook lié : quoi vérifier, quoi faire, qui appeler.

Hygiène : une alerte qui se déclenche sans action pendant deux semaines est supprimée ou rétrogradée. Une revue mensuelle des alertes (nombre, taux d'action, faux positifs) fait partie du processus. Le nombre de pages par semaine et par personne est une métrique de santé de l'équipe.

Et la phrase clé : « on alerte sur ce que l'utilisateur subit, pas sur ce que la machine fait ».

Astreinte, gestion d'incident, post-mortems

À la fin de ce chapitre, tu sauras
  • Organiser une astreinte soutenable

  • Écrire un post-mortem sans blâme qui produit des actions réelles

En 30 secondes
  1. Astreinte soutenable : rotation à 5 ou 6, moins de 2 pages par semaine, compensation, passation.
  2. Incident : rôles (le commandant ne débogue pas), mitiger avant de comprendre, communication à cadence fixe.
  3. Post-mortem sans blâme dans les 5 jours, actions suivies jusqu'à fermeture ; game days pour s'entraîner.

36.1 L'astreinteBon à savoir

  • Rotation : une semaine par personne, au moins 5 à 6 personnes pour que chacun ne soit d'astreinte qu'une semaine sur six ; un primaire et un secondaire ; pas d'astreinte pour une équipe de deux (c'est un risque humain et un risque de service).
  • Conditions : compensation (légale en France : rémunération ou repos, cadre défini par accord), matériel, droit à la déconnexion hors astreinte, pas de déploiement risqué le vendredi soir pour celui qui n'est pas d'astreinte.
  • Charge : cible < 2 pages par semaine par personne ; au-delà, l'équipe travaille la fiabilité avant les fonctionnalités (c'est ce que le budget d'erreur formalise).
  • Outillage : PagerDuty, Opsgenie, Grafana OnCall ; planning, escalade, acquittement, historique. Runbooks accessibles hors du système en panne (pas uniquement dans le wiki qui tourne sur le cluster).
  • Passation : un point hebdomadaire de 15 minutes entre sortant et entrant : ce qui s'est passé, ce qui est fragile, ce qui est planifié.

36.2 Conduire un incidentPar cœur

Détection ─► Déclaration ─► Triage ─► Mitigation ─► Résolution ─► Post-mortem
(alerte,     (canal dédié,   (sévérité,  (d'abord arrêter   (cause         (dans les 5 jours)
 utilisateur) rôles)          impact)     l'impact)          corrigée)
  • Sévérité : SEV1 (service majeur indisponible ou données à risque, tout le monde), SEV2 (dégradation importante, équipe d'astreinte), SEV3 (impact limité, heures ouvrées). Définie à l'avance, avec des exemples.
  • Rôles (à partir de SEV2) : commandant d'incident (coordonne, décide, ne débogue pas), responsable technique (investigue), communicant (statut interne et externe à intervalle fixe, ex. toutes les 30 min), scribe (chronologie horodatée). Une personne peut cumuler en petite équipe, mais le commandant ne débogue jamais.
  • Mitiger avant de comprendre : rollback, feature flag, bascule, redémarrage, augmentation de capacité. Comprendre vient après, quand les utilisateurs ne souffrent plus. Le réflexe « c'est le dernier déploiement ? » résout une majorité d'incidents.
  • Communication : page de statut (Statuspage, ou une page statique sur un hébergement indépendant), messages courts et factuels : impact, ce qu'on fait, prochaine mise à jour. Ne pas promettre d'heure de résolution.
  • Chronologie : tout est horodaté dans le canal d'incident (décisions, commandes, observations) ; c'est la matière du post-mortem. Un bot d'incident (incident.io, Rootly, ou un simple workflow Slack) automatise canal, rôles, chronologie.

36.3 Le post-mortem sans blâmePar cœur

Objectif : que le système (technique et organisationnel) devienne plus robuste, pas de trouver un coupable. Une personne qui a fait une erreur a agi rationnellement avec les informations et les outils qu'elle avait ; la question est « qu'est-ce qui a rendu cette erreur possible et son impact si grand ? ».

## Résumé
