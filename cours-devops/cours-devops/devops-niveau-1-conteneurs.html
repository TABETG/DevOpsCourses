7.1 Ce qu'est une machine virtuelleBon à savoir

Une VM est un ordinateur complet simulé : CPU virtuels, mémoire, disque, carte réseau, et son propre noyau. L'hyperviseur partage le matériel physique entre plusieurs VM.

Type 1 (bare metal)Type 2 (hébergé)
Tourne surDirectement le matérielUn OS hôte
ExemplesVMware ESXi, KVM, Hyper-V, XenVirtualBox, VMware Workstation
UsageDatacenter, cloud (AWS Nitro est dérivé de KVM)Poste de développeur

Vocabulaire à connaître : image disque (qcow2, VMDK, AMI chez AWS), snapshot, migration à chaud, sur-allocation (overcommit), extensions matérielles Intel VT-x / AMD-V.

7.2 VM contre conteneurPar cœur

Un conteneur n'est pas une petite VM. C'est un processus Linux ordinaire, isolé par le noyau de l'hôte grâce à trois mécanismes :

  • Namespaces : chaque conteneur voit ses propres PID, réseau, points de montage, utilisateurs, nom d'hôte. ps dans le conteneur ne voit que ses processus.
  • cgroups : limites de CPU, mémoire, I/O. C'est ce qui fait qu'un conteneur qui dépasse sa mémoire est tué (OOMKilled).
  • Système de fichiers en couches (OverlayFS) : l'image est une pile de couches en lecture seule, plus une couche d'écriture par conteneur.
Machine virtuelleConteneur
NoyauLe sienCelui de l'hôte, partagé
DémarrageSecondes à minutesMillisecondes
TailleGigaoctetsMégaoctets
IsolationForte (matériel virtuel)Plus faible (noyau partagé) : une faille noyau touche tous les conteneurs
Cas d'usageOS différents, isolation forte, charges legacyApplications, microservices, CI

Les deux se combinent : dans le cloud, un nœud Kubernetes est une VM qui fait tourner des conteneurs. Pour une isolation forte de conteneurs multi-locataires, il existe des micro-VM (Firecracker, gVisor, Kata) : c'est ce qui fait tourner AWS Lambda.

7.3 Docker sous Windows : ce qui se passe vraimentBon à savoir

Un conteneur Linux a besoin d'un noyau Linux. Sous Windows, Docker Desktop utilise WSL 2, une VM Linux légère gérée par Hyper-V. Le démon Docker tourne dans cette VM ; ton Git Bash parle au démon via un socket. Conséquences pratiques :

  • Les volumes montés depuis /c/Users/... traversent une frontière VM → performances I/O réduites. Pour un projet lourd, garde les sources dans le système de fichiers WSL (\\wsl$\) ou utilise des volumes nommés.
  • Git Bash convertit les chemins de type /c/... en C:\... et parfois des arguments comme /etc/nginx en C:\Program Files\Git\etc\nginx. Préfixe la commande par MSYS_NO_PATHCONV=1 quand un chemin Linux est mal interprété.
  • Les programmes interactifs ont parfois besoin de winpty.
  • Les fins de ligne \r\n cassent les scripts dans les conteneurs : .gitattributes avec eol=lf, vu au chapitre 5.
docker version              # client et serveur (Server: Docker Desktop, OS/Arch linux/amd64)
docker info | head -30      # runtime, cgroups, stockage
docker run --rm alpine uname -a   # le noyau vu du conteneur = noyau de la VM WSL
Techno de nichePour sortir du lot — Firecracker

La micro-VM d'AWS qui fait tourner Lambda et Fargate : démarrage en 125 ms, noyau minimal, isolation matérielle pour des charges non fiables. Kata Containers l'utilise comme runtime OCI, ce qui permet de lancer un « conteneur » qui est en réalité une VM.

Pourquoi ça différencie : Savoir expliquer la différence entre gVisor (noyau en espace utilisateur), Kata/Firecracker (micro-VM) et un conteneur classique est une question d'expert sur l'isolation multi-locataire.

À essayer en une heure : Nécessite KVM : sur une instance EC2 metal ou une VM avec virtualisation imbriquée (à combiner avec le TP 21), suivre le quickstart Firecracker et lancer une micro-VM en moins de dix commandes.

En entretien — « Différence entre VM et conteneur ? » Réponse en une phrase, puis les trois mécanismes : namespaces (isolation de ce qu'on voit), cgroups (limitation de ce qu'on consomme), couches (ce qu'on stocke). Puis la conséquence sécurité : noyau partagé. C'est ce niveau de réponse qui fait la différence.
Exercice 7.1

Un conteneur affiche « Killed » et son état indique OOMKilled: true. Quel mécanisme est en jeu et comment le constater ?

Corrigé
Les cgroups : la limite mémoire (--memory, ou les limits Kubernetes) est dépassée, le noyau tue le processus. docker inspect <id> | jq '.[0].State' montre OOMKilled ; docker stats montre la consommation en direct.
Exercice 7.2

Pourquoi ne peut-on pas faire tourner une image Windows Server sur un nœud Linux, ni une image Linux directement sur Windows sans WSL ?

Corrigé
Un conteneur partage le noyau de l'hôte. Une image Windows a besoin d'appels système Windows ; une image Linux a besoin d'un noyau Linux, fourni sous Windows par la VM WSL 2.
Travail pratique 7 — Voir l'isolation de ses propres yeux
  1. Lance docker run -d --name iso --memory 64m --cpus 0.5 alpine sleep 3600.
  2. Depuis Git Bash, ouvre un shell dans la VM WSL de Docker : docker run -it --rm --pid=host --privileged alpine sh. Dans ce shell, ps aux | grep sleep montre le processus du conteneur iso avec son PID hôte. Compare avec docker exec iso ps aux : c'est le namespace PID.
  3. Toujours dans le shell privilégié, lis la limite mémoire : cat /sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' iso 2>/dev/null || echo X)*/memory.max — si le chemin diffère, explore /sys/fs/cgroup avec find /sys/fs/cgroup -name memory.max | head. Retrouve la valeur 67108864.
  4. Fais dépasser la limite : docker exec iso sh -c 'head -c 100m /dev/zero | tail'. Observe le résultat et docker inspect iso | jq '.[0].State'.
  5. Montre les couches : docker image inspect alpine | jq '.[0].RootFS.Layers' puis docker history nginx:1.27.

8.2 Images et couchesPar cœur

Une image = un manifeste + des couches, chacune identifiée par un digest. Chaque instruction RUN, COPY, ADD du Dockerfile crée une couche. Docker met en cache : si une instruction et son contexte n'ont pas changé, la couche est réutilisée ; dès qu'une couche change, toutes les suivantes sont reconstruites. D'où la règle : ce qui change le moins en premier.

# Mauvais : chaque changement de code réinstalle les dépendances
COPY . .
RUN mvn package

# Bon : les dépendances sont mises en cache tant que le pom ne change pas
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

Un fichier supprimé dans une couche ultérieure reste dans l'image (couche précédente). Un secret copié puis effacé est toujours là : docker history et dive le révèlent.

8.3 Dockerfile : instructions et bonnes pratiquesPar cœur

# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY pom.xml mvnw ./
COPY .mvn .mvn
RUN --mount=type=cache,target=/root/.m2 ./mvnw -q dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 ./mvnw -q package -DskipTests

FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S app && adduser -S -G app app
WORKDIR /app
COPY --from=build --chown=app:app /app/target/*.jar app.jar
USER app
EXPOSE 8080
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75"
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s \
  CMD wget -qO- http://localhost:8080/actuator/health/liveness || exit 1
ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS -jar app.jar"]
  • Multi-étapes : l'image finale ne contient ni JDK ni Maven ni sources. De 700 Mo à 200 Mo.
  • ENTRYPOINT définit l'exécutable, CMD ses arguments par défaut. Forme exec (["java","-jar"]) : le processus est PID 1 et reçoit SIGTERM. Forme shell (java -jar) : c'est sh qui est PID 1 et ne relaie pas les signaux, sauf avec exec.
  • COPY plutôt qu'ADD (ADD décompresse et télécharge, source de surprises).
  • .dockerignore : exclure .git, target, node_modules, .env. Réduit le contexte envoyé au démon et évite les fuites.
  • Épingler les versions de base (:21-jre-alpine, jamais :latest), idéalement par digest en production.
  • RUN --mount=type=cache et --mount=type=secret (BuildKit) : cache de dépendances entre builds, secrets de build absents de l'image.
  • Une seule instruction RUN apt-get update && apt-get install -y ... && rm -rf /var/lib/apt/lists/* : sinon la couche du cache apt reste.

Images de base, du plus gros au plus sûr : ubuntu → debian-slim → alpine (musl, parfois incompatible) → distroless (Google, pas de shell) → scratch (binaire statique Go). Moins il y a de paquets, moins il y a de CVE.

docker build -t crisisshield-api:1.0.0 .
docker build --no-cache --progress=plain .    # voir tout
docker build --target build -t api-builder .   # s'arrêter à une étape
docker buildx build --platform linux/amd64,linux/arm64 -t image:tag --push .

8.6 Sécurité des conteneursPar cœur

Par défaut, un conteneur tourne en root et le démon Docker est root sur l'hôte : accès au socket /var/run/docker.sock = root sur la machine. Mesures, de la plus simple à la plus avancée :

  1. Utilisateur non root dans l'image (USER app) et/ou --user 1000:1000.
  2. Image minimale, versions épinglées, scan régulier (chapitre 10).
  3. Système de fichiers en lecture seule : --read-only --tmpfs /tmp. Un attaquant ne peut rien écrire.
  4. Capabilities : --cap-drop ALL --cap-add NET_BIND_SERVICE. Root sans capabilities ne peut presque rien.
  5. Pas d'escalade : --security-opt no-new-privileges.
  6. Limites de ressources : --memory, --cpus, --pids-limit contre les fork bombs.
  7. Jamais --privileged ni montage du socket Docker dans un conteneur applicatif.
  8. Secrets : pas dans ENV ni dans l'image ; fichier monté, secret Compose, ou gestionnaire externe (Vault, niveau 7).
  9. Docker rootless et runtimes durcis (gVisor) pour l'isolation forte.
docker run -d --name api --user 1000:1000 --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges --memory 512m --pids-limit 200 \
  --network backend -p 8080:8080 crisisshield-api:1.0.0

8.7 DéboguerPar cœur

docker logs --tail 100 api                 # 1. les logs
docker inspect api | jq '.[0].State'       # 2. ExitCode, OOMKilled, Error
docker run -it --rm --entrypoint sh image  # 3. entrer sans lancer l'app
docker exec -it api sh                     # 4. si l'app tourne
docker events --since 10m                  # 5. ce qui s'est passé
docker run --rm -it --network container:api nicolaka/netshoot   # 6. outils réseau dans le namespace de l'app

Codes de sortie : 0 succès, 1 erreur applicative, 125 erreur du démon, 126 commande non exécutable, 127 commande introuvable, 137 = 128+9 SIGKILL (OOM ou docker kill), 143 = 128+15 SIGTERM.

Techno de nichePour sortir du lot — Wolfi et apko (Chainguard)

Une « distribution sans distribution » : des images minimales construites déclarativement par apko à partir de paquets Wolfi (melange pour en compiler), avec SBOM natif, mises à jour quotidiennes, et souvent zéro CVE. Les images cgr.dev/chainguard/jre en sont issues.

Pourquoi ça différencie : C'est l'état de l'art des images durcies ; comparer Trivy sur jre-alpine et sur une image Chainguard est un argument massue en entretien DevSecOps.

À essayer en une heure : Un apko.yaml avec contents.packages: [wolfi-base, openjdk-21-jre], puis docker run --rm -v "$PWD:/w" -w /w cgr.dev/chainguard/apko build apko.yaml api:wolfi api.tar et docker load < api.tar.

En entretien — « Comment tu réduis la taille et la surface d'attaque d'une image Java ? » Multi-étapes JDK → JRE, base slim ou distroless, non root, versions épinglées, .dockerignore, une couche par groupe de changement, scan Trivy dans la CI. Ajoute MaxRAMPercentage et la forme exec de l'ENTRYPOINT : tu montres que tu as exploité du Java en conteneur.

Chapitre 9Confirmé

Docker Compose

À la fin de ce chapitre, tu sauras
  • Décrire une pile complète dans un fichier Compose : services, réseaux, volumes, secrets
  • Gérer les dépendances et l'ordre de démarrage avec les healthchecks

En 30 secondes
  1. Compose décrit une pile complète : services, réseaux, volumes, secrets, healthchecks.
  2. depends_on n'attend pas la disponibilité sans condition: service_healthy ; l'application doit retenter de toute façon.
  3. Override, profils et .env séparent dev et prod ; Compose pilote un seul hôte.

9.1 Anatomie d'un fichier ComposePar cœur

# compose.yaml  (le nom docker-compose.yml fonctionne aussi ; la clé "version" est obsolète)
name: crisisshield

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: crisis
      POSTGRES_USER: crisis
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks: [backend]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U crisis -d crisis"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    build:
      context: ./backend
      dockerfile: Dockerfile
    image: crisisshield-api:${TAG:-dev}
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/crisis
      SPRING_DATASOURCE_USERNAME: crisis
      SPRING_DATASOURCE_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    depends_on:
      db:
        condition: service_healthy
    networks: [backend, frontend]
    user: "1000:1000"
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
    deploy:
      resources:
        limits: {memory: 512m, cpus: "1.0"}
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/actuator/health/readiness"]
      interval: 10s
      start_period: 30s
      retries: 5
    restart: unless-stopped

  web:
    build: ./frontend
    ports: ["8080:8080"]
    depends_on:
      api:
        condition: service_healthy
    networks: [frontend]
    restart: unless-stopped

networks:
  backend:
  frontend:

volumes:
  pgdata:

secrets:
  db_password:
    file: ./secrets/db_password.txt

Points clés : deux réseaux (la base n'est pas joignable depuis web), un seul port publié, secrets en fichier et non en variable (jamais visibles dans docker inspect), depends_on avec condition (sans condition, Compose attend seulement le démarrage, pas la disponibilité).

9.3 Variables, surcharges, profilsImportant

  • .env à côté du fichier : variables interpolées dans le YAML (${TAG:-dev}). À ne pas commiter ; commiter un .env.example.
  • Surcharge : compose.override.yaml est fusionné automatiquement (dev : bind mounts, ports de debug). En production : docker compose -f compose.yaml -f compose.prod.yaml up -d.
  • Profils : profiles: [tools] sur un service (pgAdmin, Mailhog) qu'on ne lance qu'avec --profile tools.
  • Extension : x-common: &common puis <<: *common pour factoriser logging, restart, etc.
# compose.override.yaml (développement)
services:
  api:
    build: {target: build}
    command: ./mvnw spring-boot:run
    volumes: ["./backend/src:/app/src"]
    ports: ["5005:5005"]
    environment:
      JAVA_TOOL_OPTIONS: -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005
    read_only: false

9.4 Ce que Compose ne fait pasBon à savoir

Compose pilote un seul hôte. Pas de haute disponibilité, pas de redémarrage sur un autre nœud, pas de rolling update natif, pas de secrets chiffrés au repos. C'est parfait pour le développement, la CI, et de petites productions à un serveur. Au-delà : Kubernetes (niveau 5). Le fichier Compose reste un excellent document de l'architecture.

Techno de nichePour sortir du lot — Podman et Quadlet

Podman exécute des conteneurs sans démon et sans root par défaut ; Quadlet décrit des conteneurs et des pods dans des fichiers .container/.pod que systemd transforme en services. C'est la façon Red Hat de servir des conteneurs sur des VM, sans Kubernetes ni Compose.

Pourquoi ça différencie : Très présent dans le secteur public et bancaire français (RHEL) ; rootless par défaut, c'est un argument sécurité immédiat.

À essayer en une heure : docker run --rm -it --privileged quay.io/podman/stable podman run --rm alpine echo ok, puis écrire le fichier crisisshield-api.container équivalent à ton service Compose.

En entretien — « depends_on suffit pour que l'API attende la base ? » Non : sans condition: service_healthy, Compose attend le lancement du conteneur, pas que PostgreSQL accepte des connexions. Et en production, l'application doit de toute façon retenter (résilience), car la base peut redémarrer à tout moment.

Registres, tagging et scan de vulnérabilités

À la fin de ce chapitre, tu sauras
  • Publier et récupérer des images dans un registre privé ou public
  • Appliquer une stratégie de tags qui permet le retour arrière et la traçabilité

En 30 secondes
  1. latest est interdit en production : tags immuables (SHA, version) et déploiement par digest.
  2. Scanner (Trivy), produire un SBOM, signer (Cosign) : contenu, inventaire, origine.
  3. Le SBOM permet de répondre à une nouvelle CVE en secondes, sans rescanner.

10.1 RegistresBon à savoir

Un registre stocke images et manifestes selon la spécification OCI. Docker Hub (public, limites de pull), GitHub Container Registry (ghcr.io), GitLab Container Registry, AWS ECR, Harbor (auto-hébergé, avec scan et réplication), ou le registre officiel minimal registry:2.

docker run -d -p 5000:5000 --name registry -v regdata:/var/lib/registry registry:2
docker tag crisisshield-api:1.0.0 localhost:5000/crisisshield/api:1.0.0
docker push localhost:5000/crisisshield/api:1.0.0
curl -s localhost:5000/v2/_catalog ; curl -s localhost:5000/v2/crisisshield/api/tags/list
docker login ghcr.io -u USER --password-stdin < token.txt   # jamais le mot de passe en argument

Nom complet d'une image : registre/espace/nom:tag@sha256:digest. Sans registre → Docker Hub ; sans tag → latest.

10.2 Stratégie de tagsPar cœur

latest ne veut rien dire : il pointe sur la dernière image poussée, quelle qu'elle soit. En production, il empêche de savoir ce qui tourne et de revenir en arrière. Un tag est mutable ; un digest ne l'est pas.

TagExempleUsage
Version sémantique1.4.2, 1.4, 1Livraisons ; les tags courts glissent vers le dernier correctif
SHA du commitsha-3f9a2b1Traçabilité exacte, une image par commit
Branchemain, developEnvironnements d'intégration
Digest@sha256:ab12...Déploiement en production, pinning immuable

Pratique recommandée : la CI construit une fois, tague avec le SHA du commit, puis ajoute la version sémantique au moment de la release (retag sans reconstruction). Le déploiement référence le digest. Politique de rétention dans le registre pour ne pas exploser le stockage.

10.3 Scanner une imageImportant

Une image embarque un OS et des bibliothèques qui ont des CVE. Trivy (Aqua) est l'outil de référence, gratuit, utilisable dans la CI :

# Scan complet, vulnérabilités OS + dépendances applicatives (jar, npm...)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v trivy-cache:/root/.cache \
  aquasec/trivy image crisisshield-api:1.0.0

# Ne remonter que critique et haute, échouer si présentes (pour la CI)
... aquasec/trivy image --severity HIGH,CRITICAL --exit-code 1 --ignore-unfixed crisisshield-api:1.0.0

# Scanner le Dockerfile et la config (mauvaises pratiques)
docker run --rm -v "$PWD:/w" aquasec/trivy config /w

# Générer un SBOM (inventaire des composants)
... aquasec/trivy image --format cyclonedx --output sbom.json crisisshield-api:1.0.0

Lire un rapport : la sévérité CVSS, si un correctif existe (« fixed version »), et si le composant est réellement utilisé. Un --ignore-unfixed évite de bloquer sur des CVE sans correctif ; un fichier .trivyignore documente les acceptations de risque, avec justification et date.

SBOM (Software Bill of Materials) : la liste de tout ce que contient l'image, au format CycloneDX ou SPDX. Exigé par de plus en plus de clients et de réglementations (Cyber Resilience Act). Il permet, quand une nouvelle CVE sort (type Log4Shell), de savoir en quelques secondes quelles images sont concernées sans tout rescanner.

10.4 Signer et vérifierImportant

Un scan dit ce qu'il y a dans l'image ; une signature dit qui l'a produite et qu'elle n'a pas été modifiée. Cosign (projet Sigstore) signe le digest et stocke la signature dans le registre à côté de l'image.

docker run --rm -it -v "$PWD:/w" -w /w gcr.io/projectsigstore/cosign generate-key-pair
docker run --rm -it -v "$PWD:/w" -w /w -e COSIGN_PASSWORD gcr.io/projectsigstore/cosign \
  sign --key cosign.key localhost:5000/crisisshield/api@sha256:...
docker run --rm -v "$PWD:/w" -w /w gcr.io/projectsigstore/cosign \
  verify --key cosign.pub localhost:5000/crisisshield/api:1.0.0

En CI, on signe sans clé (keyless) avec l'identité OIDC du pipeline. Kubernetes peut refuser toute image non signée (Kyverno, niveau 7). C'est la base de la sécurité de la chaîne d'approvisionnement (SLSA).

Techno de nichePour sortir du lot — ORAS et Zot

ORAS pousse n'importe quel artefact (SBOM, chart, plan Terraform, modèle ML, fichier de politique) dans un registre OCI, avec tags, digests et signatures Cosign ; Zot est un registre OCI natif (CNCF) léger avec scan et synchronisation.

Pourquoi ça différencie : Un seul système de distribution pour tous les artefacts, signé et versionné : c'est ce que les plateformes matures font désormais.

À essayer en une heure : docker run --rm --network host ghcr.io/oras-project/oras:v1.2.0 push localhost:5000/crisisshield/sbom:1.0.0 sbom.json:application/json puis oras pull depuis un autre conteneur.

En entretien — « Comment tu garantis qu'une image en prod est celle que la CI a construite ? » Réponse : build unique dans la CI, tag par SHA de commit, scan Trivy bloquant, SBOM publié, signature Cosign, déploiement par digest, vérification de signature à l'admission. Cinq mots-clés qui te placent immédiatement sur le terrain DevSecOps.
Exercice 10.1

L'équipe déploie api:latest en production. Vendredi soir, un développeur pousse une image cassée avec ce tag. Que se passe-t-il au prochain redémarrage d'un conteneur, et comment l'éviter structurellement ?
