7.1 Ce qu'est une machine virtuelleBon à savoir

Une VM est un ordinateur complet simulé : CPU virtuels, mémoire, disque, carte réseau, et son propre noyau. L'hyperviseur partage le matériel physique entre plusieurs VM.

Type 1 (bare metal)Type 2 (hébergé)
Tourne surDirectement le matérielUn OS hôte
ExemplesVMware ESXi, KVM, Hyper-V, XenVirtualBox, VMware Workstation
UsageDatacenter, cloud (AWS Nitro est dérivé de KVM)Poste de développeur

Vocabulaire à connaître : image disque (qcow2, VMDK, AMI chez AWS), snapshot, migration à chaud, sur-allocation (overcommit), extensions matérielles Intel VT-x / AMD-V.

7.2 VM contre conteneurPar cœur

Un conteneur n'est pas une petite VM. C'est un processus Linux ordinaire, isolé par le noyau de l'hôte grâce à trois mécanismes :

  • Namespaces : chaque conteneur voit ses propres PID, réseau, points de montage, utilisateurs, nom d'hôte. ps dans le conteneur ne voit que ses processus.
  • cgroups : limites de CPU, mémoire, I/O. C'est ce qui fait qu'un conteneur qui dépasse sa mémoire est tué (OOMKilled).
  • Système de fichiers en couches (OverlayFS) : l'image est une pile de couches en lecture seule, plus une couche d'écriture par conteneur.
Machine virtuelleConteneur
NoyauLe sienCelui de l'hôte, partagé
DémarrageSecondes à minutesMillisecondes
TailleGigaoctetsMégaoctets
IsolationForte (matériel virtuel)Plus faible (noyau partagé) : une faille noyau touche tous les conteneurs
Cas d'usageOS différents, isolation forte, charges legacyApplications, microservices, CI

Les deux se combinent : dans le cloud, un nœud Kubernetes est une VM qui fait tourner des conteneurs. Pour une isolation forte de conteneurs multi-locataires, il existe des micro-VM (Firecracker, gVisor, Kata) : c'est ce qui fait tourner AWS Lambda.

7.3 Docker sous Windows : ce qui se passe vraimentBon à savoir

Un conteneur Linux a besoin d'un noyau Linux. Sous Windows, Docker Desktop utilise WSL 2, une VM Linux légère gérée par Hyper-V. Le démon Docker tourne dans cette VM ; ton Git Bash parle au démon via un socket. Conséquences pratiques :

  • Les volumes montés depuis /c/Users/... traversent une frontière VM → performances I/O réduites. Pour un projet lourd, garde les sources dans le système de fichiers WSL (\\wsl$\) ou utilise des volumes nommés.
  • Git Bash convertit les chemins de type /c/... en C:\... et parfois des arguments comme /etc/nginx en C:\Program Files\Git\etc\nginx. Préfixe la commande par MSYS_NO_PATHCONV=1 quand un chemin Linux est mal interprété.
  • Les programmes interactifs ont parfois besoin de winpty.
  • Les fins de ligne \r\n cassent les scripts dans les conteneurs : .gitattributes avec eol=lf, vu au chapitre 5.
docker version              # client et serveur (Server: Docker Desktop, OS/Arch linux/amd64)
docker info | head -30      # runtime, cgroups, stockage
docker run --rm alpine uname -a   # le noyau vu du conteneur = noyau de la VM WSL

Proxmox VE en pratique

# Sur un nœud Proxmox (ou via l'API : tout ce qui suit existe en REST)
pveversion ; pvecm status ; pvecm nodes                 # version ; état du cluster corosync ; nœuds
qm list ; qm config 100 ; qm start 100 ; qm shutdown 100 ; qm migrate 100 node2 --online   # VM (QEMU/KVM)
pct list ; pct enter 200 ; pct exec 200 -- apt update    # conteneurs LXC
qm create 9000 --name ubuntu-tpl --memory 2048 --net0 virtio,bridge=vmbr0 --scsihw virtio-scsi-pci
qm importdisk 9000 noble-server-cloudimg-amd64.img local-lvm ; qm set 9000 --ide2 local-lvm:cloudinit --boot order=scsi0 ; qm template 9000   # template cloud-init
qm clone 9000 101 --name web1 --full ; qm set 101 --ipconfig0 ip=10.0.1.11/24,gw=10.0.1.1 --sshkeys ~/.ssh/id_ed25519.pub
pvesm status ; pvesm list local-lvm                      # stockages
vzdump 101 --storage pbs --mode snapshot                  # sauvegarde (vers Proxmox Backup Server)
ha-manager add vm:101 --state started ; ha-manager status # haute disponibilité
pveum user add ci@pve ; pveum aclmod / -user ci@pve -role PVEVMAdmin ; pveum user token add ci@pve terraform   # compte et token pour l'IaC
journalctl -u pve-cluster -u corosync -f                  # quand le cluster tousse
# Terraform : une VM depuis le template cloud-init (provider bpg/proxmox)
provider "proxmox" { endpoint = "https://pve.lab:8006/", api_token = var.pve_token, insecure = false }
resource "proxmox_virtual_environment_vm" "web" {
  name = "web1" ; node_name = "pve1"
  clone { vm_id = 9000 }
  cpu { cores = 2 } ; memory { dedicated = 2048 }
  initialization {
    ip_config { ipv4 { address = "10.0.1.11/24", gateway = "10.0.1.1" } }
    user_account { username = "deploy", keys = [var.ssh_pub] }
  }
}
# Ansible : inventaire dynamique des VM Proxmox (plugin community.general.proxmox) puis les rôles du chapitre 17
  • Cluster : trois nœuds minimum (quorum corosync ; deux nœuds + QDevice sinon), réseau dédié à corosync et un autre à Ceph, horloges synchronisées. Un nœud isolé du quorum fence ses VM HA : c'est voulu.
  • Stockage : ZFS local pour la simplicité et les snapshots ; Ceph pour le partagé et la HA (trois nœuds, disques NVMe, réseau 10 Gbit minimum) ; NFS pour les ISO et sauvegardes.
  • Sauvegarde : Proxmox Backup Server sur une machine distincte, vérification des sauvegardes planifiée, restauration testée ; 3-2-1 comme au chapitre 44.
  • Sécurité : pare-feu intégré par datacenter, nœud et VM ; utilisateurs avec rôles minimaux et tokens d'API (jamais root@pam pour l'IaC) ; MFA (TOTP, WebAuthn) ; certificats ACME intégrés ; mises à jour de l'hôte Debian.
  • Kubernetes dessus : Talos Linux (chapitre 18) ou RKE2 sur des VM clonées par Terraform ; le stockage persistant par Ceph CSI ou Longhorn ; MetalLB pour les Services LoadBalancer.

Nutanix en pratique

# Depuis une CVM (Controller VM) ou Prism ; l'API v4 et Terraform couvrent tout
ncli cluster info ; ncli host list ; ncli vm list          # cluster, hôtes, VM (interface historique)
acli vm.list ; acli vm.create web1 memory=2G num_vcpus=2 ; acli vm.disk_create web1 clone_from_image=ubuntu-24.04 ; acli vm.on web1   # AHV
acli vm.snapshot_create web1 snapshot_name=avant-migration ; acli vm.clone web2 clone_from_vm=web1
acli net.list ; acli image.list                              # réseaux, catalogue d'images
nutanix_cluster_check ; ncc health_checks run_all            # NCC : vérifications de santé
cluster status ; allssh "date"                               # état et commande sur tous les nœuds
# Prism Central : catégories (étiquettes) → politiques Flow (microsegmentation), protection (snapshots, réplication), Calm (blueprints self-service), NKP (clusters Kubernetes)
# Terraform : VM sur AHV (provider nutanix/nutanix)
provider "nutanix" { username = var.user, password = var.password, endpoint = "prism-central.lab", insecure = false }
resource "nutanix_virtual_machine" "web" {
  name = "web1" ; cluster_uuid = data.nutanix_cluster.c.id
  num_vcpus_per_socket = 2 ; memory_size_mib = 2048
  disk_list { data_source_reference = { kind = "image", uuid = data.nutanix_image.ubuntu.id } }
  nic_list { subnet_uuid = data.nutanix_subnet.app.id }
  guest_customization_cloud_init_user_data = base64encode(file("cloud-init.yaml"))
  categories { name = "Environment", value = "prod" }     # pilote Flow et les politiques de protection
}
# Ansible : collection nutanix.ncp (ntnx_vms, ntnx_images, inventaire dynamique)
  • Hyperconvergence : chaque nœud apporte calcul et stockage ; la CVM de chaque nœud forme le stockage distribué AOS (réplication RF2 ou RF3, localité des données). Ajouter un nœud ajoute les deux ; c'est simple à exploiter et à faire grandir, et c'est ce qu'on paie.
  • Catégories : le mécanisme central ; elles pilotent la microsegmentation Flow (politiques par catégorie, pas par IP), la protection des données (calendriers de snapshots et réplication vers un autre site : le PRA du chapitre 44), le placement et les quotas.
  • Exploitation : mises à jour orchestrées par LCM (firmware, AOS, AHV, sans coupure), NCC pour la santé, Prism Central pour la vue multi-clusters, l'analyse de capacité et le coût ; support Nutanix comme argument principal.
  • Migration : Nutanix Move migre des VM depuis VMware, Hyper-V ou AWS avec réplication continue puis bascule courte ; c'est l'outil de la sortie de VMware. NC2 permet d'étendre le cluster sur AWS ou Azure (hybride, chapitre 24).
  • Kubernetes : NKP fournit des clusters conformes gérés depuis Prism, avec CSI Nutanix pour les volumes ; sinon Talos ou RKE2 comme sur Proxmox.

Ce que le DevOps y fait

Il ne clique pas dans Prism ni dans l'interface Proxmox : il décrit les VM en Terraform à partir de templates cloud-init construits par Packer, les configure par Ansible avec un inventaire dynamique, y déploie Kubernetes par Cluster API ou Talos, branche la sauvegarde et le monitoring (exporters Proxmox et Nutanix pour Prometheus), et traite la plateforme de virtualisation comme une ressource de la landing zone (chapitre 49) avec ses SLO (chapitre 43). Une sortie de VMware est un projet de migration classique (chapitre 50) : inventaire, dépendances, vagues, Move ou export OVF, tests, décommissionnement.

7.5 Construire un homelab DevSecOps, « security-first »Important

Un homelab est le seul endroit où tu peux casser un pare-feu, planter un cluster et le reconstruire à 23 h sans conséquence : c'est ce qui transforme ce parcours en compétence réelle, et ce qu'un recruteur ne peut pas obtenir d'une IA. Cette section s'appuie sur le parcours HomeLab DevSecOps de Stéphane Robert, une référence francophone, et le relie aux chapitres de ce cours.

Ce parcours impose « tout en Docker, rien en local » pour les TP : le homelab est l'exception assumée, c'est du matériel dédié (ou une VM cloud avec virtualisation imbriquée), jamais ton poste de travail. Sans matériel, la variante « homelab virtuel » ci-dessous couvre 80 % de l'apprentissage.

Le piège du homelab classique, et l'ordre inverse

La trajectoire habituelle : Proxmox sur un mini-PC, quelques VM, un K3s, un reverse proxy, des secrets en clair dans des YAML, « je sécuriserai plus tard ». Résultat : chaque service a ses propres identifiants, les mots de passe traînent dans l'historique Git, l'accès admin n'a pas d'authentification centrale. L'approche security-first inverse l'ordre : réseau → identité → secrets → charges de travail. Chaque nouveau service hérite alors du SSO, des secrets dynamiques, des certificats et des journaux, sans effort. C'est exactement la logique de la plateforme du chapitre 48, et celle des règles de plateforme du chapitre 43.3 (pas de dépendance circulaire).

Pourquoi la couche de confiance vit hors du cluster : si l'IdP tourne dans le cluster et que le cluster a un problème d'authentification, tu ne peux plus te connecter pour le réparer. Identité, secrets et PKI doivent survivre à la destruction du cluster pour permettre de le reconstruire. Même règle en entreprise : l'IdP de l'astreinte, l'outil d'incident et la documentation ne dépendent pas de la plateforme qu'ils servent.

Si tu dois arbitrer, sacrifie la phase 4 avant la phase 1 : un pare-feu mal posé se paie sur toutes les couches, un SBOM manquant ne casse aucun service. Et documente ton installation dès le premier jour : dans six mois, c'est ton futur toi qui reconstruit.

Matériel, et variante sans matériel

  • Matériel : un mini-PC à deux interfaces réseau pour OPNsense (Intel N100 suffit), un mini-PC pour le nœud admin, un ou trois mini-PC (N100, Ryzen) pour le cluster, un switch manageable pour les VLAN, un SSD par nœud ; budget de 500 à 1 000 € pour un ensemble complet, silencieux et sobre. Pas de serveur rack : bruit, consommation, et rien de plus à apprendre.
  • Homelab virtuel : une seule machine (ou une VM cloud avec virtualisation imbriquée, comme un serveur Hetzner à quelques euros par mois) qui fait tourner Proxmox, avec OPNsense, le nœud admin et Talos en VM à l'intérieur. Tu perds la vraie segmentation physique et le switch, tu gardes tout le reste : VLAN virtuels, IdP, OpenBao, PKI, cluster, GitOps, chaîne d'approvisionnement. C'est la version compatible avec ta règle « rien sur le poste ».
  • Ce que ce cours te fait déjà faire en Docker (kind, Vault, Keycloak, ArgoCD, Prometheus) est la phase 3 et 4 en miniature ; le homelab ajoute le réseau, la virtualisation et l'exploitation dans la durée : sauvegardes, mises à jour, pannes réelles.

En entretien — « Vous avez un homelab ? » est une vraie question de recruteur DevSecOps. La bonne réponse décrit une architecture, pas une liste de VM : « réseau segmenté par OPNsense, identité et secrets hors cluster pour éviter la dépendance circulaire, Talos piloté en GitOps, images signées vérifiées à l'admission ». Puis une panne que tu as réparée toi-même, et ce que tu en as changé.
Techno de nichePour sortir du lot — Firecracker

La micro-VM d'AWS qui fait tourner Lambda et Fargate : démarrage en 125 ms, noyau minimal, isolation matérielle pour des charges non fiables. Kata Containers l'utilise comme runtime OCI, ce qui permet de lancer un « conteneur » qui est en réalité une VM.

Pourquoi ça différencie : Savoir expliquer la différence entre gVisor (noyau en espace utilisateur), Kata/Firecracker (micro-VM) et un conteneur classique est une question d'expert sur l'isolation multi-locataire.

À essayer en une heure : Nécessite KVM : sur une instance EC2 metal ou une VM avec virtualisation imbriquée (à combiner avec le TP 21), suivre le quickstart Firecracker et lancer une micro-VM en moins de dix commandes.

En entretien — « Différence entre VM et conteneur ? » Réponse en une phrase, puis les trois mécanismes : namespaces (isolation de ce qu'on voit), cgroups (limitation de ce qu'on consomme), couches (ce qu'on stocke). Puis la conséquence sécurité : noyau partagé. C'est ce niveau de réponse qui fait la différence.
Exercice 7.1

Un conteneur affiche « Killed » et son état indique OOMKilled: true. Quel mécanisme est en jeu et comment le constater ?

Corrigé
Les cgroups : la limite mémoire (--memory, ou les limits Kubernetes) est dépassée, le noyau tue le processus. docker inspect <id> | jq '.[0].State' montre OOMKilled ; docker stats montre la consommation en direct.
Exercice 7.2

Pourquoi ne peut-on pas faire tourner une image Windows Server sur un nœud Linux, ni une image Linux directement sur Windows sans WSL ?

Corrigé
Un conteneur partage le noyau de l'hôte. Une image Windows a besoin d'appels système Windows ; une image Linux a besoin d'un noyau Linux, fourni sous Windows par la VM WSL 2.
Exercice 7.3

Une collectivité de 40 VM, deux administrateurs Linux, budget en baisse, doit quitter VMware. Proxmox ou Nutanix ? Argumente, puis indique ce qui te ferait changer d'avis.

Corrigé
Proxmox : coût de licence nul (support par socket abordable), KVM et Debian que les administrateurs connaissent, ZFS ou Ceph selon le nombre de nœuds, Proxmox Backup Server, IaC par Terraform et Ansible. Changerait la décision : exigence de support éditeur contractuel fort, équipe sans compétence Linux, besoin d'hyperconvergence à grande échelle avec LCM et réplication multi-sites clé en main, ou un existant Nutanix ailleurs dans l'organisation ; alors Nutanix, malgré le coût.
Exercice 7.4

Un cluster Proxmox à deux nœuds redémarre spontanément ses VM HA quand le lien réseau entre les nœuds tombe. Explique et corrige.

Corrigé
Sans quorum (deux nœuds = pas de majorité possible en cas de coupure), chaque nœud se croit isolé ; le fencing HA arrête ses VM pour éviter une double exécution. Correction : un troisième vote (QDevice sur une petite machine, ou un troisième nœud), un réseau corosync dédié et redondant, et ne mettre en HA que ce qui doit l'être.
Exercice 7.5

Ton homelab tourne : Keycloak et Vault sont déployés dans le cluster Talos, comme le reste. Un soir, une mise à jour de Talos casse le CNI ; plus aucun Pod ne communique. Que se passe-t-il quand tu veux te connecter à ArgoCD pour revenir en arrière, et comment l'architecture security-first l'évite ?

Corrigé
ArgoCD délègue son authentification à Keycloak, qui tourne dans le cluster cassé : impossible de se connecter, et External Secrets ne peut plus lire Vault, lui aussi dans le cluster. C'est la dépendance circulaire. Avec l'IdP, le coffre et la PKI sur le nœud admin hors cluster, tu te connectes encore (Tailscale, IdP vivant), tu reconstruis le cluster depuis Git, External Secrets resynchronise les secrets et tout revient. Même principe qu'en entreprise pour l'IdP de l'astreinte et l'outil d'incident.
Travail pratique 7 — Voir l'isolation de ses propres yeux

Options de run à connaître : -e VAR=val et --env-file, -v ou --mount, --network, --memory, --cpus, --user, --read-only, --cap-drop, --health-cmd, --init (un vrai PID 1 qui relaie les signaux).

8.2 Images et couchesPar cœur

Une image = un manifeste + des couches, chacune identifiée par un digest. Chaque instruction RUN, COPY, ADD du Dockerfile crée une couche. Docker met en cache : si une instruction et son contexte n'ont pas changé, la couche est réutilisée ; dès qu'une couche change, toutes les suivantes sont reconstruites. D'où la règle : ce qui change le moins en premier.

# Mauvais : chaque changement de code réinstalle les dépendances
COPY . .
RUN mvn package

# Bon : les dépendances sont mises en cache tant que le pom ne change pas
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

Un fichier supprimé dans une couche ultérieure reste dans l'image (couche précédente). Un secret copié puis effacé est toujours là : docker history et dive le révèlent.

8.3 Dockerfile : instructions et bonnes pratiquesPar cœur

# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY pom.xml mvnw ./
COPY .mvn .mvn
RUN --mount=type=cache,target=/root/.m2 ./mvnw -q dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 ./mvnw -q package -DskipTests

FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S app && adduser -S -G app app
WORKDIR /app
COPY --from=build --chown=app:app /app/target/*.jar app.jar
USER app
EXPOSE 8080
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75"
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s \
  CMD wget -qO- http://localhost:8080/actuator/health/liveness || exit 1
ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS -jar app.jar"]
  • Multi-étapes : l'image finale ne contient ni JDK ni Maven ni sources. De 700 Mo à 200 Mo.
  • ENTRYPOINT définit l'exécutable, CMD ses arguments par défaut. Forme exec (["java","-jar"]) : le processus est PID 1 et reçoit SIGTERM. Forme shell (java -jar) : c'est sh qui est PID 1 et ne relaie pas les signaux, sauf avec exec.
  • COPY plutôt qu'ADD (ADD décompresse et télécharge, source de surprises).
  • .dockerignore : exclure .git, target, node_modules, .env. Réduit le contexte envoyé au démon et évite les fuites.
  • Épingler les versions de base (:21-jre-alpine, jamais :latest), idéalement par digest en production.
  • RUN --mount=type=cache et --mount=type=secret (BuildKit) : cache de dépendances entre builds, secrets de build absents de l'image.
  • Une seule instruction RUN apt-get update && apt-get install -y ... && rm -rf /var/lib/apt/lists/* : sinon la couche du cache apt reste.

Images de base, du plus gros au plus sûr : ubuntu → debian-slim → alpine (musl, parfois incompatible) → distroless (Google, pas de shell) → scratch (binaire statique Go). Moins il y a de paquets, moins il y a de CVE.

docker build --no-cache --progress=plain .    # voir tout
docker build --target build -t api-builder .   # s'arrêter à une étape
docker buildx build --platform linux/amd64,linux/arm64 -t image:tag --push .

8.6 Sécurité des conteneursPar cœur

Par défaut, un conteneur tourne en root et le démon Docker est root sur l'hôte : accès au socket /var/run/docker.sock = root sur la machine. Mesures, de la plus simple à la plus avancée :

  1. Utilisateur non root dans l'image (USER app) et/ou --user 1000:1000.
  2. Image minimale, versions épinglées, scan régulier (chapitre 10).
  3. Système de fichiers en lecture seule : --read-only --tmpfs /tmp. Un attaquant ne peut rien écrire.
  4. Capabilities : --cap-drop ALL --cap-add NET_BIND_SERVICE. Root sans capabilities ne peut presque rien.
  5. Pas d'escalade : --security-opt no-new-privileges.
  6. Limites de ressources : --memory, --cpus, --pids-limit contre les fork bombs.
  7. Jamais --privileged ni montage du socket Docker dans un conteneur applicatif.
  8. Secrets : pas dans ENV ni dans l'image ; fichier monté, secret Compose, ou gestionnaire externe (Vault, niveau 7).
  9. Docker rootless et runtimes durcis (gVisor) pour l'isolation forte.
docker run -d --name api --user 1000:1000 --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges --memory 512m --pids-limit 200 \
  --network backend -p 8080:8080 crisisshield-api:1.0.0

8.7 DéboguerPar cœur

docker logs --tail 100 api                 # 1. les logs
docker inspect api | jq '.[0].State'       # 2. ExitCode, OOMKilled, Error
docker run -it --rm --entrypoint sh image  # 3. entrer sans lancer l'app
docker exec -it api sh                     # 4. si l'app tourne
docker events --since 10m                  # 5. ce qui s'est passé

Codes de sortie : 0 succès, 1 erreur applicative, 125 erreur du démon, 126 commande non exécutable, 127 commande introuvable, 137 = 128+9 SIGKILL (OOM ou docker kill), 143 = 128+15 SIGTERM.

Chapitre 9Confirmé

Docker Compose

En 30 secondes
  1. Compose décrit une pile complète : services, réseaux, volumes, secrets, healthchecks.
  2. depends_on n'attend pas la disponibilité sans condition: service_healthy ; l'application doit retenter de toute façon.
  3. Override, profils et .env séparent dev et prod ; Compose pilote un seul hôte.
À la fin de ce chapitre, tu sauras
  • Décrire une pile complète dans un fichier Compose : services, réseaux, volumes, secrets
  • Gérer les dépendances et l'ordre de démarrage avec les healthchecks
  • Séparer développement et production avec profils et fichiers de surcharge

9.1 Anatomie d'un fichier ComposePar cœur

# compose.yaml  (le nom docker-compose.yml fonctionne aussi ; la clé "version" est obsolète)
name: crisisshield

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: crisis
      POSTGRES_USER: crisis
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks: [backend]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U crisis -d crisis"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    build:
      context: ./backend
      dockerfile: Dockerfile
    image: crisisshield-api:${TAG:-dev}
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/crisis
      SPRING_DATASOURCE_USERNAME: crisis
      SPRING_DATASOURCE_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    depends_on:
      db:
        condition: service_healthy
    networks: [backend, frontend]
    user: "1000:1000"
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
    deploy:
      resources:
        limits: {memory: 512m, cpus: "1.0"}
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/actuator/health/readiness"]
      interval: 10s
      start_period: 30s
      retries: 5
    restart: unless-stopped

  web:
    build: ./frontend
    ports: ["8080:8080"]
    depends_on:
      api:
        condition: service_healthy
    networks: [frontend]
    restart: unless-stopped

networks:
  backend:
  frontend:

volumes:
  pgdata:

secrets:
  db_password:
    file: ./secrets/db_password.txt

Points clés : deux réseaux (la base n'est pas joignable depuis web), un seul port publié, secrets en fichier et non en variable (jamais visibles dans docker inspect), depends_on avec condition (sans condition, Compose attend seulement le démarrage, pas la disponibilité).

9.3 Variables, surcharges, profilsImportant

  • .env à côté du fichier : variables interpolées dans le YAML (${TAG:-dev}). À ne pas commiter ; commiter un .env.example.
  • Surcharge : compose.override.yaml est fusionné automatiquement (dev : bind mounts, ports de debug). En production : docker compose -f compose.yaml -f compose.prod.yaml up -d.
  • Profils : profiles: [tools] sur un service (pgAdmin, Mailhog) qu'on ne lance qu'avec --profile tools.
  • Extension : x-common: &common puis <<: *common pour factoriser logging, restart, etc.
# compose.override.yaml (développement)
services:
  api:
    build: {target: build}
    command: ./mvnw spring-boot:run
    volumes: ["./backend/src:/app/src"]
    ports: ["5005:5005"]
    environment:
      JAVA_TOOL_OPTIONS: -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005
    read_only: false

9.4 Ce que Compose ne fait pasBon à savoir

Compose pilote un seul hôte. Pas de haute disponibilité, pas de redémarrage sur un autre nœud, pas de rolling update natif, pas de secrets chiffrés au repos. C'est parfait pour le développement, la CI, et de petites productions à un serveur. Au-delà : Kubernetes (niveau 5). Le fichier Compose reste un excellent document de l'architecture.

Techno de nichePour sortir du lot — Podman et Quadlet

Podman exécute des conteneurs sans démon et sans root par défaut ; Quadlet décrit des conteneurs et des pods dans des fichiers .container/.pod que systemd transforme en services. C'est la façon Red Hat de servir des conteneurs sur des VM, sans Kubernetes ni Compose.

Pourquoi ça différencie : Très présent dans le secteur public et bancaire français (RHEL) ; rootless par défaut, c'est un argument sécurité immédiat.

À essayer en une heure : docker run --rm -it --privileged quay.io/podman/stable podman run --rm alpine echo ok, puis écrire le fichier crisisshield-api.container équivalent à ton service Compose.

En entretien — « depends_on suffit pour que l'API attende la base ? » Non : sans condition: service_healthy, Compose attend le lancement du conteneur, pas que PostgreSQL accepte des connexions. Et en production, l'application doit de toute façon retenter (résilience), car la base peut redémarrer à tout moment.

Registres, tagging et scan de vulnérabilités

En 30 secondes

  2. Scanner (Trivy), produire un SBOM, signer (Cosign) : contenu, inventaire, origine.

  • Publier et récupérer des images dans un registre privé ou public

  • Scanner une image, lire un rapport, produire un SBOM

10.1 RegistresBon à savoir

Un registre stocke images et manifestes selon la spécification OCI. Docker Hub (public, limites de pull), GitHub Container Registry (ghcr.io), GitLab Container Registry, AWS ECR, Harbor (auto-hébergé, avec scan et réplication), ou le registre officiel minimal registry:2.

docker run -d -p 5000:5000 --name registry -v regdata:/var/lib/registry registry:2
docker tag crisisshield-api:1.0.0 localhost:5000/crisisshield/api:1.0.0
docker push localhost:5000/crisisshield/api:1.0.0
curl -s localhost:5000/v2/_catalog ; curl -s localhost:5000/v2/crisisshield/api/tags/list
docker login ghcr.io -u USER --password-stdin < token.txt   # jamais le mot de passe en argument

Nom complet d'une image : registre/espace/nom:tag@sha256:digest. Sans registre → Docker Hub ; sans tag → latest.

10.2 Stratégie de tagsPar cœur

latest ne veut rien dire : il pointe sur la dernière image poussée, quelle qu'elle soit. En production, il empêche de savoir ce qui tourne et de revenir en arrière. Un tag est mutable ; un digest ne l'est pas.

TagExempleUsage
Version sémantique1.4.2, 1.4, 1Livraisons ; les tags courts glissent vers le dernier correctif
SHA du commitsha-3f9a2b1Traçabilité exacte, une image par commit
Branchemain, developEnvironnements d'intégration
Digest@sha256:ab12...Déploiement en production, pinning immuable

Pratique recommandée : la CI construit une fois, tague avec le SHA du commit, puis ajoute la version sémantique au moment de la release (retag sans reconstruction). Le déploiement référence le digest. Politique de rétention dans le registre pour ne pas exploser le stockage.

10.3 Scanner une imageImportant

Une image embarque un OS et des bibliothèques qui ont des CVE. Trivy (Aqua) est l'outil de référence, gratuit, utilisable dans la CI :

# Scan complet, vulnérabilités OS + dépendances applicatives (jar, npm...)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v trivy-cache:/root/.cache \
  aquasec/trivy image crisisshield-api:1.0.0

# Ne remonter que critique et haute, échouer si présentes (pour la CI)
... aquasec/trivy image --severity HIGH,CRITICAL --exit-code 1 --ignore-unfixed crisisshield-api:1.0.0

# Scanner le Dockerfile et la config (mauvaises pratiques)
docker run --rm -v "$PWD:/w" aquasec/trivy config /w

# Générer un SBOM (inventaire des composants)
... aquasec/trivy image --format cyclonedx --output sbom.json crisisshield-api:1.0.0

Lire un rapport : la sévérité CVSS, si un correctif existe (« fixed version »), et si le composant est réellement utilisé. Un --ignore-unfixed évite de bloquer sur des CVE sans correctif ; un fichier .trivyignore documente les acceptations de risque, avec justification et date.

SBOM (Software Bill of Materials) : la liste de tout ce que contient l'image, au format CycloneDX ou SPDX. Exigé par de plus en plus de clients et de réglementations (Cyber Resilience Act). Il permet, quand une nouvelle CVE sort (type Log4Shell), de savoir en quelques secondes quelles images sont concernées sans tout rescanner.

10.4 Signer et vérifierImportant

Un scan dit ce qu'il y a dans l'image ; une signature dit qui l'a produite et qu'elle n'a pas été modifiée. Cosign (projet Sigstore) signe le digest et stocke la signature dans le registre à côté de l'image.

docker run --rm -it -v "$PWD:/w" -w /w gcr.io/projectsigstore/cosign generate-key-pair
docker run --rm -it -v "$PWD:/w" -w /w -e COSIGN_PASSWORD gcr.io/projectsigstore/cosign \
  sign --key cosign.key localhost:5000/crisisshield/api@sha256:...
docker run --rm -v "$PWD:/w" -w /w gcr.io/projectsigstore/cosign \
  verify --key cosign.pub localhost:5000/crisisshield/api:1.0.0

En CI, on signe sans clé (keyless) avec l'identité OIDC du pipeline. Kubernetes peut refuser toute image non signée (Kyverno, niveau 7). C'est la base de la sécurité de la chaîne d'approvisionnement (SLSA).

Techno de nichePour sortir du lot — ORAS et Zot

ORAS pousse n'importe quel artefact (SBOM, chart, plan Terraform, modèle ML, fichier de politique) dans un registre OCI, avec tags, digests et signatures Cosign ; Zot est un registre OCI natif (CNCF) léger avec scan et synchronisation.

Pourquoi ça différencie : Un seul système de distribution pour tous les artefacts, signé et versionné : c'est ce que les plateformes matures font désormais.

À essayer en une heure : docker run --rm --network host ghcr.io/oras-project/oras:v1.2.0 push localhost:5000/crisisshield/sbom:1.0.0 sbom.json:application/json puis oras pull depuis un autre conteneur.

En entretien — « Comment tu garantis qu'une image en prod est celle que la CI a construite ? » Réponse : build unique dans la CI, tag par SHA de commit, scan Trivy bloquant, SBOM publié, signature Cosign, déploiement par digest, vérification de signature à l'admission. Cinq mots-clés qui te placent immédiatement sur le terrain DevSecOps.
Exercice 10.1

L'équipe déploie api:latest en production. Vendredi soir, un développeur pousse une image cassée avec ce tag. Que se passe-t-il au prochain redémarrage d'un conteneur, et comment l'éviter structurellement ?

Corrigé
Le redémarrage tire la nouvelle image cassée (selon la politique de pull). Éviter : tags immuables (SHA, version), déploiement par digest, droits de push sur les tags de release réservés à la CI, tags de production immuables dans le registre (ECR, Harbor le permettent).

Trivy remonte 40 CVE HIGH sur ton image eclipse-temurin:21-jre, dont 35 sans correctif. Que fais-tu ?

Corrigé
D'abord réduire la surface : passer sur la variante alpine ou distroless, reconstruire (les images de base sont mises à jour régulièrement). Puis --ignore-unfixed pour ne bloquer que sur l'actionnable, documenter les 5 restantes dans .trivyignore avec justification si non exploitables, et programmer un rebuild hebdomadaire pour récupérer les correctifs.

Révision du niveau 1

Réponds à voix haute, sans support, comme en entretien. En dessous de trois quarts de réponses solides, reprends les chapitres concernés avant de passer au niveau suivant.

  1. Hyperviseur de type 1 contre type 2, un exemple de chaque.
    Réponse attendue
    Type 1 (bare metal) : tourne directement sur le matériel — ESXi, KVM/Proxmox, Hyper-V. Type 2 (hébergé) : sur un OS — VirtualBox, VMware Workstation. Le cloud et les datacenters sont en type 1.
  2. Les trois mécanismes noyau qui font un conteneur.
    Réponse attendue
    Namespaces (isolation de ce que le processus voit : PID, réseau, montages, utilisateurs), cgroups (limites de CPU, mémoire, IO), et le système de fichiers en couches (overlayfs) ; plus les capabilities et seccomp pour restreindre.
  3. Pourquoi le noyau partagé est un enjeu de sécurité ; ce qu'apportent Firecracker et gVisor.
    Réponse attendue
    Tous les conteneurs partagent le noyau : une faille noyau ou une évasion touche l'hôte et les voisins. Firecracker : micro-VM légère (noyau dédié, démarrage en ~100 ms). gVisor : noyau en espace utilisateur qui filtre les appels système. Les deux isolent des charges non fiables.
  4. Ce que Docker Desktop fait sous Windows ; deux pièges de Git Bash.
    Réponse attendue
    Docker Desktop lance une VM Linux (WSL 2) où tourne le démon ; les conteneurs sont des processus Linux dans cette VM. Pièges Git Bash : conversion automatique des chemins (/app devient C:\…, d'où MSYS_NO_PATHCONV ou //app) et fins de ligne CRLF dans les scripts.
  5. VMware, Proxmox, Nutanix : hyperviseur, plan de contrôle, stockage, HA, sauvegarde, IaC, quand ; les commandes qm/pct/vzdump et acli/ncc ; le quorum.
    Réponse attendue
    VMware : hyperviseur ESXi, vCenter, vSAN, HA/DRS, Veeam, provider Terraform. Proxmox : KVM/LXC, cluster corosync, Ceph ou ZFS, HA manager, PBS, provider bpg ; qm (VM), pct (LXC), vzdump (sauvegarde). Nutanix : AHV, Prism, stockage réparti, snapshots, provider nutanix ; acli, ncli, ncc. Quorum : majorité de votes pour éviter le split-brain, comme etcd. Quand : Proxmox pour le labo et les PME, VMware/Nutanix pour l'entreprise avec support.
  6. Homelab : les trois couches, les quatre phases et leurs portes de sortie, pourquoi la couche de confiance vit hors du cluster.
    Réponse attendue
    Couches : matériel/hyperviseur, plateforme (Kubernetes), applications. Phases : réseau et hyperviseur (porte : VM créée par Terraform), identité et secrets (IdP et Vault hors cluster), cluster (Talos + GitOps), applications (CrisisShield déployée). La confiance (IdP, CA, Vault) vit hors du cluster pour éviter la dépendance circulaire : on ne peut pas s'authentifier à un cluster qui héberge l'IdP tombé avec lui.
  7. Comment fonctionne le cache de build ; l'ordre des instructions qui en découle.
    Réponse attendue
    Chaque instruction produit une couche ; une couche est réutilisée si l'instruction et son contexte (fichiers copiés) n'ont pas changé, sinon tout ce qui suit est reconstruit. D'où l'ordre : base, dépendances (pom/lockfile), installation, puis le code source en dernier.
  8. Pourquoi un secret effacé dans une couche ultérieure est toujours dans l'image.
    Réponse attendue
    Chaque couche est un delta immuable ; supprimer dans une couche suivante ajoute un « whiteout », mais les octets restent dans la couche précédente et sont extractibles. Solution : ne jamais copier de secret, ou multi-étapes / secrets de build (--mount=type=secret).
  9. ENTRYPOINT forme exec contre forme shell : conséquence sur SIGTERM.
    Réponse attendue
    Forme exec ["java","-jar",…] : le processus est PID 1 et reçoit SIGTERM. Forme shell java -jar … : /bin/sh est PID 1, java est son enfant, le signal n'est pas transmis : arrêt en SIGKILL après le délai.
  10. Multi-étapes : ce qu'on gagne, avec des chiffres.
    Réponse attendue
    L'image finale ne contient que le runtime : ~200 Mo au lieu de ~450 Mo avec JDK + Maven, aucun outil de build (surface d'attaque réduite), cache de dépendances dans l'étape de build, secrets de build absents de l'image publiée.
  11. Volume nommé, bind mount, tmpfs : quand utiliser chacun.
    Réponse attendue
    Volume nommé : données persistantes gérées par Docker, performant sous Windows (bases, node_modules). Bind mount : un répertoire du poste, pour le code en développement. tmpfs : mémoire, jamais sur disque, pour les secrets ou les fichiers temporaires.
  12. Pourquoi deux conteneurs sur le bridge par défaut ne se résolvent pas par nom.
    Réponse attendue
    Le bridge par défaut n'a pas de serveur DNS interne (résolution par nom désactivée pour compatibilité) ; un réseau utilisateur (docker network create) active la résolution par nom de conteneur et de service.
  13. Six mesures de durcissement d'un conteneur, dans l'ordre où tu les appliques.
    Réponse attendue
    Utilisateur non root ; image minimale épinglée ; --read-only avec tmpfs ; --cap-drop ALL ; no-new-privileges ; limites mémoire et pids. Puis seccomp/AppArmor et le scan d'image.
  14. Signification des codes 137 et 143.
    Réponse attendue
    137 = 128 + 9 : SIGKILL (OOM killer ou kill forcé). 143 = 128 + 15 : SIGTERM reçu et traité, arrêt propre.
  15. Ta méthode de débogage d'un conteneur qui ne démarre pas.
    Réponse attendue
    docker logs (message d'erreur), docker inspect (exit code, OOMKilled, config), lancer avec un shell à la place de l'entrypoint (docker run -it --entrypoint sh), vérifier montages et variables, docker events, puis netshoot dans le namespace réseau si c'est du réseau.
  16. Pourquoi depends_on seul ne suffit pas.
    Réponse attendue
    depends_on n'attend que le démarrage du conteneur, pas la disponibilité du service ; il faut condition: service_healthy avec un healthcheck. Et il n'agit qu'au démarrage : la reconnexion en cours de vie est le travail de l'application.
  17. Secret Compose contre variable d'environnement.
    Réponse attendue
    Un secret Compose est un fichier monté dans /run/secrets, absent de docker inspect, des logs et de l'environnement hérité par les sous-processus ; une variable d'environnement se lit dans inspect et fuit dans les dumps.
  18. Override, profils, .env : à quoi sert chacun.
    Réponse attendue
    compose.override.yaml : surcharges locales lues automatiquement (ports de debug). Profils : services optionnels (outils) activés à la demande. .env : valeurs de variables substituées dans le fichier Compose, à ne pas commiter si sensibles.
  19. Ce que Compose ne sait pas faire.
    Réponse attendue
    Pas d'orchestration multi-hôtes, pas de réparation automatique en cas de perte du nœud, pas de rolling update avec readiness, pas d'autoscaling, pas de secrets chiffrés, pas de politiques réseau fines. C'est la frontière avec Kubernetes.
  20. Pourquoi latest est interdit en production ; tag contre digest.
    Réponse attendue
    latest est mutable : deux déploiements peuvent exécuter deux images différentes et personne ne sait laquelle. Un tag est un alias qu'on peut réattribuer ; un digest identifie le contenu exact : on déploie par digest, on signe le digest.
  21. Ce qu'est un SBOM et ce qu'il permet lors d'une nouvelle CVE.
    Réponse attendue
    Un inventaire des composants (paquets, bibliothèques, versions) au format CycloneDX ou SPDX. À la sortie d'une CVE, on interroge les SBOM (Dependency-Track) pour savoir quels services sont touchés, sans rescanner ni reconstruire les images.
  22. Scan contre signature : ce que chacun garantit.
    Réponse attendue
    Le scan dit ce que l'image contient de vulnérable à un instant donné (et rien de plus). La signature dit qui a produit ce digest et qu'il n'a pas été modifié. Il faut les deux : une image signée peut être vulnérable, une image saine peut être remplacée.
