La CI n'est pas un outil, c'est une discipline : intégrer sur la branche principale au moins une fois par jour, et réparer immédiatement un build cassé (le pipeline rouge est la priorité de l'équipe).

11.2 Anatomie d'un pipelineImportant

commit ──► build ──► test ──► package ──► scan ──► deploy staging ──► tests e2e ──► deploy prod
           (compile)  (unit,    (image      (Trivy,   (automatique)    (smoke,       (manuel ou auto)
                       lint)     Docker)     SAST)                      contrat)
  • Étape (stage) : groupe de jobs qui s'exécutent en parallèle ; l'étape suivante attend que tous soient verts.
  • Job : une unité de travail dans un conteneur (image, script, variables).
  • Artefact : fichier produit par un job et transmis aux suivants (jar, rapport de tests, image). Il a une durée de vie.
  • Cache : accélère (dépendances Maven, npm) mais n'est pas garanti ; le pipeline doit fonctionner sans.
  • Runner / agent : la machine qui exécute les jobs. Partagé ou dédié, souvent lui-même conteneurisé.

Construire une fois, déployer partout : l'image construite au job package est celle qui va en staging puis en production, identifiée par digest. Reconstruire pour chaque environnement, c'est déployer autre chose que ce qu'on a testé.

11.3 Un pipeline rapideBon à savoir

Un pipeline lent tue la CI : les développeurs cessent d'attendre le résultat. Objectif : moins de 10 minutes jusqu'au feedback principal. Leviers :

  1. Paralléliser (lint, tests unitaires, scan en même temps).
  2. Cacher les dépendances et les couches Docker (--cache-from, BuildKit).
  3. Découper les tests : rapides d'abord, lents (intégration, e2e) après ou la nuit.
  4. Ne déclencher que ce qui a changé (rules: changes: dans un monorepo).
  5. Runners dimensionnés, images de job petites.
  6. fail fast : interrompre le pipeline dès qu'un job critique échoue.

11.4 Secrets et variables dans la CIImportant

Les identifiants (registre, cloud, base) sont stockés comme variables protégées et masquées de la plateforme, jamais dans le dépôt. Principe du moindre privilège : un token par usage, avec portée minimale et expiration. Encore mieux : plus de secrets statiques du tout, le pipeline s'authentifie par OIDC auprès du cloud (AWS AssumeRoleWithWebIdentity) avec un jeton de courte durée.

Techno de nichePour sortir du lot — Dagger

Des pipelines écrits en code (Go, Python, TypeScript, Java via l'API) et exécutés dans des conteneurs BuildKit : strictement identiques en local et en CI, avec cache intelligent et composition de modules. Le YAML de GitLab ou GitHub ne fait plus qu'appeler dagger call.

Pourquoi ça différencie : Il met fin au « ça marche dans la CI mais pas sur mon poste » et à la duplication GitLab/GitHub/Jenkins ; encore peu maîtrisé en France.

À essayer en une heure : Installer le CLI dans un conteneur avec accès au socket Docker, dagger init --sdk=python, puis dagger call build --source=. pour reconstruire l'image CrisisShield.

En entretien — « Livraison continue ou déploiement continu chez vous ? » Sache expliquer la différence et ce qui manque pour passer de l'une à l'autre (couverture de tests, observabilité, feature flags, rollback automatique). Et cite « build once, deploy everywhere » avec le digest : c'est le détail qui montre que tu as vécu une prod.
Exercice 11.1

Un pipeline dure 45 minutes : compile 3 min, tests unitaires 8 min, tests d'intégration 25 min, build image 5 min, scan 4 min, tout en séquence. Propose une réorganisation et estime la nouvelle durée jusqu'au premier feedback utile et jusqu'à l'image scannée.

Corrigé
Étape 1 : compile (3). Étape 2 en parallèle : tests unitaires (8), build image (5) puis scan (4) enchaînés (9). Étape 3 : tests d'intégration sur l'image (25), ou déplacés en pipeline nocturne / déclenché seulement sur merge vers main. Premier feedback : 11 min ; image scannée : 12 min ; pipeline complet 37 min, ou 12 min si l'intégration est sortie du chemin critique.
Exercice 11.2

Pourquoi un cache ne doit-il jamais être nécessaire au succès d'un pipeline, alors qu'un artefact peut l'être ?

Corrigé
Le cache est opportuniste : il peut être absent (nouveau runner, expiration, clé changée) ; le job doit alors simplement être plus lent. L'artefact est un produit explicite d'un job précédent, garanti par la plateforme dans le même pipeline.

12.1 GitLab CIPar cœur

# .gitlab-ci.yml
stages: [build, test, package, deploy]

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=.m2/repository"
  IMAGE: $CI_REGISTRY_IMAGE/api
  DOCKER_TLS_CERTDIR: ""

default:
  image: eclipse-temurin:21-jdk
  cache:
    key: {files: [pom.xml]}
    paths: [.m2/repository]

build:
  stage: build
  script: ./mvnw -q compile
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG

unit-tests:
  stage: test
  script: ./mvnw -q test
  artifacts:
    when: always
    reports:
      junit: target/surefire-reports/TEST-*.xml
    paths: [target/site/jacoco]
    expire_in: 1 week
  coverage: '/Total.*?([0-9]{1,3})%/'

lint:
  stage: test
  image: koalaman/shellcheck-alpine
  script: shellcheck scripts/*.sh
  rules:
    - changes: [scripts/**]

package:
  stage: package
  image: docker:27
  services: [docker:27-dind]
  needs: [unit-tests]
  before_script: echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
  script:
    - docker build --cache-from "$IMAGE:latest-cache" -t "$IMAGE:sha-$CI_COMMIT_SHORT_SHA" .
    - docker push "$IMAGE:sha-$CI_COMMIT_SHORT_SHA"
    - docker tag "$IMAGE:sha-$CI_COMMIT_SHORT_SHA" "$IMAGE:latest-cache" && docker push "$IMAGE:latest-cache"

scan:
  stage: package
  image: aquasec/trivy
  needs: [package]
  script: trivy image --severity HIGH,CRITICAL --exit-code 1 --ignore-unfixed "$IMAGE:sha-$CI_COMMIT_SHORT_SHA"
  allow_failure: false

deploy-staging:
  stage: deploy
  image: alpine:3.20
  needs: [scan]
  environment:
    name: staging
    url: https://staging.crisisshield.example
  script: ./scripts/deploy.sh staging "$IMAGE:sha-$CI_COMMIT_SHORT_SHA"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

deploy-prod:
  stage: deploy
  image: alpine:3.20
  needs: [deploy-staging]
  environment:
    name: production
    url: https://crisisshield.example
  script: ./scripts/deploy.sh prod "$IMAGE:sha-$CI_COMMIT_SHORT_SHA"
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
      when: manual

À retenir :

  • rules remplace only/except. Une règle sans when vaut on_success ; aucune règle vérifiée = job absent.
  • needs crée un graphe (DAG) : le job démarre dès que ses dépendances sont vertes, sans attendre toute l'étape.
  • artifacts:reports:junit affiche les tests dans la merge request. coverage extrait le pourcentage par regex.
  • environment donne l'historique des déploiements, le bouton de rollback et les variables scopées par environnement.
  • when: manual = livraison continue ; retirer la ligne = déploiement continu.
  • Variables prédéfinies : CI_COMMIT_SHA, CI_COMMIT_TAG, CI_PIPELINE_SOURCE, CI_REGISTRY_*, CI_JOB_TOKEN.
  • Factorisation : include: (fichiers locaux, autres projets, templates GitLab), extends:, ancres YAML, et !reference. Les composants CI (catalogue) sont la version moderne.

Construire des images : docker:dind est le plus simple mais privilégié. Alternatives sans démon : Kaniko (gcr.io/kaniko-project/executor) ou BuildKit rootless.

12.2 GitHub ActionsImportant

# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]
    tags: ['v*']

permissions:
  contents: read
  packages: write
  id-token: write        # OIDC pour signer / assumer un rôle cloud

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: {distribution: temurin, java-version: '21', cache: maven}
      - run: ./mvnw -q verify
      - uses: actions/upload-artifact@v4
        if: always()
        with: {name: reports, path: target/surefire-reports}

  package:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with: {registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }}}
      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ghcr.io/${{ github.repository }}/api
          tags: |
            type=sha,prefix=sha-
            type=semver,pattern={{version}}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
      - uses: aquasecurity/trivy-action@0.28.0
        with: {image-ref: ghcr.io/${{ github.repository }}/api:sha-${{ github.sha }}, severity: 'HIGH,CRITICAL', exit-code: '1', ignore-unfixed: true}

  deploy-prod:
    needs: package
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment: production        # les approbateurs sont configurés dans le dépôt
    steps:
      - run: ./scripts/deploy.sh prod ghcr.io/${{ github.repository }}/api:${{ github.ref_name }}

Correspondances : stage/job GitLab → job GitHub (parallèles par défaut, needs pour ordonner) ; rules → on: et if: ; include → actions réutilisables (uses:) et reusable workflows (workflow_call) ; environment existe dans les deux ; runners → runs-on, self-hosted possibles. Épingler les actions par SHA de commit plutôt que par tag pour se protéger d'une action compromise (incident tj-actions, 2025). Réduire permissions au minimum.

Tester en local : docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$PWD:/w" -w /w catthehacker/ubuntu:act-latest avec l'outil act, ou plus simplement exécuter chaque run: dans le conteneur correspondant.

12.3 JenkinsBon à savoir

Le vétéran (2011), encore massivement présent dans les grands comptes. Serveur Java, plugins (des milliers, c'est sa force et sa faiblesse), agents. Le pipeline se décrit dans un Jenkinsfile en Groovy :

pipeline {
  agent { docker { image 'eclipse-temurin:21-jdk' } }
  options { timeout(time: 30, unit: 'MINUTES') }
  environment { IMAGE = "registry.example/crisisshield/api" }
  stages {
    stage('Build') { steps { sh './mvnw -q compile' } }
    stage('Test') {
      steps { sh './mvnw -q test' }
      post { always { junit 'target/surefire-reports/*.xml' } }
    }
    stage('Package') {
      when { branch 'main' }
      agent { label 'docker' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'registry', usernameVariable: 'U', passwordVariable: 'P')]) {
          sh 'echo "$P" | docker login -u "$U" --password-stdin registry.example'
          sh "docker build -t $IMAGE:sha-${GIT_COMMIT.take(7)} . && docker push $IMAGE:sha-${GIT_COMMIT.take(7)}"
        }
      }
    }
    stage('Deploy prod') {
      when { tag pattern: 'v\\d+\\.\\d+\\.\\d+', comparator: 'REGEXP' }
      input { message 'Déployer en production ?' }
      steps { sh "./scripts/deploy.sh prod $IMAGE:${TAG_NAME}" }
    }
  }
  post { failure { mail to: 'equipe@example', subject: "Échec ${env.JOB_NAME}" } }
}

Ce qu'on te demandera en mission : reprendre des Jenkinsfiles existants, gérer les agents (souvent des VM vieillissantes), migrer vers GitLab CI ou GitHub Actions. Bibliothèques partagées (@Library) pour factoriser. Configuration as Code (plugin JCasC) pour reconstruire un Jenkins sans clic. Faiblesses classiques : plugins non mis à jour, credentials globaux, agents avec docker.sock.

Techno de nichePour sortir du lot — Tekton

CI/CD natif Kubernetes : Tasks, Pipelines et PipelineRuns sont des CRD exécutées en Pods ; c'est le moteur d'OpenShift Pipelines, et Tekton Chains signe automatiquement chaque artefact produit (provenance SLSA).

Pourquoi ça différencie : OpenShift est omniprésent dans les grands comptes français ; connaître Tekton te rend opérationnel le premier jour sur ces plateformes.

À essayer en une heure : kubectl apply -f https://storage.googleapis.com/tekton-releases/pipeline/latest/release.yaml sur kind, puis une Task qui construit l'image CrisisShield avec Kaniko.

En entretien — « GitLab CI ou GitHub Actions ? » Les deux font le même travail. Différences réelles : GitLab est une plateforme intégrée (registre, environnements, SAST inclus, auto-hébergeable) très répandue en France dans le public et la banque ; GitHub Actions a l'écosystème d'actions le plus riche et le meilleur OIDC. Jenkins : tu sais le reprendre, tu sais expliquer pourquoi on en sort.
Exercice 12.1

Dans le pipeline GitLab ci-dessus, le job lint n'apparaît jamais dans les pipelines de merge request alors que scripts/ a changé. Pourquoi ?

Corrigé
Le job n'a qu'une règle changes:, sans if: sur la source du pipeline, et le projet n'a pas de workflow:rules qui crée des pipelines de merge request : GitLab ne lance alors que des pipelines de branche, où changes se compare au commit précédent (souvent vide après un rebase ou un push forcé). Correction : un bloc workflow:rules qui autorise les pipelines de merge request, et sur le job une règle qui combine if: $CI_PIPELINE_SOURCE == "merge_request_event" et changes: [scripts/**] ; dans un pipeline de MR, la comparaison se fait avec la branche cible, ce qui est fiable.
Exercice 12.2

Transpose le job scan GitLab en étape GitHub Actions sans utiliser l'action Trivy, uniquement avec docker run.

Corrigé
- run: |
    docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
      aquasec/trivy image --severity HIGH,CRITICAL --exit-code 1 --ignore-unfixed \
      ghcr.io/${{ github.repository }}/api:sha-${{ github.sha }}
Exercice 12.3

Pourquoi épingler une action GitHub par SHA plutôt que par tag @v4 ?

Corrigé
Un tag est mutable : le mainteneur (ou un attaquant ayant compromis le dépôt de l'action) peut le déplacer vers un commit malveillant, qui s'exécutera avec les secrets de tous les pipelines qui l'utilisent. Le SHA est immuable. Dependabot peut mettre à jour les SHA.

13.2 Tests d'intégration avec TestcontainersImportant

Testcontainers lance de vrais conteneurs (PostgreSQL, Kafka, Redis) pendant les tests, puis les détruit. Fini les H2 qui ne se comportent pas comme PostgreSQL.

@SpringBootTest
@Testcontainers
class IncidentRepositoryIT {

    @Container
    @ServiceConnection   // Spring Boot 3.1+ : configure la datasource automatiquement
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired IncidentRepository repo;

    @Test
    void savesAndFindsByStatus() {
        repo.save(new Incident("Inondation", Status.OPEN));
        assertThat(repo.findByStatus(Status.OPEN)).hasSize(1);
    }
}

Dans la CI, le job a besoin d'accéder à un démon Docker : dind, ou socket monté (voir chapitre 12). Les migrations Flyway tournent au démarrage du test : le schéma est testé aussi.

13.3 SonarQube et le quality gateBon à savoir

SonarQube analyse le code (bugs, vulnérabilités, code smells, duplication, couverture) et applique un quality gate : un ensemble de seuils dont l'échec fait échouer le pipeline. Le gate par défaut « Sonar way » porte sur le nouveau code : couverture ≥ 80 %, duplication < 3 %, zéro nouveau bug ou vulnérabilité. C'est la bonne approche : on n'exige pas de nettoyer le passé, on empêche de l'aggraver.

services:

  script: /usr/share/dependency-check/bin/dependency-check.sh --scan . --format JSON --failOnCVSS 7

zap:
  stage: deploy
  needs: [deploy-staging]
  image: ghcr.io/zaproxy/zaproxy:stable
  script: zap-baseline.py -t https://staging.crisisshield.example -r zap.html
  artifacts: {paths: [zap.html]}
  allow_failure: true

Gérer le bruit : commencer non bloquant, trier, définir les seuils, puis rendre bloquant. Un pipeline qui échoue pour 200 alertes inexploitables est désactivé en une semaine.

Techno de nichePour sortir du lot — PIT (pitest) : mutation testing

L'outil modifie ton code Java (inverse une condition, supprime un appel) et vérifie que les tests échouent ; s'ils passent encore, le mutant « survit » : la couverture était là, la vérification non.

Pourquoi ça différencie : Distinguer couverture et efficacité des tests est une réponse d'expert ; un score de mutation dans le quality gate est très rare.

À essayer en une heure : ./mvnw org.pitest:pitest-maven:mutationCoverage dans le conteneur Maven du pipeline, rapport HTML en artefact, seuil sur le score de mutation.

En entretien — « Comment tu mets en place la qualité dans une équipe qui n'a pas de tests ? » Réponse : quality gate sur le nouveau code seulement, tests d'intégration réels avec Testcontainers plutôt que des mocks fragiles, analyses de sécurité d'abord en mode observation puis bloquantes, et la règle des tests flaky. Ta double casquette Tech Lead + DevSecOps est exactement ce que cette question mesure.

Chapitre 14Confirmé

Dépendances et versioning

À la fin de ce chapitre, tu sauras
  • Verrouiller les dépendances pour des builds reproductibles
  • Automatiser les mises à jour sans casser
  • Générer version, changelog et release à partir des commits
  • Héberger ses propres artefacts et images
En 30 secondes
  1. Reproductibilité = lockfiles partout (Maven, npm, pip, Docker par digest, Terraform).
  2. Renovate ouvre les MR de mise à jour ; auto-merge des correctifs, majeures à la main.
  3. semantic-release calcule version et changelog à partir des commits ; Nexus proxifie et gouverne.

14.1 ReproductibilitéImportant

Un build est reproductible quand deux exécutions à partir du même commit donnent le même résultat. Ennemis : plages de versions (^1.2.0), latest, dépendances transitives non fixées, dépôts distants qui changent.

  • Maven : versions exactes, dependencyManagement (BOM), plugin enforcer pour interdire les plages, et ./mvnw (wrapper) pour fixer la version de Maven.
  • npm : package-lock.json commité, npm ci en CI (jamais npm install).
  • Python : requirements.txt figé avec hashes (pip-compile --generate-hashes), ou uv/poetry.lock.
  • Docker : base par digest, apt-get install pkg=version.
  • Terraform : .terraform.lock.hcl commité, required_version.

14.2 Mettre à jour sans peurImportant

Renovate (auto-hébergeable, très configurable) ou Dependabot (GitHub) ouvrent automatiquement une merge request par mise à jour, le pipeline la teste, on fusionne. Stratégie : regrouper les mineures, auto-fusionner les correctifs si le pipeline est vert, traiter les majeures à la main. Un SCA (chapitre 13) priorise celles qui corrigent des CVE.

// renovate.json
{
  "extends": ["config:recommended"],
  "packageRules": [
    {"matchUpdateTypes": ["patch"], "automerge": true},
    {"matchUpdateTypes": ["minor"], "groupName": "mineures"},
    {"matchManagers": ["dockerfile"], "pinDigests": true}
  ],
  "schedule": ["before 6am on monday"]
}
// exécution : docker run --rm -e RENOVATE_TOKEN -e RENOVATE_ENDPOINT renovate/renovate crisisshield/backend

14.3 Versioning et release automatisésImportant

Chapitre 5 : Conventional Commits + SemVer. Ici on ferme la boucle : semantic-release (ou release-please, ou le plugin Maven jgitver) lit les commits depuis le dernier tag, calcule la version (fix → correctif, feat → mineur, BREAKING → majeur), génère le changelog, crée le tag et la release, et déclenche le pipeline de tag qui publie l'image versionnée.

release:
  stage: deploy
  image: node:22-alpine
  rules: [{if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH}]
  script:
    - npm i -g semantic-release @semantic-release/gitlab @semantic-release/changelog @semantic-release/git
    - semantic-release
# .releaserc : branches main, plugins commit-analyzer, release-notes-generator, changelog, gitlab, git

Règles d'équipe : pas de version bricolée à la main, la version dans le code (pom.xml) est celle que l'outil injecte ; la merge request est squashée avec un titre Conventional Commit vérifié par un hook ou un job (commitlint).

14.4 Héberger ses artefactsBon à savoir

Un gestionnaire d'artefacts (Nexus, Artifactory, GitLab Package Registry) sert de proxy et de cache vers Maven Central, npm, PyPI ; héberge les bibliothèques internes ; et permet de bloquer les dépendances interdites (licences, CVE). Indispensable en entreprise sans accès Internet direct, et bon pour la vitesse des builds.

docker run -d --name nexus -p 8081:8081 -v nexus-data:/nexus-data sonatype/nexus3
# puis ~/.m2/settings.xml (dans le conteneur de build) : <mirror> vers http://nexus:8081/repository/maven-public/
Techno de nichePour sortir du lot — diffoscope et les builds reproductibles

diffoscope compare deux artefacts (jar, image, paquet) au bit près et explique chaque différence : horodatage, ordre des entrées, chemins absolus. Avec project.build.outputTimestamp côté Maven et SOURCE_DATE_EPOCH côté BuildKit, deux builds du même commit deviennent identiques.

Pourquoi ça différencie : La reproductibilité est l'ultime preuve d'intégrité de la chaîne (SLSA) ; savoir la mesurer et la corriger est une compétence de niche très valorisée.

À essayer en une heure : docker run --rm -v "$PWD:/w" -w /w registry.salsa.debian.org/reproducible-builds/diffoscope a.jar b.jar sur deux builds successifs du backend, puis corriger jusqu'à l'identité.

En entretien — « Comment tu gères les montées de version des dépendances ? » Renovate avec auto-merge des correctifs sur pipeline vert, regroupement des mineures, majeures manuelles, SCA pour prioriser la sécurité, et lockfiles partout pour que « ça marchait hier » ait un sens. Si tu ajoutes « proxy Nexus pour la conformité et les licences », tu parles le langage des grands comptes.

Chapitre 15Senior

Stratégies de déploiement

À la fin de ce chapitre, tu sauras
  • Choisir entre recreate, rolling, blue/green, canary selon le risque et le coût
  • Séparer déploiement et activation avec les feature flags
  • Concevoir un retour arrière en moins de deux minutes
  • Gérer la base de données dans un déploiement sans interruption
En 30 secondes
  1. Recreate, rolling, blue/green, canary : interruption, coût, rollback, quand.
  2. Rolling et canary font coexister deux versions : le schéma et les API doivent être compatibles N-1.
  3. Feature flags : déployer n'est pas activer ; rollback par digest en une commande, sans build.

15.1 Les stratégiesPar cœur

StratégiePrincipeInterruptionCoûtRollbackQuand
RecreateArrêter l'ancienne, démarrer la nouvelleOuiNulRedéployer l'ancienneEnvironnements de dev, applis qui ne supportent pas deux versions

Rolling et canary imposent une contrainte forte : deux versions du code tournent en même temps, sur le même schéma de base, devant les mêmes clients. Cela conditionne les migrations (15.4) et la compatibilité des API (versionner, ne jamais retirer un champ dans la même release qu'on l'introduit).

15.2 Blue/green avec un reverse proxyBon à savoir

# nginx : upstream pointant sur la couleur active
upstream app { server app-blue:8080; }        # ← devient app-green:8080 à la bascule
server { listen 443 ssl; location / { proxy_pass http://app; } }

# scripts/switch.sh
#!/usr/bin/env bash
set -euo pipefail
target="$1"   # blue | green
docker compose up -d "app-$target"
until curl -sf "http://localhost:$( [[ $target == blue ]] && echo 8081 || echo 8082 )/actuator/health/readiness"; do sleep 2; done
sed -i "s/app-\(blue\|green\)/app-$target/" nginx/upstream.conf
docker compose exec proxy nginx -s reload
echo "Trafic sur $target"

Avec Traefik, la bascule est un changement de label ; avec un ALB AWS, un changement de target group ; avec Kubernetes, un changement de sélecteur de Service. Le principe reste identique : la nouvelle version est prête et testée avant de recevoir du trafic.

15.3 Feature flags : déployer n'est pas activerImportant

Le code de la fonctionnalité est en production, désactivé. On l'active pour les employés, puis 5 % des utilisateurs, puis tous, sans redéploiement. Si problème, on désactive en une seconde. C'est ce qui rend le trunk-based development possible : la fonctionnalité inachevée est fusionnée, cachée derrière un flag.

// Spring Boot avec OpenFeature + flagd, ou Unleash, ou une simple table
if (features.isEnabled("nouvelle-carte-incidents", user)) {
    return newMapService.render(zone);
}
return legacyMapService.render(zone);

Discipline : chaque flag a un propriétaire et une date de suppression. Les flags oubliés sont de la dette. Types : release (temporaire), ops (kill switch permanent, ex. désactiver l'export PDF en cas de charge), expérimentation, permission.

15.4 La base de donnéesPar cœur

Le code se déploie et se retire en secondes ; un schéma, non. Règles :

  1. Migrations versionnées (Flyway) exécutées avant le nouveau code, jamais dans le même déploiement qu'une suppression.
  2. Chaque migration est compatible avec la version N-1 du code (expand/contract, chapitre 6).
  3. Pas de migration longue bloquante en heures de pointe : CREATE INDEX CONCURRENTLY, copies par lots.
  4. Rollback = déployer l'ancien code, pas annuler la migration. Les migrations « down » sont rarement sûres.
  5. Migration de données massive : job séparé, reprise possible, mesuré.

15.5 Rollback et santé du déploiementImportant

Un déploiement n'est terminé que lorsque les vérifications post-déploiement passent : readiness, smoke tests, puis quelques minutes de métriques (taux d'erreur, latence p95) comparées à la version précédente. Automatiser le retour arrière si les seuils sont dépassés (Argo Rollouts, Flagger, ou un simple script qui surveille Prometheus, niveau 6). Toujours garder l'image précédente disponible par digest ; le rollback ne doit jamais nécessiter un build.

Techno de nichePour sortir du lot — Flipt

Feature flags open source, déclaratifs : les flags vivent dans des fichiers YAML du dépôt (mode GitOps), avec segmentation, rollouts pondérés, et un fournisseur OpenFeature pour Java et JavaScript.

Pourquoi ça différencie : Des flags versionnés et revus comme du code, sans SaaS, c'est le choix des plateformes souveraines.

À essayer en une heure : docker run --rm -p 8080:8080 docker.flipt.io/flipt/flipt, puis le provider OpenFeature Flipt dans CrisisShield et le fichier features.yaml dans le dépôt de config.

En entretien — « Comment tu déploies sans interruption ? » Choisis une stratégie et déroule tout : image immuable prête, migration expand compatible, bascule blue/green ou rolling avec readiness, smoke, observation des métriques, rollback par digest en une commande, contract retiré à la release suivante. Mentionne les feature flags pour découpler déploiement et activation.
