Chapitre 20Confirmé

Concepts du cloud

En 30 secondes
  1. Choisir le niveau de service le plus haut qui satisfait les contraintes ; multi-AZ est le minimum.
  2. Responsabilité partagée : la quasi-totalité des fuites vient du côté client (bucket, clé, security group).
  3. Compte root avec MFA puis jamais utilisé ; budgets et alertes avant la première ressource.
À la fin de ce chapitre, tu sauras
  • Distinguer IaaS, PaaS, SaaS, FaaS et choisir le bon niveau d'abstraction
  • Expliquer régions, zones de disponibilité, edge, et concevoir pour la panne
  • Appliquer le modèle de responsabilité partagée
  • Lire une facture cloud et les cinq piliers d'une architecture bien conçue

20.1 Les niveaux de servicePar cœur

ModèleTu gèresLe fournisseur gèreExemples
Sur siteTout, du bâtiment à l'applicationRienDatacenter interne
IaaSOS, runtime, application, donnéesMatériel, virtualisation, réseau physiqueEC2, Azure VM, Compute Engine
CaaSConteneurs, applicationOrchestrateur, nœuds (selon le mode)ECS Fargate, EKS, AKS, GKE, Cloud Run
PaaSApplication, donnéesRuntime, OS, mise à l'échelleElastic Beanstalk, App Service, App Engine, Heroku
FaaSLe code d'une fonctionTout le reste, facturé à l'exécutionLambda, Azure Functions, Cloud Functions
SaaSLa configuration et les donnéesToutGmail, Salesforce, GitLab.com

Plus on monte, moins on opère et moins on contrôle. Le bon niveau est le plus haut qui satisfait les contraintes (réglementaires, techniques, coût). Une équipe DevOps de deux personnes ne devrait pas gérer des nœuds Kubernetes si Fargate ou Cloud Run suffisent.

20.2 Géographie : concevoir pour la panneImportant

  • Région : un ensemble de datacenters dans une zone géographique (Paris eu-west-3, Irlande eu-west-1, Francfort eu-central-1). Choix par latence, réglementation (RGPD, données de santé HDS), coût et disponibilité des services.
  • Zone de disponibilité (AZ) : un ou plusieurs datacenters isolés (alimentation, réseau) dans la région, reliés à faible latence. Une région a au moins trois AZ. La règle : toute production s'étend sur au moins deux AZ.
  • Edge / points de présence : CDN (CloudFront), DNS (Route 53), protection DDoS, au plus près des utilisateurs.
  • Pannes réelles : une AZ tombe quelques fois par an quelque part ; une région entière, rarement mais ça arrive (us-east-1). Multi-AZ est le minimum ; multi-région est un choix coûteux réservé aux besoins de continuité forts.

Latence : intra-AZ < 1 ms, inter-AZ 1 à 2 ms (facturé), Paris–Irlande ≈ 20 ms, Paris–Virginie ≈ 80 ms. Une application bavarde entre AZ paie en latence et en transfert de données.

20.3 Responsabilité partagéePar cœur

Le fournisseur est responsable de la sécurité du cloud (datacenters, matériel, hyperviseur, services managés). Le client est responsable de la sécurité dans le cloud : identités et droits, configuration réseau, chiffrement des données, patchs des OS qu'il gère, code applicatif. La quasi-totalité des fuites cloud vient du côté client : bucket public, clé d'accès commitée, security group ouvert, rôle trop large.

20.4 Ce qui coûteBon à savoir

Calcul (à la seconde ou à la requête), stockage (par Go-mois, par classe), transfert de données (sortant vers Internet et inter-région, souvent la surprise de la facture), requêtes (S3, API), services managés (par heure d'instance de base, par Go de logs ingérés), adresses IP publiques, NAT Gateway (par heure et par Go). Entrant : gratuit. Le chapitre 23 détaille.

20.5 Well-Architected : les piliersBon à savoir

AWS, Azure et Google publient chacun un cadre d'architecture. Piliers communs : excellence opérationnelle, sécurité, fiabilité, efficacité des performances, optimisation des coûts, durabilité. C'est une grille de revue : pour chaque pilier, des questions (« comment détectez-vous les incidents ? », « comment gérez-vous les identités ? »). En mission, une revue Well-Architected est un livrable classique de consultant.

Techno de nichePour sortir du lot — Cloud Custodian

Des règles YAML évaluées sur les ressources cloud (AWS, Azure, GCP, Kubernetes) qui trouvent, notifient et corrigent : arrêter les instances non taguées, chiffrer les volumes, supprimer les adresses orphelines, planifiées en Lambda.

Pourquoi ça différencie : Gouvernance et FinOps en code, avec action : très recherché, et complémentaire d'AWS Config qui ne fait que détecter.

À essayer en une heure : docker run --rm -v "$PWD:/w" -w /w -e AWS_ENDPOINT_URL=http://localstack:4566 --network <réseau> cloudcustodian/c7n run -s out politique.yml avec une règle qui marque les buckets sans tag Owner.

En entretien — « Pourquoi le cloud plutôt qu'un datacenter ? » Éviter la réponse marketing. Dire : élasticité (payer l'usage, absorber les pics), vitesse (une base répliquée en 10 minutes), services managés qui remplacent des équipes, résilience géographique accessible. Puis les contreparties : coût à l'usage qui dérape sans FinOps, dépendance, compétences, et souveraineté des données (sujet sensible en France : SecNumCloud, S3NS, Bleu, OVHcloud).
Exercice 20.1

Une application interne, trafic stable, 200 utilisateurs, équipe de deux développeurs sans ops. Quel niveau de service et pourquoi pas les autres ?

Corrigé
PaaS ou CaaS serverless (App Runner / Cloud Run / App Service) : zéro nœud à gérer, mise à l'échelle automatique, HTTPS fourni. IaaS demanderait de patcher des VM ; Kubernetes est disproportionné ; FaaS mal adapté à une application web classique avec état de session et connexions base persistantes.
Exercice 20.2

Une fuite de données est due à une base RDS accessible publiquement avec un mot de passe faible. Qui est responsable au sens du modèle partagé, et quelles trois mesures auraient dû être en place ?

Corrigé
Le client : la configuration réseau et les identifiants sont de son côté. Mesures : sous-réseau privé sans accès public (publicly_accessible = false), security group n'autorisant que l'application, secret généré et tourné par Secrets Manager (ou authentification IAM). Bonus : détection par AWS Config / Security Hub de la règle « RDS public ».
Travail pratique 20 — Compte AWS prêt pour la suite

Ce TP est le seul qui exige un vrai compte. Coût : zéro si tu restes dans le Free Tier et que tu détruis tout.

  1. Crée un compte AWS. Active immédiatement le MFA sur le compte root, puis ne l'utilise plus jamais.
  2. Active AWS Organizations et crée un compte membre sandbox via Terraform (ressource aws_organizations_account) ; c'est là que tout se passera, isolé.
  3. Crée un budget de 5 € avec alerte e-mail à 50 % et 100 % (aws_budgets_budget). Active Cost Explorer.
  4. Configure l'accès par IAM Identity Center (SSO) avec un utilisateur et un permission set AdministratorAccess sur le sandbox, puis la CLI en conteneur : docker run --rm -it -v "$HOME/.aws:/root/.aws" amazon/aws-cli sso login --profile sandbox. Aucune clé d'accès permanente ne doit exister.
  5. Applique deux garde-fous par SCP sur le sandbox : interdire toute région autre que eu-west-3 et us-east-1 (nécessaire pour certains services globaux), et interdire la désactivation de CloudTrail.
  6. Écris scripts/nuke-check.sh qui liste tout ce qui coûte dans le sandbox (EC2, RDS, NAT, EIP, volumes, buckets) pour vérifier avant de fermer le poste. Regarde aussi aws-nuke (à manier avec précaution).

Livrable : infra/aws-bootstrap/ (organisation, budget, SCP), et tp20.md avec la capture du budget et de la connexion SSO.

Correction type : solution complète, étape par étape.

21.1 IAM : le cœur de toutPar cœur

Tout appel d'API AWS est authentifié (qui) et autorisé (quoi) par IAM. Entités : utilisateurs (à éviter : préférer Identity Center), groupes, rôles (identité temporaire assumée par un service, une instance, un pipeline, un humain via SSO), politiques (documents JSON qui autorisent ou refusent).

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "LireLesRapports",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::crisisshield-reports", "arn:aws:s3:::crisisshield-reports/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "true" } }
    },
    {
      "Sid": "SecretDeLaBase",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:eu-west-3:123456789012:secret:crisisshield/prod/db-*"
    }
  ]
}

Règles d'évaluation : refus explicite > autorisation explicite > refus implicite. Les politiques se cumulent : identité (attachée au rôle), ressource (bucket policy, trust policy d'un rôle), SCP (organisation), permission boundary, session. Une action n'est autorisée que si aucune couche ne refuse et qu'au moins une autorise.

  • Rôle pour EC2 (instance profile), pour ECS (task role ≠ execution role), pour Lambda : l'application obtient des identifiants temporaires via le service de métadonnées ; aucun secret à gérer. IMDSv2 obligatoire.
  • Pipeline CI : fédération OIDC. GitLab ou GitHub présente un jeton signé, AWS le vérifie et délivre des identifiants de 15 minutes à 1 heure. Plus aucune clé statique en CI.
  • Humains : Identity Center, MFA, sessions courtes. Les clés d'accès longue durée sont un incident en attente.
  • Moindre privilège : commencer par IAM Access Analyzer (génère une politique à partir de l'usage réel dans CloudTrail), et affiner. Refuser "Action": "*" et "Resource": "*" en revue de code.
  • Trust policy : qui peut assumer le rôle. C'est là que se cachent les erreurs graves ("Principal": "*").

21.2 VPC : le réseauPar cœur

VPC 10.20.0.0/16 (eu-west-3)
├── AZ a                    AZ b                    AZ c
│   public  10.20.0.0/24    10.20.1.0/24            10.20.2.0/24    ← ALB, NAT Gateway
│   private 10.20.10.0/24   10.20.11.0/24           10.20.12.0/24   ← ECS, EKS, EC2 applicatifs
│   data    10.20.20.0/24   10.20.21.0/24           10.20.22.0/24   ← RDS, ElastiCache
├── Internet Gateway (entrée/sortie des sous-réseaux publics)
├── NAT Gateway par AZ (sortie Internet des privés ; coûteux : ~35 €/mois + trafic)
├── VPC Endpoints : S3, ECR, Secrets Manager, CloudWatch Logs (gratuit ou moins cher que la NAT)
└── Route tables : public → IGW ; private → NAT ; data → aucune sortie Internet
  • Security group : pare-feu stateful attaché à une interface. Autoriser par référence à un autre security group (« le SG de la base accepte 5432 depuis le SG de l'application ») plutôt que par CIDR : les règles suivent les instances.
  • NACL : stateless, au niveau du sous-réseau, à laisser par défaut sauf besoin de refus explicite.
  • ALB (couche 7, HTTP, terminaison TLS avec ACM, routage par chemin et hôte, WAF), NLB (couche 4, très haut débit, IP fixe), API Gateway (APIs serverless, quotas, authentification).
  • Route 53 : DNS avec health checks, routage pondéré (canary), géographique, failover.
  • Connectivité : VPC peering (deux VPC), Transit Gateway (hub pour des dizaines de VPC et le site), Site-to-Site VPN, Direct Connect (fibre dédiée). PrivateLink pour exposer un service à un autre compte sans peering.
  • Flow Logs : journal des flux acceptés/refusés, indispensable pour déboguer « ça ne passe pas ».

21.4 StockageImportant

  • S3 : stockage objet, durabilité 11 neufs, illimité. Classes : Standard, Intelligent-Tiering, Standard-IA, Glacier (Instant, Flexible, Deep Archive). Règles de cycle de vie pour descendre de classe et expirer. Versioning, chiffrement par défaut (SSE-S3 ou SSE-KMS), Block Public Access au niveau compte, bucket policy, Object Lock (immutabilité, ransomware), réplication inter-région. Accès pré-signé pour les uploads depuis le navigateur. Hébergement statique derrière CloudFront pour le front React.
  • EBS : disque bloc d'une instance (gp3 par défaut, io2 pour les bases exigeantes), snapshots incrémentaux vers S3.
  • EFS : NFS partagé entre instances et conteneurs, élastique, plus cher.
  • ECR : registre d'images, scan intégré, politiques de cycle de vie, réplication.

21.5 Bases de données managéesImportant

  • RDS : PostgreSQL, MySQL, MariaDB, Oracle, SQL Server. Multi-AZ (réplica synchrone, bascule automatique en 60 à 120 s), réplicas de lecture, sauvegardes automatiques (rétention 1 à 35 jours, restauration à un instant précis), fenêtres de maintenance, Performance Insights. Authentification IAM possible. RDS Proxy pour mutualiser les connexions (Lambda, pics).
  • Aurora : PostgreSQL/MySQL compatibles, stockage distribué sur 3 AZ, jusqu'à 15 réplicas, bascule en secondes, Serverless v2 (capacité à la demande), Global Database (réplication inter-région < 1 s). Plus cher à l'instance, souvent moins cher à charge équivalente.
  • DynamoDB : clé-valeur/document serverless, latence de quelques ms à toute échelle, facturation à la requête ou provisionnée, TTL, streams, Global Tables. Modéliser par accès (single-table design).
  • ElastiCache (Redis/Valkey, Memcached), OpenSearch, MSK (Kafka managé), SQS/SNS/EventBridge pour la messagerie.

21.6 Lambda et le serverlessImportant

Une fonction, un déclencheur (HTTP via API Gateway ou Function URL, événement S3, message SQS, planification EventBridge, flux DynamoDB), une durée max de 15 min, une mémoire de 128 Mo à 10 Go (le CPU suit), facturation par ms. Concepts : cold start (initialisation ; Java est le plus lent, mitigé par SnapStart ou GraalVM), concurrence réservée/provisionnée, couches, image de conteneur jusqu'à 10 Go. Déploiement : SAM, CDK, Terraform, Serverless Framework. Java : Spring Cloud Function, Quarkus (excellent en Lambda natif).

resource "aws_lambda_function" "report" {
  function_name = "crisisshield-report"
  package_type  = "Image"
  image_uri     = "${aws_ecr_repository.report.repository_url}@${data.aws_ecr_image.report.image_digest}"
  role          = aws_iam_role.report.arn
  memory_size   = 1024
  timeout       = 60
  environment { variables = { BUCKET = aws_s3_bucket.reports.id } }
  tracing_config { mode = "Active" }
}
resource "aws_lambda_event_source_mapping" "queue" {
  event_source_arn = aws_sqs_queue.reports.arn
  function_name    = aws_lambda_function.report.arn
  batch_size       = 10
}

21.7 Observabilité et sécurité nativesImportant

  • CloudWatch : métriques (natives et custom), logs (groupes, rétention à définir sinon infinie et payante, Logs Insights), alarmes, dashboards, Container Insights. X-Ray : traces distribuées.
  • CloudTrail : tous les appels d'API, à activer sur l'organisation, envoyé dans un bucket verrouillé. C'est la base de toute investigation.
  • AWS Config : inventaire et conformité des ressources (règles : bucket public, chiffrement, MFA). Security Hub : agrégation, standards CIS / AWS Foundational. GuardDuty : détection de menaces (clés compromises, minage, appels suspects). Inspector : CVE sur EC2, ECR, Lambda. KMS : clés de chiffrement, avec rotation et politiques. Secrets Manager : secrets avec rotation automatique (RDS natif). WAF et Shield : protection applicative et DDoS. SSM Session Manager : shell sur une instance sans SSH ni port ouvert, tracé.

CloudFormation est l'IaC natif d'AWS ; le CDK le génère depuis TypeScript/Python/Java. En mission, tu croiseras les deux ; Terraform reste le plus demandé.

Techno de nichePour sortir du lot — AWS Nitro Enclaves

Une machine virtuelle isolée, sans réseau ni stockage persistant, à côté d'une instance EC2 : elle produit un document d'attestation signé, et KMS ne déchiffre une clé que si l'enclave est attestée. Traitement de secrets, signature, HSM logiciel, confidential computing.

Pourquoi ça différencie : Ton expérience PKI/HSM plus le confidential computing : un créneau où presque personne ne se positionne en France.

À essayer en une heure : Sur une instance compatible (par exemple m6i.xlarge, quelques centimes) avec nitro-cli, construire l'enclave d'exemple, lire l'attestation, et documenter la comparaison avec un HSM.

En entretien — « Conçois l'infrastructure AWS d'une application web avec base de données. » Déroule : VPC 3 AZ, sous-réseaux publics/privés/données, ALB avec ACM et WAF dans le public, ECS Fargate (ou EKS) dans le privé avec rôle de tâche, RDS PostgreSQL Multi-AZ dans données avec Secrets Manager et rotation, S3 + CloudFront pour le front, endpoints VPC pour éviter la NAT, CloudWatch avec rétention, CloudTrail et GuardDuty, tout en Terraform avec state S3, déploiement par pipeline OIDC. Puis les coûts : NAT, transfert, dimensionnement RDS. C'est la question la plus fréquente ; répète-la jusqu'à la dérouler en trois minutes.
Exercice 21.1

Une Lambda doit lire un objet dans le bucket crisisshield-reports. Elle échoue avec AccessDenied alors que sa politique d'identité autorise s3:GetObject sur arn:aws:s3:::crisisshield-reports. Pourquoi, et quelle autre cause possible ?

Corrigé
L'ARN d'un objet est arn:aws:s3:::crisisshield-reports/* ; le bucket seul ne couvre pas les objets. Autre cause : la bucket policy ou une SCP refuse explicitement, ou l'objet est chiffré avec une clé KMS sur laquelle le rôle n'a pas kms:Decrypt.
Exercice 21.2

Les tâches ECS dans les sous-réseaux privés n'arrivent pas à tirer leur image depuis ECR. Trois causes possibles dans l'ordre où tu les vérifies.

Corrigé
1) Pas de route vers Internet (NAT) ni d'endpoints VPC pour ECR (ecr.api, ecr.dkr) et S3 (les couches sont dans S3) ; 2) le security group des tâches bloque la sortie 443 ou le security group des endpoints n'accepte pas les tâches ; 3) le rôle d'exécution n'a pas ecr:GetAuthorizationToken et ecr:BatchGetImage. Flow Logs et l'événement d'échec de la tâche (message CannotPullContainerError) orientent.
Exercice 21.3

Un batch nocturne de 2 heures tourne sur une instance m6i.xlarge à la demande. Deux façons de diviser le coût par 5 ou plus.

Corrigé
Instance Spot (−70 à −90 %) avec reprise sur interruption (le batch doit être idempotent et reprendre), et arrêt de l'instance en dehors des 2 heures (ou lancement à la demande par EventBridge + arrêt à la fin). Graviton (m7g) pour −20 % supplémentaires.
Travail pratique 21 — CrisisShield sur AWS, en Terraform, de bout en bout

Deux modes : LocalStack pour tout développer et valider gratuitement (IAM, VPC, S3, ECR, Secrets Manager, Lambda, SQS sont bien émulés ; ECS et RDS le sont partiellement, en édition payante), puis sandbox AWS pour un déploiement réel de quelques heures. Coût estimé du déploiement réel avec NAT Gateway, ALB, RDS db.t4g.micro Multi-AZ, deux tâches Fargate : environ 0,25 €/heure ; détruis en fin de session.

  1. Réseau : module network du TP 16 étendu : 3 AZ, sous-réseaux publics/privés/données, IGW, une seule NAT (choix coût documenté), endpoints S3 (gateway), ECR, Secrets Manager, CloudWatch Logs. Flow Logs activés vers CloudWatch avec rétention 7 jours.
  2. Identités : rôle OIDC pour ton GitLab (trust policy limitée à ton projet et à la branche main), rôles d'exécution et de tâche ECS distincts, politique de tâche générée avec Access Analyzer après un premier tour trop large, puis resserrée.
  3. Données : RDS PostgreSQL 16 Multi-AZ, chiffré KMS, non public, mot de passe généré et stocké dans Secrets Manager avec rotation activée, security group n'acceptant que le SG de l'API. Sauvegardes 7 jours.
  4. Application : ECR avec scan à la poussée et cycle de vie (garder 10 images), cluster ECS, service Fargate de 2 tâches sur 2 AZ derrière un ALB HTTPS (certificat ACM sur un sous-domaine que tu possèdes, ou HTTP si aucun domaine), health check sur /actuator/health/readiness, déploiement rolling avec circuit breaker et rollback automatique. Logs dans CloudWatch, rétention 14 jours. Front React sur S3 privé derrière CloudFront avec Origin Access Control.
  5. Serverless : une Lambda (image de conteneur, Quarkus ou Python) déclenchée par SQS qui génère un rapport PDF d'incident dans le bucket reports ; l'API publie dans la file. Tracing X-Ray activé.
  6. Sécurité : CloudTrail organisation, GuardDuty, Security Hub avec le standard AWS Foundational, WAF sur l'ALB avec les règles managées de base. Note dans le compte rendu les 5 premiers findings de Security Hub et corrige-en 3.
  7. Pipeline : le pipeline du niveau 2 pousse dans ECR via OIDC, puis met à jour le service ECS avec la nouvelle image par digest (aws ecs update-service ou Terraform). Smoke test sur l'URL de l'ALB. Job manuel destroy.
  8. Coupe le service RDS primaire (reboot with failover) et mesure le temps d'indisponibilité vu par un curl en boucle.

Chapitre 23Senior

FinOps

En 30 secondes
  1. FinOps : informer (tags, attribution), optimiser (leviers dans l'ordre), opérer (revue mensuelle).
  2. Éteindre, redimensionner, changer d'architecture, puis seulement s'engager (Savings Plans).
  3. NAT, transfert de données, logs sans rétention, IPv4 publiques : les postes surprises.
À la fin de ce chapitre, tu sauras
  • Rendre les coûts visibles, attribuables et prévisibles
  • Appliquer les leviers d'optimisation dans le bon ordre
  • Mettre en place un processus FinOps léger dans une équipe

23.1 Le problèmeBon à savoir

Dans un datacenter, le coût est fixe et décidé une fois. Dans le cloud, chaque développeur avec des droits de création est un acheteur. Sans discipline, la facture croît de 20 à 30 % par an à usage constant : ressources oubliées, surdimensionnement, environnements de test allumés la nuit, logs sans rétention, transfert de données non anticipé. FinOps (FinOps Foundation) : rendre chaque équipe responsable de ses coûts avec les données pour décider. Trois phases : informer, optimiser, opérer.

23.2 Informer : voir et attribuerImportant

  • Tagging obligatoire : Project, Environment, Owner, CostCenter. Imposé par IaC (tags par défaut du provider) et par politique (SCP ou AWS Config qui refuse ou signale les ressources non taguées). Les tags activés pour la facturation apparaissent dans Cost Explorer.
  • Un compte par environnement et par équipe : l'attribution devient triviale.
  • Outils : Cost Explorer et Cost and Usage Report (AWS), Cost Management (Azure, GCP), Kubecost/OpenCost pour Kubernetes, Infracost dans les merge requests.
  • Budgets et alertes par compte et par projet ; détection d'anomalies (AWS Cost Anomaly Detection).
  • Unité de coût : coût par utilisateur, par transaction, par incident traité. C'est ce qui permet de dire si une hausse est saine (plus de clients) ou non.

23.3 Optimiser : les leviers, dans l'ordrePar cœur

  1. Éteindre : environnements de dev/test hors heures ouvrées (−65 % sur ces environnements), ressources orphelines (volumes EBS détachés, EIP non associées, snapshots anciens, load balancers sans cible, NAT inutilisées).
  2. Redimensionner : Compute Optimizer / recommandations, instances utilisées à 10 % de CPU, RDS surdimensionnées, gp2 → gp3, logs avec rétention.
  3. Changer d'architecture : Graviton/ARM, Spot pour ce qui tolère l'interruption, serverless pour les charges intermittentes, endpoints VPC au lieu de NAT, S3 Intelligent-Tiering et cycle de vie, cache pour réduire les requêtes.
  4. S'engager : Savings Plans et instances réservées sur la charge de base stable, seulement après les étapes précédentes (on ne s'engage pas sur du gaspillage). Couverture cible : 70 à 80 % de la base.
  5. Négocier : au-delà de quelques centaines de milliers d'euros par an, contrats d'entreprise (EDP) avec remise.

Ordre de grandeur des postes surprises : NAT Gateway (35 €/mois par AZ + 0,045 €/Go), transfert inter-AZ (0,01 €/Go dans chaque sens), sortie Internet (0,09 €/Go), CloudWatch Logs ingestion (0,50 €/Go), adresses IPv4 publiques (3,6 €/mois chacune depuis 2024), snapshots accumulés.

23.4 Opérer : le processusBon à savoir

Revue mensuelle de 30 minutes par équipe : top 10 des coûts, variation, anomalies, actions. Un rapport automatique posté dans le canal de l'équipe. Les recommandations sont converties en tickets avec un gain estimé. Les développeurs voient le coût de leur merge request (Infracost) avant de fusionner. Objectif : que le coût soit une métrique d'ingénierie comme la latence, pas un sujet réservé à la direction financière.

Techno de nichePour sortir du lot — Kepler et Cloud Carbon Footprint

Kepler (CNCF) mesure par eBPF la consommation énergétique de chaque Pod et l'exporte dans Prometheus ; Cloud Carbon Footprint estime les émissions CO2 par compte cloud. C'est le GreenOps.

Pourquoi ça différencie : Les DSI y sont désormais contraintes par la directive CSRD ; un consultant capable de l'outiller est rare et demandé.

À essayer en une heure : Helm kepler sur kind, dashboard Grafana « énergie par namespace », puis le lien avec OpenCost : coût et carbone par équipe côte à côte.

En entretien — « La facture AWS a augmenté de 40 % en six mois, que fais-tu ? » Méthode : Cost Explorer par service et par tag pour trouver le poste, vérifier si l'unité de coût a augmenté aussi (croissance saine ?), puis les leviers dans l'ordre : éteindre, redimensionner, architecture, engagement. Donne un exemple chiffré (NAT, logs). Termine par la mise en place du processus pour que ça ne se reproduise pas.

Chapitre 24Expert

Multi-cloud et hybride

En 30 secondes
  1. Multi-cloud subi, choisi par service, ou portable : le troisième est rarement justifié.
  2. La vraie dépendance est dans les données et les compétences ; formats ouverts et plan de sortie testé.
  3. Hybride : plan d'adressage sans chevauchement, DNS et identités fédérés, liaison dédiée si latence.
À la fin de ce chapitre, tu sauras
  • Distinguer multi-cloud subi, choisi et portable, et évaluer le coût réel de chacun
  • Concevoir une connectivité hybride entre un site et le cloud
  • Reconnaître la couche d'abstraction utile (Kubernetes, Terraform) et ses limites

24.1 Les trois multi-cloudsBon à savoir

  • Subi : par acquisitions, par équipes autonomes, par choix historiques. Le plus fréquent. L'enjeu est de gouverner (identités, sécurité, coûts) sans tout unifier.
  • Choisi par service : AWS pour la plateforme, GCP pour BigQuery, Azure pour Microsoft 365 et Entra ID. Raisonnable si les frontières sont nettes et le transfert de données limité (la sortie de données est facturée par chacun).
  • Portable (« la même application partout, pour ne pas dépendre ») : le plus coûteux et le moins souvent justifié. Il impose le plus petit dénominateur commun (pas de services managés spécifiques), double les compétences et les pipelines, et la « portabilité » n'est presque jamais exercée. Justifiable pour des exigences réglementaires de réversibilité (finance, DORA européen) ou de continuité extrême.

Ce qui est portable de fait : conteneurs, Kubernetes, Terraform (même outil, code différent par fournisseur), PostgreSQL, Kafka, l'observabilité OpenTelemetry. Ce qui ne l'est pas : IAM, réseau, services managés propriétaires (DynamoDB, Cosmos, BigQuery), les fonctions.

24.2 Hybride : site et cloudBon à savoir

Presque toutes les grandes entreprises sont hybrides : datacenter existant, mainframe, contraintes de latence ou de souveraineté, migration progressive.

  • Connectivité : VPN Site-to-Site (rapide à mettre en place, débit limité, sur Internet), liaison dédiée (Direct Connect, ExpressRoute, Cloud Interconnect : latence stable, débit élevé, semaines de mise en place), Transit Gateway comme hub. Plan d'adressage sans chevauchement, DNS hybride (résolveurs conditionnels : Route 53 Resolver).
  • Identité : fédération de l'annuaire (Entra ID, AD) vers le cloud ; une seule identité.
  • Extension du cloud sur site : AWS Outposts, Azure Arc / Azure Stack, Google Distributed Cloud : les API cloud sur du matériel chez toi. Kubernetes sur site (OpenShift, Rancher, Tanzu) piloté depuis le cloud.
  • Migration : les « 6 R » (rehost, replatform, refactor, repurchase, retire, retain), traitées au niveau 9.

24.3 Gouverner plusieurs cloudsBon à savoir

Une couche transverse minimale : identités fédérées (un fournisseur d'identité), IaC unique (Terraform), pipeline unique, observabilité unifiée (OpenTelemetry vers un backend commun : Grafana, Datadog), posture de sécurité (CSPM multi-cloud : Wiz, Prisma, Defender for Cloud multi-cloud), FinOps consolidé (FOCUS, le format de facturation commun de la FinOps Foundation), et des politiques as code communes (OPA). Sans cela, multi-cloud = plusieurs silos.

Techno de nichePour sortir du lot — NetBird et Headscale

Réseaux maillés WireGuard zero trust auto-hébergés : chaque machine, conteneur ou poste rejoint le maillage par identité OIDC (Keycloak), avec listes de contrôle par groupe, traversée de NAT et DNS interne, sans VPN central ni port ouvert.

Pourquoi ça différencie : Relier site, clouds et postes en zero trust sans appliance : très différenciant face aux VPN classiques.

À essayer en une heure : Compose officiel de NetBird avec ton Keycloak comme IdP ; relie le conteneur « legacy » du TP 24 et une instance LocalStack au maillage et écris une ACL.

En entretien — « Faut-il être multi-cloud pour éviter la dépendance ? » Réponse d'expert : la dépendance réelle est dans les données et les compétences, pas dans les API. Le coût de la portabilité est certain, son bénéfice hypothétique. Préférer : bien choisir un fournisseur principal, garder les données dans des formats ouverts (PostgreSQL, Parquet, Kafka), documenter un plan de sortie, et n'utiliser un second cloud que pour un service qui le justifie. Mentionne la réglementation quand elle impose la réversibilité.

Révision du niveau 4

Réponds à voix haute, sans support, comme en entretien. En dessous de trois quarts de réponses solides, reprends les chapitres concernés avant de passer au niveau suivant.

  1. IaaS, CaaS, PaaS, FaaS, SaaS : ce que tu gères dans chacun, et comment tu choisis.
    Réponse attendue
    IaaS : tu gères OS et tout ce qu'il y a dessus (EC2). CaaS : tu gères les conteneurs, pas les hôtes (ECS/EKS managé). PaaS : tu livres du code, la plateforme fait le reste (App Runner, Beanstalk). FaaS : des fonctions par événement (Lambda). SaaS : tu utilises (RDS est un SaaS de base). Choix : plus on monte, moins on exploite et moins on contrôle ; on prend le plus haut niveau qui respecte les contraintes (langage, réseau, coût).
  2. Région, AZ, edge : pourquoi multi-AZ est le minimum et multi-région rarement justifié.
    Réponse attendue
    Une région est un ensemble d'AZ (datacenters distincts, latence < 2 ms) ; edge = points de présence CDN. Multi-AZ protège d'une panne de datacenter à faible coût (réseau local) ; multi-région double les coûts et pose le problème des données (réplication, cohérence) : justifié par une exigence réglementaire ou un RTO global.
  3. Responsabilité partagée : trois exemples de chaque côté.
    Réponse attendue
    Fournisseur : sécurité physique, hyperviseur, réseau de la région, correctifs des services managés. Client : configuration IAM, chiffrement et exposition des données (bucket public), correctifs de l'OS des EC2, code applicatif, secrets.
  4. Les postes de facture surprises.
    Réponse attendue
    NAT Gateway (par Go et par heure), trafic sortant inter-région et vers Internet, snapshots et volumes orphelins, adresses IP publiques, journaux CloudWatch sans rétention, instances de dev allumées la nuit, LoadBalancers oubliés, requêtes API à la seconde (S3, KMS).
  5. IAM : ordre d'évaluation des politiques ; identité contre ressource contre SCP.
    Réponse attendue
    Deny explicite gagne toujours ; sinon il faut un allow ; SCP (organisation) borne ce qu'un compte peut faire, même à l'admin ; politique de ressource (bucket) et politique d'identité (rôle) s'évaluent ensemble ; permission boundary borne une identité ; session policies en dernier.
  6. Pourquoi plus aucune clé d'accès statique, et comment (rôles, OIDC, Identity Center).
    Réponse attendue
    Une clé statique fuit (dépôt, log, poste) et ne expire pas. On la remplace par des rôles assumés (instance profile, rôle de tâche), par OIDC pour la CI (jeton échangé contre des identifiants de 15 min à 1 h), par Identity Center (SSO, sessions courtes) pour les humains.
  7. Dessine un VPC de production en trois AZ avec ses tables de routage.
    Réponse attendue
    Trois AZ, chacune avec un sous-réseau public (ALB, NAT), privé (applications), base (RDS). Tables de routage : public → IGW ; privé → NAT de sa zone (un par AZ en prod) + endpoints S3/ECR ; base → aucune route sortante. Aucune IP publique sur les instances.
  8. Security group contre NACL ; règles par référence de SG.
    Réponse attendue
    SG : stateful, par instance, allow seulement, référence possible (api accepte 8080 depuis le SG de l'ALB) : ajouter une instance ne change aucune règle. NACL : stateless, par sous-réseau, allow/deny ordonnés, pour bloquer une plage. SG pour tout le contrôle applicatif.
  9. NAT Gateway contre endpoints VPC : coût et sécurité.
    Réponse attendue
    Le NAT coûte à l'heure et au Go, et expose le trafic à Internet. Les endpoints (Gateway S3/DynamoDB gratuits, Interface pour ECR, Secrets Manager, CloudWatch) gardent le trafic dans le réseau AWS et réduisent la facture NAT, souvent le premier poste caché.
  10. EC2, ECS Fargate, EKS, Lambda, App Runner : critères de choix.
    Réponse attendue
    EC2 : contrôle total, exploitation à charge (OS). ECS Fargate : conteneurs sans nœuds, simple, verrouillé AWS. EKS : Kubernetes standard, portable, plus complexe. Lambda : événementiel, court, facturé à l'appel. App Runner : PaaS pour une API web. Critère : compétence de l'équipe, portabilité, profil de charge, coût à l'échelle.
  11. Spot, Savings Plans, Graviton : quand et combien.
    Réponse attendue
    Spot : jusqu'à −90 %, interruptible, pour les charges tolérantes (CI, batch, nœuds de calcul avec marge). Savings Plans : engagement 1–3 ans sur le socle stable, après optimisation, −30 à −50 %. Graviton (ARM) : −20 % à performance égale, presque tout est compatible (Java, conteneurs multi-arch).
  12. S3 : classes, cycle de vie, protection contre l'exposition et le ransomware.
    Réponse attendue
    Classes : Standard, Intelligent-Tiering, IA, Glacier (accès rare) ; cycle de vie pour migrer et expirer. Exposition : Block Public Access au niveau compte, politiques de bucket, chiffrement par défaut. Ransomware : versioning, Object Lock (WORM), réplication vers un compte isolé, MFA delete.
  13. RDS Multi-AZ contre réplica de lecture contre Aurora.
    Réponse attendue
    Multi-AZ : réplique synchrone en attente, bascule automatique (~1 min), zéro perte, pour la disponibilité. Réplica de lecture : copie asynchrone lisible, pour décharger les lectures. Aurora : stockage réparti sur 3 AZ, bascule en secondes, réplicas partageant le stockage, Global Database pour le multi-région.
  14. Lambda : limites, cold start, comment Java s'y comporte.
    Réponse attendue
    15 min max, 10 Go de mémoire, taille de paquet limitée, pas de connexions persistantes faciles (pool). Cold start : initialisation à la première invocation ; Java est le plus lent (secondes) → SnapStart, natif (Quarkus/GraalVM), ou provisioned concurrency.
  15. CloudTrail, Config, GuardDuty, Security Hub, Inspector : rôle de chacun.
    Réponse attendue
    CloudTrail : journal de tous les appels API (qui a fait quoi). Config : inventaire et conformité des ressources (règles). GuardDuty : détection de menaces sur les journaux et le réseau. Security Hub : agrégation des findings et référentiels (CIS). Inspector : vulnérabilités des instances et images.
  16. Traduire une architecture AWS en Azure et GCP.
    Réponse attendue
    VPC ↔ VNet ↔ VPC ; ALB ↔ Application Gateway ↔ Cloud Load Balancing ; EKS ↔ AKS ↔ GKE ; RDS ↔ Flexible Server ↔ Cloud SQL ; S3 ↔ Blob ↔ Cloud Storage ; IAM rôle ↔ identité managée ↔ compte de service ; Secrets Manager ↔ Key Vault ↔ Secret Manager ; CloudTrail ↔ Activity Log ↔ Cloud Audit Logs.
  17. Ce qui est structurellement différent chez Azure et chez GCP.
    Réponse attendue
    Azure : identité par Entra ID intégrée à l'entreprise, groupes de ressources, abonnements, réseau plus simple mais moins isolant par défaut. GCP : projets comme unité, VPC global (multi-région natif), IAM par ressource hiérarchique, GKE le plus abouti, facturation à la seconde.
  18. Cloud de confiance, SecNumCloud, Bleu, S3NS : de quoi il s'agit.
    Réponse attendue
    Cloud de confiance : offre qualifiée pour héberger des données sensibles à l'abri des lois extraterritoriales. SecNumCloud : qualification ANSSI (sécurité et immunité juridique). Bleu (Orange/Capgemini, techno Microsoft) et S3NS (Thales, techno Google) : clouds sous contrôle français avec technologies américaines, en cours de qualification.
  19. FinOps : informer, optimiser, opérer ; les leviers dans l'ordre.
    Réponse attendue
    Informer (tags, allocation, coût par unité), optimiser (éteindre, redimensionner, architecture, engagements — dans cet ordre), opérer (rapport mensuel, anomalies, décisions). Le premier levier est toujours d'éteindre ce qui ne sert pas.
  20. Multi-cloud subi, choisi, portable ; où est la vraie dépendance.
    Réponse attendue
    Subi : rachats, équipes qui ont choisi seules. Choisi : exigence client ou réglementaire, rare. Portable : un cloud principal et des briques standard (conteneurs, PostgreSQL, Terraform, OpenTelemetry). La vraie dépendance : identité, réseau, services serverless propriétaires, et surtout les données et les compétences.
