16.1 Pourquoi l'infrastructure as codeBon à savoir

Une infrastructure créée à la main est irreproductible, non revue, non versionnée, et connue d'une seule personne. En code : revue par merge request, historique Git, environnements identiques, reconstruction en cas de sinistre, documentation qui ne ment pas.

Deux familles d'outils : provisioning (créer les ressources : Terraform, OpenTofu, Pulumi, CloudFormation, CDK) et configuration (installer et régler ce qui tourne dessus : Ansible, Chef, Puppet). Terraform est déclaratif : tu décris l'état voulu, l'outil calcule les actions. OpenTofu est le fork communautaire (Linux Foundation) créé en 2023 après le changement de licence de Terraform ; syntaxe et providers identiques, commande tofu au lieu de terraform.

16.2 Le modèlePar cœur

   code HCL (.tf)         state (terraform.tfstate)          réalité (API cloud)
   ce que je veux    ◄──►  ce que Terraform croit exister ◄──►  ce qui existe
                 plan = diff(code, state)  ; refresh = diff(state, réalité)
terraform init      # télécharge providers et modules, configure le backend
terraform fmt       # formate
terraform validate  # syntaxe et cohérence
terraform plan -out=tfplan   # calcule les actions : + créer, ~ modifier, -/+ remplacer, - détruire
terraform apply tfplan       # exécute exactement le plan revu
terraform destroy
terraform state list ; terraform state show aws_instance.web
terraform output -json

Le state est le maillon critique : il contient les identifiants réels des ressources (et souvent des secrets en clair). Il doit être distant, chiffré, verrouillé, sauvegardé, et jamais commité.

16.3 Syntaxe HCLImportant

terraform {
  required_version = ">= 1.9"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.60" }
  }
  backend "s3" {
    bucket         = "crisisshield-tfstate"
    key            = "prod/network.tfstate"
    region         = "eu-west-3"
    dynamodb_table = "tfstate-lock"      # ou use_lockfile = true en 1.10+
    encrypt        = true
  }
}

provider "aws" { region = var.region }

variable "region"      { type = string, default = "eu-west-3" }
variable "environment" { type = string, validation { condition = contains(["dev","staging","prod"], var.environment), error_message = "dev, staging ou prod" } }
variable "cidr"        { type = string }

locals {
  name = "crisisshield-${var.environment}"
  tags = { Project = "crisisshield", Environment = var.environment, ManagedBy = "terraform" }
}

resource "aws_vpc" "main" {
  cidr_block           = var.cidr
  enable_dns_hostnames = true
  tags                 = merge(local.tags, { Name = local.name })
}

resource "aws_subnet" "private" {
  for_each          = { a = 0, b = 1, c = 2 }
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.cidr, 8, each.value)
  availability_zone = "${var.region}${each.key}"
  tags              = merge(local.tags, { Name = "${local.name}-private-${each.key}" })
}

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter { name = "name", values = ["ubuntu/images/hvm-ssd/ubuntu-noble-24.04-amd64-server-*"] }
}

output "vpc_id"     { value = aws_vpc.main.id }
output "subnet_ids" { value = [for s in aws_subnet.private : s.id] }
  • resource crée, data lit l'existant, variable entre, output sort, locals calcule.
  • for_each (map ou set) plutôt que count : supprimer un élément au milieu d'un count décale les index et recrée tout.
  • Fonctions : cidrsubnet, merge, lookup, templatefile, jsonencode, try. terraform console pour les tester.
  • Dépendances implicites par référence (aws_vpc.main.id) ; depends_on seulement quand la relation n'est pas dans les attributs.
  • lifecycle { prevent_destroy = true } sur une base de données ; create_before_destroy pour éviter une coupure lors d'un remplacement ; ignore_changes pour ce qu'un autre système modifie.

16.4 Modules et organisationImportant

infra/
├── modules/
│   ├── network/     main.tf variables.tf outputs.tf README.md
│   ├── database/
│   └── service/
└── envs/
    ├── dev/         main.tf (appelle les modules)  backend.tf  terraform.tfvars
    ├── staging/
    └── prod/
module "network" {
  source      = "../../modules/network"     # ou git::https://..., ou registre
  environment = "prod"
  cidr        = "10.20.0.0/16"
}
module "db" {
  source     = "../../modules/database"
  subnet_ids = module.network.subnet_ids
  instance   = "db.r6g.large"
}

Un module = une responsabilité, une interface (variables, outputs) documentée, versionné (tag Git) quand il est partagé. Un state par environnement et par domaine (réseau, données, applications) : un state géant est lent et un apply raté bloque tout. Les states se lisent entre eux avec terraform_remote_state ou, mieux, via des data sources.

Alternatives d'organisation : Terragrunt (DRY des backends et des variables), workspaces (déconseillés pour séparer des environnements réels : même backend, même code, une erreur de workspace détruit la prod).

16.5 Le state : incidents et réparationsPar cœur

terraform import aws_s3_bucket.logs crisisshield-logs      # adopter une ressource existante
# ou bloc import { to = aws_s3_bucket.logs, id = "crisisshield-logs" } puis plan -generate-config-out
terraform state mv aws_instance.old module.service.aws_instance.web   # renommer sans recréer
terraform state rm aws_instance.temp                        # oublier sans détruire
terraform force-unlock LOCK_ID                              # verrou orphelin après un crash
terraform apply -refresh-only                               # réconcilier le state avec la réalité
terraform plan -replace=aws_instance.web                    # forcer un remplacement
moved { from = aws_instance.old, to = aws_instance.web }    # refactoring déclaratif

Règle : ne jamais éditer le fichier state à la main. Sauvegarde automatique du state par le backend (versioning S3). Une équipe = un backend partagé avec verrouillage, sinon deux apply simultanés corrompent tout.

16.6 Terraform dans la CIImportant

.tf-base: &tf
  image: hashicorp/terraform:1.9
  before_script: [cd infra/envs/$ENV, terraform init -input=false]

validate:
  <<: *tf
  script: [terraform fmt -check -recursive, terraform validate]

security:
  image: aquasec/trivy
  script: trivy config --severity HIGH,CRITICAL --exit-code 1 infra/

plan:
  <<: *tf
  script: terraform plan -input=false -out=tfplan && terraform show -no-color tfplan > plan.txt
  artifacts: {paths: [infra/envs/$ENV/tfplan, infra/envs/$ENV/plan.txt], expire_in: 1 day}
  rules: [{if: $CI_PIPELINE_SOURCE == "merge_request_event"}, {if: $CI_COMMIT_BRANCH == "main"}]

apply:
  <<: *tf
  script: terraform apply -input=false tfplan
  needs: [plan]
  when: manual
  rules: [{if: $CI_COMMIT_BRANCH == "main"}]
  resource_group: $ENV          # un seul apply à la fois par environnement

Le plan est posté en commentaire de la merge request (outil tfcmt ou Atlantis) : le relecteur voit exactement ce qui va changer. Tests : terraform test (natif depuis 1.6, fichiers .tftest.hcl), Terratest (Go) pour des tests d'intégration réels. Sécurité : Trivy config / Checkov / tfsec détectent un bucket public, un security group ouvert, un chiffrement absent. Coûts : Infracost affiche le delta de coût dans la merge request.

Sans compte cloud : LocalStack émule les API AWS (S3, IAM, EC2, Lambda, DynamoDB...) dans un conteneur, avec le provider AWS pointé sur http://localstack:4566. Le provider docker (kreuzwerker) permet aussi de gérer des conteneurs, réseaux et volumes locaux en Terraform.

# Expressions : for, if, splat, dynamic
locals {
  subnets      = { for k, v in var.subnets : k => v if v.enabled }              # filtrer une map
  subnet_ids   = [for s in aws_subnet.private : s.id]                           # liste depuis for_each
  tags_by_env  = merge(local.tags, var.environment == "prod" ? { Backup = "true" } : {})
  instance_type = var.environment == "prod" ? "m7g.large" : "t4g.small"
}

resource "aws_security_group" "api" {
  name   = "${local.name}-api"
  vpc_id = aws_vpc.main.id
  dynamic "ingress" {                                  # un bloc par élément, sans copier-coller
    for_each = var.allowed_ports
    content {
      from_port       = ingress.value
      to_port         = ingress.value
      protocol        = "tcp"
      security_groups = [aws_security_group.alb.id]
    }
  }
  lifecycle {
    create_before_destroy = true
    precondition {                                     # échoue au plan avec un message clair
      condition     = length(var.allowed_ports) > 0
      error_message = "allowed_ports ne peut pas être vide."
    }
  }
}

# Plusieurs régions ou comptes : alias de provider
provider "aws" { alias = "dr", region = "eu-west-1" }
resource "aws_s3_bucket" "replica" { provider = aws.dr, bucket = "${local.name}-replica" }
module "network_dr" { source = "../../modules/network", providers = { aws = aws.dr }, cidr = "10.30.0.0/16" }

# Assumer un rôle dans un autre compte
provider "aws" { alias = "security", assume_role { role_arn = "arn:aws:iam::222222222222:role/terraform" } }

# Vérifications continues (1.5+) : évaluées à chaque plan, ne bloquent pas, alertent
check "certificate_valid" {
  data "aws_acm_certificate" "api" { domain = "api.crisisshield.example" }
  assert {
    condition     = data.aws_acm_certificate.api.status == "ISSUED"
    error_message = "Le certificat de l'API n'est pas émis."
  }
}

# Refactoring déclaratif, sans toucher au state à la main
moved   { from = aws_instance.web,        to = module.service.aws_instance.web }
removed { from = aws_s3_bucket.legacy,    lifecycle { destroy = false } }      # 1.7+ : oublier sans détruire
import  { to = aws_s3_bucket.logs,        id = "crisisshield-logs" }

# Valeurs sensibles et éphémères
variable "db_password" { type = string, sensitive = true }                     # masqué dans plan et outputs
ephemeral "aws_secretsmanager_secret_version" "db" { secret_id = "crisisshield/prod/db" }   # 1.10+ : jamais écrit dans le state
output "db_endpoint" { value = aws_db_instance.main.endpoint }
output "db_password" { value = var.db_password, sensitive = true }
  • Fonctions à connaître sans réfléchir : merge, lookup, try, coalesce, cidrsubnet, templatefile, jsonencode/yamldecode, flatten, zipmap, setproduct, format, regex, can. terraform console pour les tester sur le state réel.
  • Types : object({ name = string, size = optional(number, 20) }) avec valeurs par défaut ; validation sur chaque variable exposée par un module ; nullable = false.
  • Modules : une interface minimale (peu de variables, des objets), des outputs pour tout ce qu'un autre module pourrait consommer, un README généré (terraform-docs), une version par tag Git ou registre privé, des exemples dans examples/ qui servent de tests. Composer des petits modules plutôt qu'un module « tout-en-un » à 80 variables.
  • Provisioners (local-exec, remote-exec) : dernier recours ; ils ne sont pas idempotents et cassent le modèle. Préférer user_data, Packer, Ansible, ou un opérateur.
  • OpenTofu : mêmes fichiers ; en plus, chiffrement du state côté client, for_each sur les providers, fonctions fournies par des providers. Choix par licence et politique interne, pas par fonctionnalité.

Méthode devant un plan inattendu : lire le plan en entier avant d'agir ; chercher forces replacement et -/+ ; comparer avec state show ; ne jamais « appliquer pour voir » en production ; si la ressource est une base de données, s'arrêter et sauvegarder. Un apply en production se fait depuis la CI, après un plan revu, avec un plan sauvegardé, dans une fenêtre, avec un retour arrière connu (le commit précédent).

Techno de nichePour sortir du lot — Pulumi en Java ou Kotlin

L'infrastructure décrite dans un vrai langage : boucles, types, tests JUnit, packages Maven, mêmes fournisseurs que Terraform (par pont), état stocké dans S3 ou Pulumi Cloud.

Pourquoi ça différencie : Pour un expert Java, c'est un argument immédiat : « l'infra testée avec les mêmes outils que le code ». Peu de consultants IaC le pratiquent.

À essayer en une heure : docker run --rm -it -v "$PWD:/w" -w /w pulumi/pulumi-java pulumi new aws-java puis pointer le fournisseur AWS vers LocalStack et recréer le module réseau du TP 16.

En entretien — « Deux personnes lancent apply en même temps, que se passe-t-il ? » Sans verrou : corruption du state. Avec backend S3 + verrou : la seconde attend ou échoue. Enchaîne : state distant chiffré versionné, un state par environnement et domaine, apply uniquement depuis la CI avec resource_group, plan revu en merge request. Puis « et si le state est corrompu ? » : restaurer la version S3 précédente, refresh-only, import au pire.
Exercice 16.1

Un plan annonce -/+ aws_db_instance.main (forces replacement) à cause d'un changement de nom. Que fais-tu avant tout apply ?

Corrigé
Ne pas appliquer : le remplacement détruit la base. Vérifier si l'attribut est modifiable sans remplacement (souvent non pour identifier) ; sinon renoncer au renommage, ou passer par un snapshot et une restauration planifiée. Ajouter prevent_destroy = true pour que Terraform refuse ce type de plan à l'avenir.
Exercice 16.2

Pourquoi count = 3 puis suppression du deuxième élément d'une liste recrée-t-il des ressources, alors que for_each ne le fait pas ?

Corrigé
Avec count, les ressources sont adressées par index ([0], [1], [2]) ; supprimer l'élément 1 fait que l'ancien [2] devient [1] : Terraform voit une modification et recrée. Avec for_each, l'adresse est la clé (["b"]), stable.
Exercice 16.3

Où sont les secrets dans un projet Terraform, et comment les protéger ?

Corrigé
Dans les variables (ne pas les mettre dans tfvars commités : passer par TF_VAR_x depuis la CI ou un gestionnaire de secrets), dans le state (chiffrement du backend, accès restreint, sensitive = true pour masquer l'affichage), dans les outputs (sensitive = true). Idéalement, Terraform crée le secret dans Vault ou Secrets Manager et l'application l'y lit : le secret ne transite pas.
Exercice 16.4

Un module doit créer N buckets à partir d'une liste de noms, chacun avec versioning si un booléen est vrai, et exposer la map nom → ARN. Écris-le avec for_each, dynamic ou une expression conditionnelle, et un output.

Corrigé
variable "buckets" { type = map(object({ versioned = optional(bool, false) })) }
resource "aws_s3_bucket" "b" { for_each = var.buckets, bucket = each.key }
resource "aws_s3_bucket_versioning" "v" {
  for_each = { for k, v in var.buckets : k => v if v.versioned }
  bucket   = aws_s3_bucket.b[each.key].id
  versioning_configuration { status = "Enabled" }
}
output "arns" { value = { for k, b in aws_s3_bucket.b : k => b.arn } }
Exercice 16.5

Le pipeline échoue avec Error acquiring the state lock depuis 20 minutes. Déroule ta procédure, avec les vérifications avant le force-unlock.

Corrigé
Lire le message : il donne l'ID du verrou, qui l'a posé, quand, et depuis quelle machine. Vérifier qu'aucun job ne tourne (pipelines en cours, un collègue en local). Si le poseur est un job mort depuis plus longtemps que la durée d'un apply, terraform force-unlock ID ; puis plan pour vérifier que le state est cohérent (un apply interrompu peut avoir créé des ressources non enregistrées : les importer). Prévention : resource_group en CI, -lock-timeout, et jamais d'apply local sur l'environnement de prod.
Travail pratique 16 — Terraform contre LocalStack et Docker

Environnement : un compose.yaml avec localstack/localstack (port 4566) ; Terraform s'exécute avec docker run --rm -v "$PWD:/w" -w /w --network <réseau-compose> hashicorp/terraform:1.9 — écris un petit script tf.sh qui encapsule cette commande.

  1. Provider Docker : décris en Terraform la pile CrisisShield (réseau, volumes, conteneurs PostgreSQL, API, front) avec le provider kreuzwerker/docker. plan, apply, vérifie avec docker ps, change l'image de l'API, observe le plan de remplacement, apply. Puis destroy.
  2. LocalStack : module network (VPC, 3 sous-réseaux privés, 3 publics avec for_each, IGW, tables de routage), module storage (bucket S3 chiffré, versionné, accès public bloqué), module identity (rôle IAM avec politique minimale pour lire le bucket). Environnements dev et prod avec des CIDR différents.
  3. Backend distant : crée d'abord un bucket tfstate et une table DynamoDB dans LocalStack (un petit module « bootstrap » avec state local), puis migre les environnements vers ce backend (terraform init -migrate-state). Simule un verrou orphelin (tue le conteneur en plein apply) et répare avec force-unlock.
  4. Import : crée un bucket à la main avec awslocal s3 mb, puis adopte-le en Terraform avec un bloc import et -generate-config-out.
  5. Refactoring : renomme une ressource avec un bloc moved et prouve que le plan est vide.
  6. CI : pipeline fmt, validate, Trivy config (fais-le échouer avec un bucket public, corrige), plan en artefact, apply manuel avec resource_group. Écris deux tests .tftest.hcl sur le module network.
  7. Langage : réécris le module réseau avec dynamic pour les règles de security group, des variables typées object avec optional et validation, une precondition, un bloc check, et un alias de provider pour une seconde région LocalStack (deux conteneurs LocalStack ou deux régions du même). terraform-docs génère le README du module.
  8. Débogage : provoque et répare chacun des cas du tableau 16.8 que LocalStack permet (verrou orphelin, cycle de security groups, remplacement forcé, dérive de tags avec ignore_changes, lockfile multi-plateforme entre Git Bash et le conteneur CI). Note pour chacun la ligne du plan qui t'a mis sur la piste.
  9. Tests : trois .tftest.hcl avec mock_provider (sans rien créer) sur le module réseau, plus un terraform test réel contre LocalStack en CI ; un removed block pour sortir une ressource du state sans la détruire.

17.1 PrincipesBon à savoir

Ansible se connecte en SSH (pas d'agent), exécute des modules Python sur la cible, et décrit l'état voulu en YAML. Chaque module est idempotent : relancer un playbook ne change rien si l'état est déjà bon (ok contre changed). C'est l'outil de configuration : paquets, fichiers, services, utilisateurs, et de plus en plus l'orchestration de tâches ad hoc (rotation de certificats, patching).

17.7 Ansible en profondeur : variables, flux, stratégiesPar cœur

Précédence des variables (de la plus faible à la plus forte ; retenir les repères, pas les 22 niveaux) : defaults/ d'un rôle < group_vars/all < group_vars/<groupe> < host_vars/ < variables du play < vars/ d'un rôle < variables de bloc et de tâche < set_fact et register < --extra-vars (toujours gagnant). Règle pratique : les rôles exposent leurs réglages dans defaults/, l'inventaire les surcharge, -e sert aux exécutions ponctuelles.

- name: Déployer l'API avec reprise sur erreur
  hosts: web
  serial: "25%"                     # rolling : un quart des hôtes à la fois
  max_fail_percentage: 0            # on s'arrête au premier hôte en échec
  any_errors_fatal: true
  become: true
  tasks:
    - name: Retirer l'hôte du load balancer
      ansible.builtin.uri: { url: "https://lb.internal/api/drain/{{ inventory_hostname }}", method: POST }
      delegate_to: localhost         # exécuté depuis le contrôleur, pour chaque hôte

    - name: Déployer, avec retour arrière si échec
      block:
        - name: Nouvelle version
          community.docker.docker_compose_v2:
            project_src: /opt/crisisshield
          register: deploy
        - name: Attendre que l'API réponde
          ansible.builtin.uri: { url: "http://localhost:8080/actuator/health/readiness", status_code: 200 }
          register: health
          until: health.status == 200
          retries: 30
          delay: 2
      rescue:
        - name: Revenir à la version précédente
          ansible.builtin.command: /opt/crisisshield/rollback.sh
          changed_when: true
        - ansible.builtin.fail: { msg: "Déploiement annulé sur {{ inventory_hostname }}" }
      always:
        - name: Remettre l'hôte dans le load balancer
          ansible.builtin.uri: { url: "https://lb.internal/api/undrain/{{ inventory_hostname }}", method: POST }
          delegate_to: localhost

    - name: Tâche longue sans bloquer (async)
      ansible.builtin.command: /opt/tools/reindex.sh
      async: 1800
      poll: 0
      register: reindex
    - name: Vérifier plus tard
      ansible.builtin.async_status: { jid: "{{ reindex.ansible_job_id }}" }
      register: job
      until: job.finished
      retries: 60
      delay: 30

    - name: Une seule fois pour tout le groupe
      ansible.builtin.command: /opt/tools/notify-release.sh
      run_once: true
      delegate_to: "{{ groups['web'][0] }}"

    - name: Boucle sur une structure, avec libellé lisible
      ansible.builtin.user:
        name: "{{ item.name }}"
        groups: "{{ item.groups | join(',') }}"
      loop: "{{ users }}"
      loop_control: { label: "{{ item.name }}" }
      when: item.state | default('present') == 'present'

    - name: Idempotence forcée sur une commande
      ansible.builtin.command: /opt/tools/migrate.sh
      register: mig
      changed_when: "'applied' in mig.stdout"
      failed_when: mig.rc not in [0, 3]
  • Stratégies : linear (défaut, tâche par tâche sur tous les hôtes), free (chaque hôte avance à son rythme : plus rapide, ordre non garanti), debug. serial et throttle contrôlent la vague et la concurrence.
  • Filtres et lookups à connaître : default, combine, dict2items/items2dict, selectattr/map(attribute=), json_query, to_nice_yaml, b64encode, regex_replace, ipaddr ; lookup('file'), lookup('env'), lookup('ansible.builtin.password'), lookup('community.hashi_vault.hashi_vault'). Tester dans un playbook avec ansible.builtin.debug.
  • Templates : contrôle des blancs ({%- -%}), macros, {{ ansible_managed }} en entête, validate: sur les fichiers de config, backup: true.
  • Tags et reprise : --tags, --skip-tags, --start-at-task, --step, --limit @retry (rejouer seulement les hôtes en échec).
  • Vault : plusieurs identités (--vault-id prod@prompt), chiffrer une valeur plutôt qu'un fichier (encrypt_string) pour garder le diff lisible.

Un playbook affiche changed à chaque exécution sur une tâche shell: echo "x" >> /etc/motd. Problème et correction ?

Corrigé

Exercice 17.2

Pourquoi recharger nginx dans un handler plutôt que dans une tâche juste après le template ?

Corrigé
Le handler ne s'exécute que si une tâche l'a notifié suite à un changement réel, et une seule fois même si plusieurs tâches le notifient. Une tâche ordinaire rechargerait nginx à chaque passage, inutilement, et plusieurs fois.

18.1 Packer : des images de machines comme des images DockerBon à savoir

Packer construit une image à partir d'une source (AMI de base, ISO, image Docker), applique des provisioners (shell, Ansible), puis enregistre le résultat (AMI, image Azure, VMDK, image Docker) via des post-processors. Même logique que le Dockerfile, pour des VM. Cas d'usage : « golden images » de nœuds (Docker, agent de monitoring, durcissement déjà appliqués), démarrage rapide des autoscaling groups, conformité.

# ubuntu-docker.pkr.hcl
packer {
  required_plugins {
    amazon = { source = "github.com/hashicorp/amazon", version = "~> 1" }
    ansible = { source = "github.com/hashicorp/ansible", version = "~> 1" }
  }
}

variable "region" { default = "eu-west-3" }

source "amazon-ebs" "ubuntu" {
  region        = var.region
  instance_type = "t3.small"
  ssh_username  = "ubuntu"
  ami_name      = "crisisshield-node-{{timestamp}}"
  source_ami_filter {
    filters     = { name = "ubuntu/images/hvm-ssd/ubuntu-noble-24.04-amd64-server-*" }
    owners      = ["099720109477"]
    most_recent = true
  }
  tags = { Project = "crisisshield", BuiltBy = "packer" }
}

build {
  sources = ["source.amazon-ebs.ubuntu"]

  provisioner "shell" {
    inline = ["sudo apt-get update", "sudo apt-get upgrade -y"]
  }
  provisioner "ansible" {
    playbook_file = "../ansible/playbooks/node.yml"   # rôles common + docker
  }
  post-processor "manifest" { output = "manifest.json" }
}
docker run --rm -v "$PWD:/w" -w /w -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY hashicorp/packer:1.11 init .
... packer validate . && packer build .
# Le manifest contient l'ID de l'AMI, que Terraform lit ensuite (data "aws_ami" filtré sur le tag).

Sans AWS : le builder docker de Packer produit une image Docker à partir d'un provisioner Ansible, ce qui permet de valider la chaîne en local. Le builder qemu produit des images de VM à partir d'une ISO (autoinstall Ubuntu, kickstart RHEL) pour les datacenters ou Proxmox.

18.2 Cycle de vie d'une golden imageBon à savoir

  1. Pipeline hebdomadaire (ou déclenché par CVE) : Packer construit une nouvelle image, la scanne (Trivy sait scanner une VM ou une AMI), la tague.
  2. Terraform référence l'image par tag ou via un paramètre SSM ; un apply remplace les instances (rolling de l'autoscaling group).
  3. Les anciennes images sont conservées N semaines pour rollback, puis supprimées (coût de stockage).

C'est l'infrastructure immuable (chapitre 19) : on ne patche pas une machine, on la remplace.

18.3 VagrantBon à savoir

Vagrant décrit une VM de développement dans un Vagrantfile (box de base, réseau, dossiers partagés, provisioners) : vagrant up donne un environnement identique à toute l'équipe. Historiquement essentiel, il est largement remplacé par Docker Compose et les Dev Containers pour les applications, et reste utile pour tester des playbooks Ansible sur de vraies VM multi-OS, ou du réseau. Sous Windows, il pilote VirtualBox ou Hyper-V ; il ne tourne pas dans Docker, ce qui en fait un cas hors de ta règle « tout en conteneur » : à connaître, pas à installer.

  config.vm.network "private_network", ip: "192.168.56.10"
  config.vm.provider "virtualbox" do |vb| vb.memory = 2048 end
  config.vm.provision "ansible" do |a| a.playbook = "playbooks/web.yml" end

Pourquoi ça différencie : L'immutabilité poussée au bout ; c'est ce que choisissent les plateformes sur site et edge exigeantes, et un sujet qui impressionne en entretien sécurité.

Immutabilité, dérive et GitOps

En 30 secondes

  2. La dérive rend le code menteur : la détecter (plan nocturne), la prévenir (pas d'écriture console), la traiter.

  • Définir GitOps et ses quatre principes ; distinguer push et pull

19.1 Infrastructure immuableImportant

Un serveur muable est modifié au fil du temps (patchs, hotfix SSH, « juste ce fichier ») jusqu'à devenir un snowflake : unique, irreproductible, que personne n'ose redémarrer. Un serveur immuable n'est jamais modifié après création : tout changement = nouvelle image, nouvelle instance, l'ancienne est détruite. Conteneurs, golden images et autoscaling groups rendent cela naturel.

Conséquences : plus d'accès SSH en production (ou en lecture seule, tracé), les logs et données vivent hors de l'instance, les déploiements sont des remplacements, le rollback est un redéploiement de l'image précédente, et le « pet » devient du « cattle ».

19.2 La dérive (drift)Important

La dérive est l'écart entre ce que le code déclare et ce qui existe : quelqu'un a modifié un security group dans la console, un processus a changé un fichier de config, un autoscaling a créé des instances. Elle rend le code menteur et le prochain apply dangereux (il « corrige » ce que quelqu'un a fait exprès).

  • Détection : terraform plan planifié (job nocturne qui échoue si le plan n'est pas vide, avec alerte), ansible-playbook --check périodique, outils dédiés (driftctl, Cloud Custodian), et détection native (CloudFormation drift, ArgoCD OutOfSync).
  • Prévention : supprimer les droits d'écriture console en production (tout passe par la CI), politiques (SCP AWS, Azure Policy, OPA) qui refusent les ressources non taguées ManagedBy=terraform.
  • Traitement : soit le code est mis à jour (le changement manuel était légitime), soit la réalité est réalignée (apply), jamais laisser l'écart persister.

19.3 GitOpsPar cœur

Défini par l'OpenGitOps (CNCF), quatre principes :

  1. Déclaratif : l'état désiré du système est décrit (Kubernetes YAML, Terraform, Helm values).
  2. Versionné et immuable : cet état est stocké dans Git, seule source de vérité, avec historique complet.
  3. Tiré automatiquement : des agents récupèrent l'état désiré depuis Git (pull), plutôt que la CI qui pousse (push).
  4. Réconcilié en continu : les agents comparent l'état réel à l'état désiré et corrigent l'écart, en permanence. La dérive est éliminée par construction.
Push (CI classique)Pull (GitOps)
Qui déploieLe pipeline, avec des identifiants du cluster/cloudUn agent dans le cluster, qui lit Git
SecretsIdentifiants de prod dans la CI (surface d'attaque)La CI n'a qu'un accès Git ; le cluster n'expose pas d'API entrante
DériveDétectée seulement au prochain déploiementCorrigée en continu
RollbackRelancer un ancien pipelinegit revert
AuditLogs de CIHistorique Git = qui a changé quoi en prod
OutilsGitLab CI, Actions, JenkinsArgoCD, Flux (Kubernetes) ; Atlantis, Terraform Cloud, Spacelift (Terraform)

19.4 Structure des dépôtsBon à savoir

crisisshield/            (dépôt applicatif : code, Dockerfile, pipeline CI)
   CI : build → test → image sha-abc123 → met à jour le tag dans le dépôt de config ↓

crisisshield-config/     (dépôt de configuration : l'état désiré)
├── base/                manifests Kubernetes ou chart Helm communs
├── envs/
│   ├── staging/         kustomization.yaml, values.yaml (image: sha-abc123)
│   └── prod/            (image: sha-9f8e7d6, mis à jour par merge request revue)
└── infra/               Terraform, réconcilié par Atlantis ou un pipeline plan/apply

Séparer le code de la configuration évite qu'un changement de configuration prod redéclenche le build, et permet des droits différents (les développeurs fusionnent dans le code ; la prod exige une approbation sur le dépôt de config). Promotion staging → prod = une merge request qui copie le tag d'image. L'outil d'image updater (ArgoCD Image Updater, Flux image automation) peut automatiser la mise à jour du tag en staging.

Pièges : les secrets (chiffrés dans Git avec SOPS ou Sealed Secrets, ou référencés via External Secrets ; jamais en clair), les changements d'urgence (toujours via Git, même en incident, sinon l'agent annule la modification manuelle), et les bases de données (la réconciliation ne sait pas migrer des données).

Techno de nichePour sortir du lot — Digger

Orchestration Terraform en GitOps à l'intérieur de ta CI existante : plan posté en commentaire de merge request, apply après approbation, verrouillage par MR, détection de dérive, sans serveur dédié contrairement à Atlantis.

Pourquoi ça différencie : GitOps pour l'infrastructure sans nouveau composant à exploiter : un choix pragmatique que peu connaissent.

À essayer en une heure : Image diggerhq/digger dans un job GitLab du TP 16, avec le backend LocalStack ; observe le commentaire de plan et le verrou entre deux MR.

En entretien — « C'est quoi GitOps, en quoi c'est différent de la CI/CD ? » Les quatre principes, puis la différence push/pull et ses trois bénéfices : sécurité (pas d'identifiants prod dans la CI), dérive corrigée en continu, rollback par revert. Exercice 19.1

En pleine nuit, un ingénieur augmente à la main le nombre de réplicas d'un service de 3 à 10 pour absorber un pic. Le cluster est géré par ArgoCD avec auto-sync. Que se passe-t-il, et quelle aurait été la bonne procédure ?

Corrigé
ArgoCD détecte l'écart (OutOfSync) et remet 3 réplicas dans les minutes qui suivent. Bonne procédure : une merge request d'urgence sur le dépôt de config (avec un processus d'approbation accéléré), ou un autoscaler horizontal qui rend ce réglage automatique. En dernier recours, désactiver temporairement l'auto-sync de l'application, ce qui est tracé.
Exercice 19.2

Le terraform plan nocturne montre qu'un security group de prod autorise désormais le port 22 depuis 0.0.0.0/0, ajouté via la console. Décris le traitement complet.

Corrigé
Alerte immédiate (c'est une exposition). Identifier l'auteur (CloudTrail), comprendre le besoin (accès d'urgence ?), réaligner la réalité par apply (fermer), proposer la solution légitime en code (bastion, SSM Session Manager). Post-mortem : pourquoi la console était accessible en écriture, mettre une SCP ou retirer les droits.
Travail pratique 19 — Détection de dérive et dépôt de configuration
  1. Sur le projet Terraform du TP 16 : ajoute un pipeline planifié drift-detection (terraform plan -detailed-exitcode, code 2 = dérive) qui échoue et notifie. Provoque une dérive dans LocalStack (awslocal ec2 authorize-security-group-ingress) et vérifie la détection.
  2. Crée le dépôt crisisshield-config avec la structure de la section 19.4, en version Compose pour l'instant (envs/staging/compose.yaml et envs/prod/compose.yaml avec le tag d'image en variable dans un fichier image.env).
  3. Modifie le pipeline de CrisisShield : après le build d'image, un job met à jour envs/staging/image.env dans le dépôt de config par commit automatique (token de projet à portée minimale). La promotion en prod est une merge request manuelle.
  4. Écris un agent de réconciliation minimal en Bash (reconcile.sh, tournant dans un conteneur en boucle) : toutes les 60 s, git pull le dépôt de config, et si le tag ou le compose a changé, docker compose up -d. Le pipeline n'a alors plus aucun accès à ton « environnement de prod » : seulement à Git. Vérifie qu'un git revert sur le dépôt de config déclenche un rollback.
  5. Chiffre le fichier de secrets du dépôt de config avec SOPS + age (image ghcr.io/getsops/sops), et fais-le déchiffrer par l'agent.
