Chapitre 1Débutant

Architecture d'une Data Platform et rôles

En 30 secondes
  1. Une Data Platform collecte, stocke, transforme, sert et gouverne les données de l'entreprise ; l'équipe InfraOps/Data Platform en fournit les briques (calcul, bases, stockage, orchestration, monitoring) en libre-service aux équipes Data.
  2. Rôles : Data Engineer (pipelines), Data Scientist (modèles), Data Analyst (requêtes et tableaux de bord), DBA (bases), SRE/DevOps (fiabilité, automatisation), Data Platform Engineer (la plateforme elle-même), Tech Lead Talend (standards, revues, industrialisation).
  3. Tout passe par trois flux : ingestion (Talend, API, fichiers) → stockage (S3, PostgreSQL/Aurora, DynamoDB, Redshift) → service (Druid, Elasticsearch, BI), orchestré par Airflow et supervisé de bout en bout.
À la fin de ce chapitre, tu sauras

  • Dessiner l'architecture de référence de la mission
  • Situer chaque technologie dans un flux de données

Qui fait quoi

Diagnostic d'une machine lente

uptime                      # load > nombre de vCPU ? (load = runnable + iowait)
top -o %CPU / htop          # quel processus ; %st élevé = steal (voisin bruyant, instance burstable T sans crédits)
vmstat 1 5                  # r (runnable), b (bloqués IO), si/so (swap = manque de mémoire), wa (iowait), st
free -m                     # available faible ? swap utilisé ? dmesg -T | grep -i 'killed process' (OOM killer)
iostat -xz 1 5              # %util ~100, await élevé, avgqu-sz : disque saturé → gp3 IOPS/throughput, ou requête qui scanne
df -h ; du -xsh /var/* | sort -h | tail   # disque plein : logs, tmp Talend, WAL
ss -s ; ss -tnp state established | wc -l ; sar -n DEV 1 3   # connexions, retransmissions, débit
ps -eo pid,ppid,stat,%cpu,%mem,rss,etime,cmd --sort=-%mem | head   # processus zombie (Z), gros RSS (JVM Talend)
journalctl -u talend-jobserver --since '1 hour ago' ; systemctl status ; dmesg -T | tail   # erreurs système, disque, réseau
# JVM : jcmd <pid> GC.heap_info ; jstat -gcutil <pid> 1000 5 (GC continu = heap trop petit)

Patch, hardening, sauvegarde

Packer construit une AMI mensuelle (CIS : pas de root SSH, auditd, fail2ban inutile sans SSH, pare-feu, SSM agent) ; instance refresh de l'ASG remplace la machine ; SSM Patch Manager pour l'urgence ; Data Lifecycle Manager pour les snapshots EBS quotidiens (rétention 7/30 j) ; test de restauration trimestriel ; alarmes CloudWatch : StatusCheckFailed_System (recover automatique), CPUUtilization, mem_used_percent et disk_used_percent (agent), CPUCreditBalance sur T.

Exercice 3.1

Load average à 12 sur 4 vCPU mais CPU à 30 % : que se passe-t-il ?

Corrigé
Les processus attendent l'IO (état D) : le load compte les bloqués. vmstat montre b et wa élevés, iostat un disque à 100 %. Cause fréquente : job Talend qui écrit un gros fichier temporaire sur un gp2 épuisé.
Exercice 3.2

Question d'entretien : pourquoi un ASG de taille 1 ?

Corrigé
Pour l'auto-réparation (health check → remplacement), l'instance refresh (patch sans intervention) et la cohérence de configuration : la machine est jetable, le state est ailleurs (EBS séparé, S3, base).
Travail pratique 3 — EC2 Job Server et salle de diagnostic
  1. Launch template + ASG(1) + AMI Packer + user-data qui installe l'agent et le Job Server ; SSM Session Manager ; alarmes.
  2. Provoquer quatre saturations (stress-ng CPU, dd sur le disque, allocation mémoire jusqu'au swap, boucle réseau) et les diagnostiquer avec la séquence de commandes.
  3. Instance refresh avec une nouvelle AMI ; snapshot et restauration du volume data.

Le refresh remplace l'instance en 6 min sans perdre le volume data (attaché par user-data) ; la restauration du snapshot est chronométrée (12 min) et notée dans le runbook.
Chapitre 4Confirmé

PostgreSQL de débutant à expert

En 30 secondes
  1. Architecture : un processus par connexion (postmaster → backends), shared_buffers (cache), WAL (journal d'écriture : durabilité et réplication), checkpointer, autovacuum, background writer ; MVCC : chaque transaction voit un instantané, les anciennes versions restent jusqu'au vacuum.
  2. Index : B-tree (égalité, plage, tri), hash (égalité seule), GIN (tableaux, JSONB, full-text), GiST (géométrie, plages), BRIN (grosses tables ordonnées) ; un index sert quand il est sélectif et utilisé par le plan.
  3. Diagnostic : pg_stat_activity (qui attend quoi), pg_locks, pg_stat_statements (top requêtes), EXPLAIN ANALYZE (plan réel), pg_stat_user_tables (lignes mortes).
À la fin de ce chapitre, tu sauras
  • Expliquer MVCC, WAL, vacuum, verrous et niveaux d'isolation
  • Lire un EXPLAIN ANALYZE et corriger une requête lente
  • Diagnostiquer un blocage, un deadlock, une saturation

Architecture et réglages

shared_buffers = 25 % RAM ; effective_cache_size = 75 % RAM ; work_mem par opération de tri (attention : × connexions × opérations) ; maintenance_work_mem pour vacuum/index
max_connections : petit (100–300) + pooler (PgBouncer) ; wal_level = replica/logical ; checkpoint_completion_target 0.9 ; max_wal_size selon le débit d'écriture
MVCC : UPDATE = nouvelle version de ligne + ancienne marquée ; VACUUM récupère ; VACUUM FULL réécrit (verrou exclusif) ; autovacuum par table (scale_factor 0.2 par défaut → 0.02 sur les tables chaudes)
Isolation : READ COMMITTED (défaut : chaque instruction voit les commits précédents) ; REPEATABLE READ (instantané par transaction ; erreur de sérialisation possible) ; SERIALIZABLE (comme si en série ; retries à prévoir)
Verrous : lecture ne bloque pas écriture (MVCC) ; écriture bloque écriture sur la même ligne ; DDL prend AccessExclusive (file d'attente : lock_timeout !) ; deadlock = détecté après deadlock_timeout (1 s), une transaction annulée

Requêtes lentes

CREATE EXTENSION pg_stat_statements; SELECT calls, round(total_exec_time) AS ms, round(mean_exec_time,1) AS mean, rows, left(query,80) FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM ventes WHERE magasin_id = 42 AND date >= now() - interval '7 days';
-- Seq Scan on ventes (actual rows=8200 loops=1) Buffers: shared read=180000   → index manquant : CREATE INDEX CONCURRENTLY ON ventes (magasin_id, date DESC);
-- Index Scan … rows=8200 estimated=3 : statistiques fausses → ANALYZE ventes ; ALTER TABLE … ALTER COLUMN magasin_id SET STATISTICS 1000
-- Nested Loop avec 1 M de boucles : jointure mal estimée → index sur la clé de jointure, ou work_mem pour un Hash Join
-- Sort Method: external merge Disk: 250MB → work_mem trop petit pour cette requête (SET LOCAL work_mem)
SELECT pid, now()-xact_start AS age, state, wait_event_type, wait_event, left(query,60) FROM pg_stat_activity WHERE state <> 'idle' ORDER BY age DESC;   -- qui bloque / attend
SELECT blocked.pid, blocking.pid AS blocked_by, left(blocked.query,50) FROM pg_stat_activity blocked JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 5;   -- bloat
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag FROM pg_stat_replication;   -- réplication
Exercice 4.1

Un UPDATE de masse est lent et la table grossit : pourquoi ?

Corrigé
MVCC : chaque ligne modifiée devient une nouvelle version ; les anciennes attendent le vacuum. Faire par lots, laisser autovacuum passer (ou VACUUM manuel), éviter VACUUM FULL en production (verrou).
Exercice 4.2

Question d'entretien : différence entre REPEATABLE READ et SERIALIZABLE ?

Corrigé
RR garantit un instantané stable mais permet des anomalies d'écriture (write skew) ; SERIALIZABLE les détecte et annule une transaction (à réessayer). Le défaut READ COMMITTED suffit à la plupart des traitements.
Travail pratique 4 — Laboratoire PostgreSQL
  1. PostgreSQL 16 en Docker avec 5 M de lignes de ventes ; pg_stat_statements ; cinq requêtes lentes à corriger par EXPLAIN (index, statistiques, work_mem, jointure, partition).
  2. Provoquer un blocage (transaction ouverte + DDL) et un deadlock ; les lire dans pg_stat_activity/pg_locks ; corriger avec lock_timeout.
  3. Réplication streaming vers un second conteneur, mesure du lag, bascule manuelle (pg_ctl promote).
Correction type
Chaque correction est mesurée : 2 400 ms → 12 ms avec l'index composite ; le deadlock apparaît dans les logs avec les deux requêtes ; le DDL bloqué derrière la transaction longue bloque aussi les SELECT (file d'attente), ce qui justifie lock_timeout = '2s' dans les migrations ; le lag de réplication passe à 0 après un checkpoint.

Exercice 5.1

Après une bascule Aurora, l'application ne se reconnecte pas : pourquoi ?

Corrigé
Le pool a gardé des connexions vers l'ancien writer (désormais reader : erreurs « read-only transaction ») ou le cache DNS. Remède : endpoint cluster, TTL bas, validation des connexions dans le pool, retries, ou RDS Proxy qui absorbe la bascule.
Exercice 5.2

Question d'entretien : Multi-AZ RDS contre réplica de lecture ?

Corrigé
Multi-AZ = disponibilité (réplique synchrone invisible, bascule automatique) ; réplica = performance de lecture (asynchrone, lisible, promotion manuelle). Aurora fusionne les deux via son stockage partagé.
Travail pratique 5 — RDS et Aurora en pratique
  1. RDS PostgreSQL Multi-AZ et cluster Aurora Serverless v2 en Terraform, Parameter Groups, logs exportés, Performance Insights.
  2. Bascule forcée des deux, chronométrée avec une boucle d'écriture ; comparaison du comportement du pool Hikari avec et sans validation.
  3. Restauration PITR dans un cluster de test et vérification d'une ligne témoin ; destruction des ressources (coût mesuré).
Correction type
Mesures attendues : RDS Multi-AZ 55–70 s d'indisponibilité, Aurora 20–35 s ; sans validation du pool, 2 minutes d'erreurs « cannot execute INSERT in a read-only transaction » après la bascule Aurora ; PITR restaurée à la seconde demandée ; coût du labo ≈ 2 € pour 3 h.

Exercice 6.1

Une table DynamoDB de commandes avec PK = date du jour : problème ?

Corrigé
Toutes les commandes du jour tombent sur une partition : throttling garanti aux heures de pointe. Clé = identifiant de commande ou client#date, avec un GSI par date si on doit lister par jour (et le savoir chaud : sharding de la clé, date#suffixe).

Corrigé
Colonnaire, compressé, typé, avec statistiques : Redshift Spectrum et Athena ne lisent que les colonnes et blocs nécessaires : 10 à 100× moins de données scannées, donc plus rapide et moins cher.

Exercice 14.2

Corrigé
RTO = durée maximale d'interruption acceptée ; RPO = quantité de données (en temps) qu'on accepte de perdre. Ils se fixent par service avec le métier, se chiffrent en coût, et se prouvent par des exercices.
