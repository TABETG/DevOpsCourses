37.1 Shift-left et modélisation des menacesImportant

Corriger une faille coûte dix fois moins en conception qu'en production. Shift-left = déplacer la sécurité vers la gauche du cycle : exigences, conception, code, avant le build. Cela commence par la modélisation des menaces : pour chaque fonctionnalité, qui peut attaquer quoi, par où, et qu'est-ce qu'on fait.

Méthode STRIDE, appliquée à « créer un incident » dans CrisisShield
─────────────────────────────────────────────────────────────────────────────
S  Spoofing        Un attaquant se fait passer pour un opérateur      → authentification forte, jetons courts
T  Tampering       Modification d'un incident en transit ou en base   → TLS, contrôle d'intégrité, audit
R  Repudiation     Un opérateur nie avoir clôturé un incident         → journal d'audit signé, horodatage
I  Info disclosure Fuite de la localisation des victimes              → chiffrement, minimisation, RBAC
D  Denial          Saturation de l'API pendant une crise réelle       → rate limiting, autoscaling, WAF
E  Elevation       Un lecteur devient administrateur                  → contrôle d'accès côté serveur, tests

Outils : un diagramme de flux de données (DFD) avec les frontières de confiance, un atelier d'une heure par fonctionnalité sensible, OWASP Threat Dragon ou une simple table dans le dépôt. Les menaces deviennent des exigences, puis des tests. Références : OWASP Top 10, OWASP ASVS (exigences vérifiables par niveau), CWE Top 25.

37.3 SAST en pratiqueImportant

# Semgrep : règles communautaires + règles maison
semgrep ci --config p/owasp-top-ten --config p/java --config .semgrep/    # en CI, avec SARIF
# .semgrep/no-raw-query.yaml : interdire les requêtes JPA construites par concaténation
rules:
  - id: jpa-concat-query
    languages: [java]
    severity: ERROR
    message: Requête construite par concaténation, risque d'injection. Utiliser des paramètres nommés.
    patterns:
      - pattern: $EM.createQuery("..." + $X, ...)
      - pattern-not: $EM.createQuery("...", ...)

Semgrep est rapide et lisible : les règles maison encodent les conventions de l'équipe (pas de @CrossOrigin("*"), pas de désactivation CSRF, pas de Random pour un jeton). CodeQL (GitHub) fait de l'analyse de flux de données plus profonde mais plus lente. SonarQube couvre qualité et sécurité avec le quality gate. Pour le front : ESLint plugin security, Semgrep JavaScript.

37.4 SCA, SBOM et priorisationImportant

90 % du code d'une application moderne est de la dépendance. Le SCA les inventorie et croise avec les bases de CVE. Le SBOM (CycloneDX ou SPDX) est cet inventaire, produit à chaque build, stocké et versionné : quand une CVE sort, on interroge les SBOM au lieu de rescanner. Le VEX (Vulnerability Exploitability eXchange) documente pour chaque CVE si elle est exploitable dans ce produit (« non affecté : la fonction vulnérable n'est pas appelée »), ce qui coupe le bruit.

# Générer, stocker, interroger
syft crisisshield-api:1.7.0 -o cyclonedx-json > sbom.json
grype sbom:sbom.json --fail-on high          # scanner un SBOM sans l'image
# Attacher le SBOM à l'image dans le registre (chapitre 40 : signé)
cosign attach sbom --sbom sbom.json registry/crisisshield/api@sha256:...
# Dependency-Track : plateforme qui ingère les SBOM et alerte sur les nouvelles CVE

Prioriser : le CVSS mesure la gravité théorique ; EPSS estime la probabilité d'exploitation dans les 30 jours ; le catalogue KEV (CISA) liste les CVE exploitées activement ; la reachability (la fonction vulnérable est-elle appelée ?) est le meilleur filtre. Règle pratique : KEV → 24 h ; CVSS ≥ 9 avec EPSS élevé → 7 jours ; le reste par cycle de mise à jour Renovate. Un SLA de correction par sévérité, mesuré.

37.6 Un programme mesurableBon à savoir

Indicateurs : couverture des dépôts par les analyses, délai moyen de correction par sévérité, vulnérabilités ouvertes par âge, part des MR bloquées et pourquoi, dette de sécurité acceptée avec date de revue. Corrigé

Corrigé

38.1 Le problème des secretsImportant

Un secret statique (mot de passe de base, clé d'API) est copié dans des variables, des fichiers, des pipelines, des postes ; il ne tourne jamais ; personne ne sait qui l'a ; quand il fuit, on ne s'en aperçoit pas. Objectifs : centraliser, chiffrer au repos et en transit, contrôler et auditer chaque accès, faire tourner automatiquement, et surtout remplacer les secrets statiques par des identités (une charge de travail prouve qui elle est et reçoit un secret de courte durée) ou des secrets dynamiques (créés à la demande, révoqués à l'expiration).

38.2 VaultPar cœur

HashiCorp Vault (et son fork open source OpenBao) : un serveur qui stocke des secrets chiffrés, expose des moteurs, authentifie des clients par de nombreux moyens, applique des politiques et journalise tout.

Client (app, pipeline, humain)
   │ 1. s'authentifie (Kubernetes SA, OIDC, AWS IAM, AppRole, JWT GitLab)
   ▼
Vault ──► délivre un token avec des politiques et un TTL
   │ 2. lit ou génère un secret
   ├── KV v2         : secrets statiques versionnés (kv/crisisshield/prod/smtp)
   ├── Database      : identifiants PostgreSQL générés à la demande, TTL 1 h, révoqués après
   ├── PKI           : certificats X.509 émis à la volée (mTLS, services internes)
   ├── Transit       : chiffrement as a service (l'app envoie les données, Vault chiffre, la clé ne sort jamais)
   ├── AWS / Azure / GCP : identifiants cloud temporaires
   └── SSH, TOTP, Kubernetes (tokens de SA)
   3. audit device : chaque requête journalisée (hachée)
# Démarrer en labo (mode dev : en mémoire, non scellé ; en prod : stockage Raft, auto-unseal par KMS, HA)

# Secrets dynamiques PostgreSQL : un couple utilisateur/mot de passe par instance de l'app, 1 h de vie
v secrets enable database
v write database/config/crisis plugin_name=postgresql-database-plugin \
   connection_url="postgresql://{{username}}:{{password}}@db-rw.crisisshield.svc:5432/crisis" \
   allowed_roles=crisisshield-api username=vault password=...
v write database/roles/crisisshield-api db_name=crisis default_ttl=1h max_ttl=24h \
   creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT app_rw TO \"{{name}}\";"
v read database/creds/crisisshield-api      # → username v-kubernet-crisissh-x7f2..., password ..., lease 1h

Rotation du mot de passe root de la base par Vault lui-même (rotate-root) : plus personne ne le connaît. Chaque instance de l'application a ses propres identifiants : une fuite est attribuable et révocable sans impact sur les autres.

    import: vault://

38.4 Pipelines et humains sans secretsImportant

  • CI : le job GitLab présente son CI_JOB_JWT/ID token ; Vault (auth jwt) vérifie l'émetteur, le projet, la branche, et délivre un token de 10 minutes avec la politique du projet. Aucune variable secrète dans GitLab. Même principe avec AWS (OIDC), sans passer par Vault.
  • Humains : auth OIDC (Keycloak, Entra ID) avec MFA ; accès aux secrets de prod juste-à-temps, approuvé, tracé, expirant. Interface Vault ou CLI.
  • Serveurs : certificats SSH signés par Vault (validité 1 h) au lieu de clés autorisées permanentes.

38.5 KMS et chiffrement d'enveloppeImportant

Un KMS (AWS KMS, Azure Key Vault, GCP Cloud KMS, un HSM) garde des clés maîtresses qui ne sortent jamais du service (ou du matériel). Chiffrement d'enveloppe : on génère une clé de données (DEK), on chiffre les données avec, on chiffre la DEK avec la clé maîtresse (KEK) du KMS, et on stocke la DEK chiffrée à côté des données. Le KMS ne voit jamais les données ; on peut faire tourner la KEK sans rechiffrer les données. C'est ainsi que fonctionnent S3 SSE-KMS, EBS, RDS, les Secrets Kubernetes chiffrés au repos (EKS avec KMS), et le moteur Transit de Vault. Ton expérience PKI/HSM se raconte ici : un HSM est un KMS matériel certifié (FIPS 140-2/3), exigé pour les clés de signature critiques et certains référentiels.

# Transit : l'application ne manipule jamais la clé
v secrets enable transit ; v write -f transit/keys/crisisshield type=aes256-gcm96
v write transit/encrypt/crisisshield plaintext=$(echo -n "06 12 34 56 78" | base64)   # → vault:v1:...
v write transit/decrypt/crisisshield ciphertext=vault:v1:...
v write -f transit/keys/crisisshield/rotate     # nouvelle version ; rewrap possible sans tout déchiffrer

38.6 Sealed Secrets et SOPSBon à savoir

Quand il n'y a pas de gestionnaire de secrets (petit projet, cluster isolé) : Sealed Secrets (clé dans le cluster, kubeseal chiffre, le SealedSecret est commité) ou SOPS (fichiers chiffrés avec age, PGP ou une clé KMS ; Flux le déchiffre nativement, ArgoCD via plugin). Ce sont des solutions de chiffrement dans Git, pas de gestion de secrets : pas de rotation automatique, pas de secrets dynamiques, pas d'audit d'accès. Acceptables en dessous d'un certain niveau d'exigence, à documenter comme tel.

Techno de nichePour sortir du lot — Infisical et OpenBao

Infisical : plateforme de secrets open source avec interface, versionnage, injection par CLI, agent ou opérateur Kubernetes, secrets dynamiques et PKI, plus simple à adopter que Vault. OpenBao : le fork communautaire de Vault sous la Linux Foundation, choix des organisations qui refusent la licence BSL.

Pourquoi ça différencie : Savoir positionner Vault, OpenBao et Infisical selon le contexte (licence, souveraineté, taille d'équipe) est une réponse d'architecte.

À essayer en une heure : Compose d'Infisical, l'opérateur Kubernetes sur kind, et un secret de CrisisShield synchronisé ; puis remplace l'image Vault du TP 38 par openbao/openbao et vérifie la compatibilité.

En entretien — « Comment tu gères les secrets ? » Hiérarchie : d'abord supprimer le secret (identité : rôle IAM, Workload Identity, OIDC en CI), ensuite secret dynamique de courte durée (Vault database, PKI), ensuite secret statique centralisé avec rotation (Vault KV, Secrets Manager) livré par External Secrets, et en dernier le chiffrement dans Git (Sealed Secrets, SOPS) avec ses limites énoncées. KMS et enveloppe pour les données. Ta PKI/HSM est ton point fort : place-la.

39.1 Le modèle des 4 CPar cœur

Cloud (compte, réseau, IAM) → Cluster (API, etcd, nœuds, RBAC) → Conteneur (image, runtime, capabilities) → Code (l'application). Chaque couche protège la suivante ; une faille dans une couche externe rend les internes inutiles. Les niveaux précédents ont couvert le cloud et le code ; ce chapitre couvre cluster et conteneur.

39.2 Durcir le clusterImportant

  • API server : authentification OIDC (pas de certificats clients distribués aux humains), RBAC strict, audit logging activé et exporté (qui a fait quoi sur l'API), pas d'accès anonyme, admission control activé.
  • etcd : chiffrement au repos des Secrets (provider KMS sur EKS/AKS/GKE), accès réseau limité au control plane, sauvegardes chiffrées.
  • Nœuds : OS minimal (Bottlerocket, Flatcar, Talos : immuables, sans SSH), kubelet authentifié et autorisé (pas de port en lecture anonyme), mises à jour par remplacement (Packer, niveau 3), IMDS bloqué aux Pods (ou IMDSv2 avec hop limit 1).
  • Réseau : NetworkPolicies default-deny par namespace (chapitre 26), CNI qui les applique, egress contrôlé (les Pods n'ont pas besoin d'Internet en général), mTLS par mesh si exigé.
  • RBAC : aucun cluster-admin permanent pour les humains, rôles par namespace, ServiceAccounts dédiés sans token monté, audit des bindings (kubectl-who-can, rbac-tool).
  • Composants : versions supportées (Kubernetes a 3 versions maintenues, ~14 mois chacune), add-ons épinglés, scan des images de l'infrastructure aussi.

Le CIS Kubernetes Benchmark liste ces contrôles ; kube-bench les vérifie automatiquement (Job dans le cluster). kubescape couvre CIS, NSA/CISA et MITRE ATT&CK. Les fournisseurs managés en implémentent une partie ; le reste te revient.

39.3 Pod Security StandardsPar cœur

Trois profils définis par Kubernetes : privileged (tout), baseline (interdit le plus dangereux : privileged, hostNetwork, hostPath, capabilities dangereuses), restricted (le durcissement complet : non root, pas d'escalade, drop ALL, seccomp RuntimeDefault, volumes limités). Le contrôleur Pod Security Admission les applique par namespace avec trois modes : enforce (refuse), audit (journalise), warn (avertit).

apiVersion: v1
kind: Namespace
metadata:
  name: crisisshield
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: v1.31
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted

Approche : warn et audit partout d'abord, corriger les workloads (le Deployment du chapitre 26 est déjà conforme), puis enforce. Les namespaces système et certains agents (CNI, agents de logs, Falco) ont besoin de privilèges : namespaces dédiés, profil adapté, justification documentée.

39.4 Politiques as code : Kyverno et OPA GatekeeperImportant

PSA couvre la sécurité des Pods ; il ne dit rien sur « les images doivent venir de notre registre », « chaque Deployment a des requests », « pas de tag latest », « les Ingress ont TLS ». Un moteur de politiques en admission (webhook) valide, mute ou génère des ressources.

# Kyverno : YAML, lisible, avec mutation et génération
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: {name: images-registre-interne}
spec:
  validationFailureAction: Enforce
  background: true                       # aussi audit de l'existant
  rules:
    - name: registre-autorise
      match: {any: [{resources: {kinds: [Pod]}}]}
      exclude: {any: [{resources: {namespaces: [kube-system, monitoring]}}]}
      validate:
        message: "Les images doivent provenir de registry.crisisshield.example"
        pattern:
          spec:
            containers: [{image: "registry.crisisshield.example/*"}]
    - name: pas-de-latest
      match: {any: [{resources: {kinds: [Pod]}}]}
      validate:
        message: "Tag latest interdit : utiliser un digest ou une version"
        pattern:
          spec:
            containers: [{image: "!*:latest"}]
---
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: {name: defauts-securite}
spec:
  rules:
    - name: ajouter-seccomp
      match: {any: [{resources: {kinds: [Pod]}}]}
      mutate:
        patchStrategicMerge:
          spec:
            securityContext:
              +(seccompProfile): {type: RuntimeDefault}      # ajouté seulement si absent
    - name: generer-networkpolicy
      match: {any: [{resources: {kinds: [Namespace]}}]}
      generate:
        apiVersion: networking.k8s.io/v1
        kind: NetworkPolicy
        name: default-deny
        namespace: "{{request.object.metadata.name}}"
        data: {spec: {podSelector: {}, policyTypes: [Ingress, Egress]}}
---
# Vérification de signature d'image (chapitre 40)
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: {name: images-signees}
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30
  rules:
    - name: verifier-cosign
      match: {any: [{resources: {kinds: [Pod], namespaces: [crisisshield]}}]}
      verifyImages:
        - imageReferences: ["registry.crisisshield.example/crisisshield/*"]
          attestors:
            - entries:
                - keyless:
                    subject: "https://gitlab.example/crisisshield/backend//.gitlab-ci.yml@refs/heads/main"
                    issuer: "https://gitlab.example"
                    rekor: {url: https://rekor.sigstore.dev}
          mutateDigest: true       # remplace le tag par le digest vérifié

OPA Gatekeeper : le même rôle, avec des politiques en Rego (langage déclaratif puissant, courbe d'apprentissage) et des ConstraintTemplate réutilisables ; OPA sert aussi hors Kubernetes (Terraform, API, Envoy). ValidatingAdmissionPolicy (CEL, natif Kubernetes depuis 1.30) couvre les validations simples sans webhook. Choix courant : Kyverno pour Kubernetes, OPA quand la même politique doit s'appliquer ailleurs. Dans les deux cas, les politiques sont versionnées, testées (kyverno test, conftest) et appliquées en CI sur les manifests avant même le cluster.

39.5 Sécurité à l'exécutionImportant

Tout ce qui précède est préventif. Falco (CNCF) observe les appels système (eBPF) et alerte sur des comportements : un shell lancé dans un conteneur, une écriture dans /etc, une lecture de /etc/shadow, une connexion sortante inattendue, un binaire exécuté depuis /tmp, un montage du socket Docker. Les règles se personnalisent ; Falcosidekick route vers Slack, Loki, un SIEM. Alternatives : Tetragon (Cilium, peut aussi bloquer), Sysdig, Aqua, Wiz.

- rule: Shell dans un conteneur de production
  desc: Un shell interactif a été lancé dans un conteneur du namespace crisisshield
  condition: spawned_process and container and proc.name in (bash, sh, zsh) and k8s.ns.name = "crisisshield" and proc.tty != 0
  output: "Shell dans un conteneur (user=%user.name pod=%k8s.pod.name image=%container.image.repository cmd=%proc.cmdline)"
  priority: WARNING

Compléments : profils seccomp et AppArmor par workload (Security Profiles Operator génère les profils par observation), runtimes isolés (gVisor, Kata) pour les charges non fiables, scan continu des images déjà déployées (Trivy Operator produit des rapports CRD par workload).

39.6 Multi-locataire et postureBon à savoir

Plusieurs équipes ou clients sur un cluster : namespaces avec PSA restricted, quotas, NetworkPolicies, RBAC, politiques Kyverno par tenant, nœuds dédiés par taints pour les charges sensibles, et si l'isolation doit être forte, des clusters séparés (vCluster ou clusters virtuels comme intermédiaire). La posture se mesure : kube-bench, kubescape, Trivy Operator, CSPM cloud (Security Hub, Defender, Wiz) avec un score suivi dans le temps et des seuils par environnement.

Techno de nichePour sortir du lot — KubeArmor

Enforcement à l'exécution par les modules de sécurité du noyau (AppArmor, BPF-LSM) : il bloque, et pas seulement détecte, l'exécution de processus, l'accès à des fichiers ou le réseau par Pod, avec des politiques CRD et une découverte automatique du comportement normal.

Pourquoi ça différencie : Falco alerte ; KubeArmor empêche. Savoir les combiner est une réponse qui dépasse le discours habituel.

À essayer en une heure : Helm kubearmor sur kind, une KubeArmorPolicy qui interdit tout shell dans les Pods de l'API, puis kubectl exec refusé et journalisé.

En entretien — « Comment tu sécurises un cluster Kubernetes ? » Les 4 C, puis par couche : API OIDC + RBAC + audit, etcd chiffré, nœuds immuables sans SSH, NetworkPolicies default-deny, PSA restricted, Kyverno pour registre/signatures/ressources, Falco à l'exécution, kube-bench et Trivy Operator pour mesurer. Précise la méthode : audit → warn → enforce, jamais enforce d'un coup sur un cluster existant.

40.2 Sigstore : signer sans gérer de clésImportant

Sigstore = Cosign (signer et vérifier artefacts et images), Fulcio (CA qui émet des certificats de signature de 10 minutes liés à une identité OIDC), Rekor (journal de transparence public, en append-only, où chaque signature est enregistrée). Signature keyless : le pipeline s'authentifie par OIDC (GitLab, GitHub, Google), obtient un certificat éphémère, signe, publie dans Rekor ; le vérificateur exige que l'identité du signataire corresponde (« le job de la branche main du projet X »). Plus de clé privée à protéger et à faire tourner.

# Dans le pipeline (GitLab : id_tokens avec audience sigstore)
sign-image:
  id_tokens: {SIGSTORE_ID_TOKEN: {aud: sigstore}}
  script:
    - cosign sign --yes "$IMAGE@$DIGEST"                                    # signature keyless
    - cosign attest --yes --predicate sbom.json --type cyclonedx "$IMAGE@$DIGEST"   # attestation SBOM
    - cosign attest --yes --predicate provenance.json --type slsaprovenance "$IMAGE@$DIGEST"

# Vérifier (localement, en CI de déploiement, ou par Kyverno à l'admission)
cosign verify "$IMAGE@$DIGEST" \
  --certificate-identity "https://gitlab.example/crisisshield/backend//.gitlab-ci.yml@refs/heads/main" \
  --certificate-oidc-issuer https://gitlab.example
cosign verify-attestation --type cyclonedx ... | jq '.payload | @base64d | fromjson | .predicate'
# Signer aussi les blobs (binaire, chart Helm, fichier Terraform plan)
cosign sign-blob --yes --bundle release.bundle release.tar.gz

Pour une entreprise qui ne veut pas de journal public : Sigstore privé (Fulcio + Rekor auto-hébergés), ou signature avec clé dans un KMS/HSM (cosign sign --key awskms://...), ce qui rejoint ton expérience PKI. Notation (Notary v2) est l'alternative de la CNCF, avec clés classiques.

40.3 SLSA et la provenancePar cœur

SLSA (Supply-chain Levels for Software Artifacts) définit des niveaux pour la piste de build :

NiveauExigenceCe que ça empêche
Build L1Provenance existe (qui, quoi, comment, générée par le build)Erreurs, confusion sur l'origine
Build L2Provenance signée par une plateforme de build hébergéeFalsification de provenance après coup
Build L3Plateforme de build durcie : builds isolés, clés de signature inaccessibles au job, paramètres non modifiables par l'utilisateurCompromission par un job malveillant ou un mainteneur ; c'est le niveau visé

La provenance est une attestation in-toto : « cet artefact (digest) a été produit par ce builder, à partir de ce dépôt à ce commit, avec ces paramètres ». Générée par le builder (GitLab produit des attestations SLSA pour les artefacts ; GitHub via slsa-github-generator ou actions/attest-build-provenance), signée avec Sigstore, vérifiable par les consommateurs et par Kyverno. Les builds reproductibles (même source → mêmes octets) sont la vérification ultime ; Maven et Docker (BuildKit avec SOURCE_DATE_EPOCH, rewrite-timestamp) s'en approchent.

40.4 Sécuriser le pipeline lui-mêmeImportant

  • Runners : éphémères (un conteneur ou une VM par job, détruit après), isolés par projet ou par niveau de confiance, sans socket Docker (Kaniko, BuildKit rootless, ou build sur des runners dédiés), pas d'accès réseau non nécessaire.
  • Identité : OIDC partout, jetons à portée minimale et courte durée ; les jobs de MR de forks n'ont accès à aucun secret.
  • Code du pipeline : fichiers de pipeline protégés (CODEOWNERS, approbation obligatoire), templates centralisés versionnés et épinglés, images de job depuis le registre interne et épinglées par digest, actions/composants par SHA.
  • Dépendances de build : proxy Nexus/Artifactory avec liste d'autorisation, vérification des signatures Maven Central (pgpverify), npm audit signatures, lockfiles avec hashes (chapitre 14).
  • Séparation : le job qui construit n'a pas le droit de déployer ; le job qui déploie ne peut déployer que ce qui est signé par le job de build (GitOps + Kyverno ferment la boucle).

41.1 Zero trustPar cœur

Le modèle périmétrique (« à l'intérieur du réseau, on fait confiance ») ne tient plus : cloud, télétravail, mouvement latéral après une première compromission. Zero trust (NIST SP 800-207) : ne jamais faire confiance implicitement, toujours vérifier. Chaque accès est authentifié (identité forte de l'utilisateur et de l'appareil ou de la charge), autorisé (moindre privilège, contexte : appareil conforme, localisation, heure), chiffré, journalisé, et de courte durée.

Principe                      Implémentation
──────────────────────────── ──────────────────────────────────────────────────────────────
Identité forte des humains    IdP central (Keycloak, Entra ID), MFA résistant au phishing (FIDO2/passkeys), SSO partout
Identité des charges          Certificats SPIFFE (SPIRE, mesh), rôles IAM, tokens de ServiceAccount projetés
Micro-segmentation            NetworkPolicies, security groups par référence, mesh avec AuthorizationPolicy
Chiffrement partout           mTLS interne, TLS 1.3 externe, chiffrement au repos KMS
Accès aux ressources          Proxy d'identité (BeyondCorp, Cloudflare Access, Pomerium, Teleport) au lieu du VPN
Accès administrateur          Juste-à-temps, approuvé, enregistré (Teleport, Boundary, SSM Session Manager)
Posture de l'appareil         MDM, certificat machine, conformité vérifiée avant accès
Journalisation et détection   Tout accès tracé vers un SIEM ; alertes sur anomalies

Ce n'est pas un produit ni un projet : c'est une direction, appliquée d'abord aux accès les plus sensibles (production, secrets, données personnelles).

41.2 PKI interneImportant

CA racine (hors ligne : HSM ou machine isolée, clé jamais en ligne, validité 10-20 ans)
└── CA intermédiaire « services » (Vault PKI ou step-ca, en ligne, validité 2-5 ans)
│   ├── certificats de services internes (mTLS), validité heures à jours, renouvelés automatiquement
│   └── certificats Ingress internes via cert-manager
└── CA intermédiaire « personnes / machines » (certificats clients, SSH)
Externe : Let's Encrypt (ACME) pour tout ce qui est public, via cert-manager ou le load balancer cloud
  • Cycle de vie : émission automatisée (ACME, API Vault, cert-manager), durée courte (jours), renouvellement bien avant expiration, révocation (CRL, OCSP, ou simplement durée courte qui rend la révocation presque inutile), rotation des intermédiaires planifiée, cérémonie documentée pour la racine.
  • Distribution de la confiance : le certificat racine dans les trust stores (images de base, trust-manager dans Kubernetes, MDM sur les postes) ; la rotation de la racine est un projet en soi, d'où sa longue durée.
  • Erreurs classiques : certificats de 5 ans jamais renouvelés, clés privées dans Git, une seule CA pour tout, pas d'inventaire (une expiration = un incident majeur : alerte à 30 et 14 jours obligatoire, chapitre 35), SAN manquants.

41.3 Identité des charges de travail : SPIFFE et SPIREImportant

SPIFFE définit une identité universelle pour les charges : un identifiant spiffe://crisisshield.example/ns/crisisshield/sa/api porté par un certificat X.509 court (SVID) ou un JWT. SPIRE l'implémente : un serveur, des agents sur chaque nœud qui attestent les charges (par ServiceAccount, par processus, par métadonnées cloud) et leur délivrent des SVID renouvelés automatiquement. Istio et Linkerd utilisent SPIFFE en interne ; SPIRE l'étend hors du mesh (VM, autres clouds, sur site) et permet la fédération entre domaines de confiance. Résultat : plus aucun secret pour authentifier un service auprès d'un autre, d'une base, de Vault ou d'un cloud.

41.4 Authentification des humainsPar cœur

L'authentification est la première ligne de tout ce qui précède : un IdP mal configuré annule le mesh, la PKI et Vault. Ce que le DevSecOps exige d'un système d'authentification, quel que soit le produit :

  • Mots de passe : stockés avec Argon2id (ou bcrypt), jamais réversibles ; politique NIST SP 800-63B : longueur (12 caractères et plus) plutôt que complexité imposée, pas d'expiration périodique, refus des mots de passe compromis (liste Have I Been Pwned), pas d'indices ni de questions secrètes.
  • MFA : obligatoire pour tout accès sensible et tout administrateur. Du plus faible au plus fort : SMS (interceptable), TOTP (application), notification push avec appariement de numéro, FIDO2 / passkeys (résistant au phishing : la clé est liée au domaine, un faux site n'obtient rien). Les passkeys sont le standard à recommander en 2026.
  • SSO : une identité, un endroit où la désactiver. OpenID Connect pour tout ce qui est moderne, SAML 2.0 pour les applications d'entreprise legacy ; l'IdP (Keycloak, Entra ID, Okta) fédère les annuaires (LDAP, Active Directory) et les fournisseurs sociaux ou partenaires (identity brokering).
  • Sessions : cookie HttpOnly, Secure, SameSite=Lax ou Strict, identifiant régénéré après connexion (fixation), durée absolue et durée d'inactivité, révocation côté serveur, déconnexion propagée (back-channel logout OIDC).
  • Attaques à traiter : force brute et credential stuffing (limitation par compte et par IP, verrouillage progressif, détection d'anomalie), énumération de comptes (messages identiques que le compte existe ou non), phishing (passkeys, pas de lien de connexion magique sans second facteur), et surtout la récupération de compte, maillon faible de tout système : elle doit être aussi forte que la connexion.
  • Keycloak en pratique : un realm par domaine de confiance, des clients par application avec le flux strictement nécessaire, des flows d'authentification personnalisés (MFA conditionnelle par rôle ou par risque), la détection de force brute activée, les événements exportés vers le SIEM, la configuration en code (export du realm, keycloak-config-cli, opérateur), la haute disponibilité (cluster, base PostgreSQL managée) et un suivi rigoureux des versions : Keycloak publie régulièrement des correctifs de sécurité.

41.5 OAuth 2.1 et OpenID Connect en détailPar cœur

OAuth 2.1 est un cadre de délégation d'autorisation : une application obtient un jeton pour appeler une API au nom d'un utilisateur, sans jamais voir son mot de passe. OpenID Connect ajoute l'authentification par-dessus : un jeton d'identité (id_token) signé qui dit qui s'est connecté, quand, et comment. Quatre rôles : le propriétaire de la ressource (l'utilisateur), le client (l'application), le serveur d'autorisation (Keycloak), le serveur de ressources (l'API).

FluxPourStatut en OAuth 2.1
Authorization Code + PKCEToute application avec un utilisateur : web, SPA, mobile, CLI avec navigateurLe flux par défaut ; PKCE obligatoire pour tous les clients, publics ou confidentiels

Les trois jetons et ce qu'on en fait :

  • Access token : pour appeler l'API ; courte durée (5 à 15 minutes) ; audience (aud) = l'API visée, scopes minimaux ; JWT signé ou jeton opaque vérifié par introspection. Le client ne le lit pas, il le transmet.
  • ID token : pour le client, jamais envoyé à une API ; contient sub, auth_time, acr (niveau d'authentification), nonce (anti-rejeu).
  • Refresh token : pour obtenir un nouvel access token sans réauthentifier ; longue durée mais rotation à chaque usage avec détection de réutilisation (un refresh token volé et rejoué révoque toute la famille) ; lié au client ; côté navigateur uniquement via un BFF, jamais dans le localStorage.
// Valider un JWT côté serveur de ressources : la liste complète, sans exception
1. alg dans une liste blanche (RS256 ou ES256) ; refuser "none" et HS256 avec un secret partagé
2. signature vérifiée avec la clé publique désignée par kid, obtenue via le JWKS de l'émetteur (cache, rotation)
3. iss = exactement l'URL attendue (https://auth.crisisshield.example/realms/crisis)
4. aud contient l'identifiant de cette API (sinon un jeton émis pour une autre API est réutilisable ici)
5. exp et nbf avec une tolérance d'horloge de quelques secondes
6. typ / scope / rôles : le jeton a le droit de faire cette opération
7. Contrôle d'accès par objet : cet utilisateur a-t-il le droit sur CET incident (IDOR) — le jeton ne le dit pas, le code doit le vérifier

Compléments quand le risque le justifie : jetons liés au client (DPoP : preuve de possession d'une clé, ou mTLS-bound) pour qu'un jeton volé soit inutilisable ; PAR (Pushed Authorization Requests) et JAR pour ne pas exposer les paramètres d'autorisation dans l'URL ; FAPI 2.0 comme profil de référence pour la finance et la santé. Découverte automatique via /.well-known/openid-configuration : ne jamais coder en dur les URL des points de terminaison.

# Spring Boot 3 : l'API comme serveur de ressources (aucun secret, seulement l'émetteur)
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.crisisshield.example/realms/crisis
          audiences: [crisisshield-api]        # rejette les jetons émis pour d'autres API
@Configuration
@EnableMethodSecurity
class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
            .csrf(c -> c.disable())                       // API sans session ni cookie : pas de CSRF
            .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(a -> a
                .requestMatchers("/actuator/health/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/incidents/**").hasAuthority("ROLE_operator")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(keycloakRoles())))
            .build();
    }
    // Les rôles Keycloak sont dans realm_access.roles : les convertir en autorités Spring
    JwtAuthenticationConverter keycloakRoles() {
        var conv = new JwtAuthenticationConverter();
        conv.setJwtGrantedAuthoritiesConverter(jwt -> {
            var realm = (Map<String, Object>) jwt.getClaims().getOrDefault("realm_access", Map.of());
            var roles = (Collection<String>) realm.getOrDefault("roles", List.of());
            return roles.stream().map(r -> new SimpleGrantedAuthority("ROLE_" + r)).collect(toList());
        });
        return conv;
    }
}

Validation et révocation

  • Validation par le client : chaîne jusqu'à une racine de confiance du magasin (système, navigateur, JVM cacerts, ou magasin applicatif), dates, nom (SAN), usages, révocation. Le serveur doit envoyer le certificat feuille et les intermédiaires ; jamais la racine (elle est déjà chez le client).
  • Révocation : CRL (liste signée, téléchargée, lourde), OCSP (requête par certificat, fuite de vie privée, dépendance), OCSP stapling (le serveur joint la réponse OCSP : à activer), et la solution moderne : certificats courts (heures ou jours) renouvelés automatiquement, où la révocation devient inutile. C'est le choix du mesh, de Vault PKI et de cert-manager en interne.
  • Épinglage (pinning) : à éviter sauf cas précis (mobile vers sa propre API) car il casse la rotation ; préférer la validation de la chaîne et Certificate Transparency pour les certificats publics.

Exploiter une PKI

  • Inventaire : tout certificat est connu (émetteur, propriétaire, expiration, où il est déployé) ; sans inventaire, l'expiration est un incident garanti. cert-manager et Vault donnent l'inventaire interne ; pour l'externe, scan et Certificate Transparency.
  • Automatisation : ACME (Let's Encrypt, ou une CA interne qui parle ACME comme step-ca ou Vault), cert-manager, renouvellement bien avant expiration, rechargement sans coupure.
  • Cérémonie de clés pour la racine : machine hors ligne, plusieurs témoins, procédure écrite, clé dans un HSM ou chiffrée et partagée (Shamir), certificat racine publié, journal signé ; la racine ne signe que des intermédiaires, une ou deux fois par décennie.
  • HSM et KMS : clés critiques (racine, signature de code, signature de jetons) dans un HSM (PKCS#11, certification FIPS 140-3 ou Critères Communs) ou un KMS cloud ; la clé ne sort jamais, les opérations sont journalisées ; les exigences RGS, eIDAS, PCI l'imposent.
  • Signature de code et d'artefacts : la PKI signe aussi les jars, images, paquets (chapitre 40) et les jetons (JWT, chapitre 41.5) ; la rotation des clés de signature de l'IdP se fait par JWKS avec plusieurs clés actives.
  • Cadres : RGS en France pour l'administration, eIDAS pour la signature électronique, les Baseline Requirements du CA/Browser Forum pour les certificats publics, le durcissement TLS de l'ANSSI comme référence de configuration.

Exercice 41.1

Le certificat de la CA intermédiaire expire dans 30 jours. Déroule la rotation sans interruption des services qui présentent des certificats émis par elle.

Corrigé
Émettre une nouvelle intermédiaire signée par la racine (cérémonie), la publier dans Vault comme nouvel émetteur par défaut tout en gardant l'ancienne active, distribuer la chaîne mise à jour dans les trust stores (les deux intermédiaires sont signées par la même racine : les clients qui font confiance à la racine acceptent les deux), laisser les certificats courts se renouveler naturellement sur la nouvelle (24 h), vérifier qu'aucun certificat n'est plus émis par l'ancienne, la retirer après expiration du dernier certificat émis. Alerte à 30 jours = c'est déjà tard ; planifier à 90.
Exercice 41.2

Une SPA React stocke l'access token dans le localStorage et l'envoie en en-tête Authorization. Deux risques et l'architecture recommandée.

Corrigé
XSS = vol du jeton ; refresh token dans le navigateur = session longue volable. Recommandation : BFF (backend for frontend) qui gère les jetons côté serveur et donne au navigateur un cookie de session HttpOnly Secure SameSite, ou à défaut Authorization Code + PKCE avec jetons très courts, refresh rotation, et politique CSP stricte.
Exercice 41.3

Une API accepte tout JWT dont la signature est valide auprès du JWKS de Keycloak. Trouve trois attaques que cette validation laisse passer et la ligne de configuration ou de code qui ferme chacune.

Corrigé
Un jeton émis pour une autre API du même realm (pas de vérification d'audience → audiences / token.audience) ; un jeton d'un autre realm ou d'un autre émetteur qui publie aussi un JWKS (pas de vérification d'iss → issuer-uri exact) ; un id_token utilisé comme access token (vérifier typ/azp et l'audience) ; et, si l'algorithme n'est pas restreint, un jeton alg: none ou HS256 signé avec la clé publique comme secret (liste blanche d'algorithmes). Enfin, la signature ne dit rien du droit sur l'objet : IDOR reste à traiter dans le code.
Exercice 41.4

Le service Incidents doit appeler le service Notification « au nom de » l'opérateur connecté. Compare trois options : relayer l'access token reçu, utiliser Client Credentials, utiliser Token Exchange.

Corrigé
Relayer le jeton : simple mais l'audience ne correspond pas (rejet, ou pire, acceptation laxiste) et Notification reçoit un jeton trop puissant. Client Credentials : Notification sait qu'Incidents appelle, mais perd l'identité de l'opérateur (audit et autorisation impossibles). Token Exchange : Incidents échange le jeton contre un jeton d'audience notification à portée réduite, qui porte l'utilisateur d'origine et le service intermédiaire (act) ; c'est la solution correcte, complétée par mTLS/SPIFFE entre les deux services.
Exercice 41.5

Un client Java refuse de se connecter à ton API avec PKIX path building failed, alors que curl depuis la même machine fonctionne. Quatre hypothèses, dans l'ordre où tu les vérifies.

Corrigé
1) La JVM utilise son propre cacerts qui ne contient pas la racine interne (curl utilise le magasin système) : keytool -list et ajouter la racine, ou un truststore applicatif. 2) Le serveur n'envoie pas l'intermédiaire et curl a la chaîne en cache ou dans son magasin : openssl s_client -showcerts. 3) Un proxy d'entreprise réécrit les certificats et sa racine n'est que dans le magasin système. 4) Version de Java ancienne qui refuse l'algorithme ou la taille de clé. Jamais de TrustManager qui accepte tout « pour tester ».

Outils de conformité continue : les CSPM (Security Hub avec ses standards, Defender for Cloud, Wiz, Prowler en open source) mappent automatiquement l'état du cloud sur CIS, ISO, PCI ; les plateformes de GRC (Vanta, Drata, Sprinto) collectent les preuves par API et suivent les contrôles ; OSCAL (NIST) normalise politiques et preuves en machine-lisible. 42.3 Le RGPD dans la plateformeImportant

  • Cartographie : où sont les données personnelles (bases, logs, sauvegardes, traces, files Kafka, exports) ; le registre des traitements en dépend.
  • Minimisation et pseudonymisation : ne collecter que le nécessaire ; identifiants indirects dans les logs et les traces ; données sensibles chiffrées au niveau applicatif (Transit, chapitre 38) avec clé par organisation pour permettre l'effacement par destruction de clé (crypto-shredding).
  • Droits : l'effacement doit atteindre les sauvegardes (délai documenté) et les journaux (rétention limitée) ; la portabilité exige un export machine-lisible.
  • Localisation et sous-traitants : régions européennes, liste des sous-traitants (cloud, SaaS d'observabilité, e-mail) avec clauses contractuelles ; transferts hors UE encadrés.
  • Violation : détection (chapitres 35, 39), qualification, notification à la CNIL sous 72 h ; le processus d'incident (chapitre 36) inclut le DPO.
  • Privacy by design : analyse d'impact (AIPD) pour les traitements à risque (données de santé, localisation, surveillance), et le DevSecOps y contribue la partie technique.

Révision du niveau 7

Réponds à voix haute, sans support, comme en entretien. En dessous de trois quarts de réponses solides, reprends les chapitres concernés avant de passer au niveau suivant.

  1. STRIDE sur une fonctionnalité de ton choix, en deux minutes.
    Réponse attendue
    Prendre la fonctionnalité (ex. export CSV), tracer les flux et frontières de confiance, puis par lettre : Spoofing (jeton forgé), Tampering (paramètre modifié), Repudiation (pas de journal), Information disclosure (PII dans l'export), Denial of service (export massif), Elevation (rôle dans le corps). Pour chaque menace : contrôle et test.
  2. La cartographie des analyses de sécurité : étape, outil, mode bloquant ou non.
    Réponse attendue
    Commit : secrets (gitleaks), lint. MR : SAST (Semgrep, bloquant High), SCA (Trivy fs, bloquant High/Critical avec SLA), IaC (Checkov, bloquant sur les règles critiques). Build : SBOM (Syft), scan image (Trivy), signature. Staging : DAST (ZAP, non bloquant puis bloquant sur les règles triées). Prod : admission (Kyverno), runtime (Falco), surveillance continue (Dependency-Track, Trivy Operator).
  3. SBOM, VEX, EPSS, KEV, reachability : rôle de chacun dans la priorisation.
    Réponse attendue
    SBOM : ce qu'on a. VEX : ce qui ne nous affecte pas (avec justification). EPSS : probabilité d'exploitation dans les 30 jours. KEV : exploité activement (CISA). Reachability : le code vulnérable est-il appelé. Priorité : KEV et EPSS élevé et atteignable d'abord, VEX pour clore le reste avec preuve.
  4. Comment introduire la sécurité sans qu'elle soit contournée.
    Réponse attendue
    Commencer en audit, trier avec l'équipe, ne bloquer que ce qui est sûr, message d'erreur qui donne la correction, SLA raisonnable, exception datée possible, champions dans les équipes, mesurer le bruit, et rendre le chemin conforme plus facile que le contournement (template, plateforme).
  5. La hiérarchie des secrets : identité > dynamique > statique centralisé > chiffré dans Git.
    Réponse attendue
    Le mieux est de ne pas avoir de secret (identité : rôle IAM, SVID, OIDC) ; sinon des secrets dynamiques à durée courte (Vault database) ; sinon un secret statique dans un gestionnaire central avec rotation et audit ; en dernier, chiffré dans Git (SealedSecrets, SOPS), jamais en clair.
  6. Vault : moteurs, auth, politiques, audit ; livrer un secret à un Pod (cinq méthodes).
    Réponse attendue
    Moteurs : kv, database, transit, pki, aws… Auth : kubernetes, jwt (CI), oidc (humains), approle, cert. Politiques : chemins et capacités, par identité. Audit : chaque requête journalisée. Livrer un secret à un Pod : Vault Agent sidecar, injector (annotations), CSI provider, External Secrets (Secret K8s généré), ou l'application via Spring Cloud Vault.
  7. Chiffrement d'enveloppe ; KMS contre HSM ; le moteur Transit.
    Réponse attendue
    Chiffrement d'enveloppe : une clé de données chiffre les données, une clé maîtresse (KMS) chiffre la clé de données ; on ne fait tourner que la maîtresse. KMS : service géré, clés en logiciel/HSM, facturé à l'appel. HSM : matériel certifié, clés qui ne sortent jamais, pour la PKI racine et les exigences réglementaires. Transit : « chiffrement comme service » de Vault, l'application n'a jamais la clé.
  8. Les 4 C ; durcir l'API, etcd, les nœuds.
    Réponse attendue
    Cloud, Cluster, Container, Code : chaque couche suppose la précédente durcie. API : audit, RBAC minimal, anonymous-auth off, admission, chiffrement des secrets etcd. etcd : TLS, accès réservé, sauvegardes chiffrées. Nœuds : OS minimal (Talos, Bottlerocket), pas de SSH, kubelet authentifié, CIS benchmark, rotation des nœuds.
  9. Pod Security Standards : trois profils, trois modes, la méthode de déploiement.
    Réponse attendue
    Privileged, baseline, restricted. Modes : enforce (refuse), audit (journalise), warn (avertit). Déploiement : warn + audit sur tout, corriger les violations lues dans l'audit, puis enforce namespace par namespace ; exceptions documentées pour l'infrastructure.
  10. Kyverno contre OPA Gatekeeper contre ValidatingAdmissionPolicy ; validate, mutate, generate, verifyImages.
    Réponse attendue
    Kyverno : YAML, natif Kubernetes, valide, mute, génère, vérifie les signatures. Gatekeeper : Rego (OPA), puissant et verbeux, validation surtout. VAP : CEL intégré à l'API server, sans composant, validation simple. Validate : refuser ; mutate : compléter (seccomp) ; generate : créer (NetworkPolicy par namespace) ; verifyImages : signature et attestations à l'admission.
  11. Falco : ce qu'il voit ; trois règles utiles.
    Réponse attendue
    Falco observe les appels système (eBPF) et les événements Kubernetes en temps réel : ce que fait un processus déjà dans un Pod. Règles : shell interactif dans un conteneur de prod, lecture d'un secret monté par un processus inattendu, connexion sortante hors des destinations connues (ou écriture dans /usr/bin).
  12. Les attaques supply chain de référence et leur leçon.
    Réponse attendue
    SolarWinds (build compromis → signer le build et la provenance), Codecov (script CI modifié → épingler par hash, vérifier), Log4Shell (dépendance transitive → SBOM et SCA continue), xz (mainteneur infiltré → reproductibilité, dépendances minimales), event-stream/typosquats npm (lockfile, proxy avec liste, délai avant adoption).
  13. Sigstore keyless : Cosign, Fulcio, Rekor ; ce qu'une signature prouve et ne prouve pas.
    Réponse attendue
    Cosign signe ; Fulcio émet un certificat de 10 min lié à une identité OIDC (le pipeline de main) ; Rekor journalise la signature de façon publique et infalsifiable. Prouve : ce digest a été signé par cette identité à cette date. Ne prouve pas : que le contenu est sain, que le pipeline n'était pas compromis, ni que le code est celui attendu (d'où provenance et reproductibilité).
  14. SLSA : les trois niveaux de build ; provenance ; reproductibilité.
    Réponse attendue
    L1 : provenance existe. L2 : provenance générée et signée par un service de build hébergé. L3 : build isolé (runner éphémère, sans socket), jetons non exportables, provenance non falsifiable par le job. Provenance : qui, quoi, comment, avec quelles entrées. Reproductibilité : même source → même digest, vérifiable par un tiers.
  15. Sécuriser le pipeline lui-même : six mesures.
    Réponse attendue
    Runners éphémères sans socket Docker, images de job épinglées par digest, jetons d'identité courts (pas de variable secrète), branches protégées et revue obligatoire, dépendances du pipeline épinglées (actions par SHA, charts par version), journal et signature de ce que le pipeline produit, compliance pipeline non contournable.
  16. Zero trust : principes NIST et implémentation par principe.
    Réponse attendue
    NIST 800-207 : toute ressource est une ressource, l'accès est par session, décidé dynamiquement (identité, appareil, contexte), tout est authentifié et chiffré, tout est journalisé. Implémentation : IdP unique et MFA/passkeys, identité des charges (SPIRE, mTLS), micro-segmentation (NetworkPolicy, mesh), accès JIT (Teleport), certificats courts, audit centralisé.
  17. Une PKI interne : hiérarchie, durées, rotation de l'intermédiaire, HSM.
    Réponse attendue
    Racine hors ligne (10 ans, cérémonie, clé chiffrée hors du poste, HSM en entreprise) → intermédiaire en ligne (Vault PKI, 5 ans, renouvelée à mi-vie) → feuilles courtes (24 h à 90 j, automatisées par cert-manager). Rotation de l'intermédiaire : nouvelle CSR signée par la racine, distribution des deux dans le bundle, bascule des émissions, retrait de l'ancienne après expiration des feuilles.
  18. SPIFFE/SPIRE : ce que c'est, ce que ça supprime.
    Réponse attendue
    SPIFFE : un standard d'identité pour les charges (spiffe://domaine/ns/…/sa/…) portée par un SVID (certificat X.509 ou JWT). SPIRE : l'implémentation (serveur + agents) qui attest les charges et renouvelle les SVID. Supprime : mots de passe entre services, secrets de bootstrap, listes d'IP ; la base et Vault authentifient par certificat.
  19. Authentification des humains : mots de passe (Argon2id, NIST), MFA et passkeys, SSO, sessions, récupération de compte.
    Réponse attendue
    Mots de passe : Argon2id (ou bcrypt), longueur minimale 12, liste noire des compromis, pas de complexité imposée ni d'expiration (NIST 800-63B). MFA : TOTP au minimum, passkeys/WebAuthn (résistant au phishing) pour les admins. SSO par un IdP unique (OIDC). Sessions courtes, refresh rotation, révocation centrale. Récupération : second facteur exigé, pas de question secrète, journalisée.
  20. OAuth 2.1 et OIDC : rôles, flux autorisés et supprimés, les trois jetons, les sept points de validation d'un JWT, BFF, Token Exchange, IDOR.
    Réponse attendue
    Rôles : resource owner, client, authorization server, resource server. Flux : authorization code + PKCE (tout client), client credentials (machine) ; supprimés : implicit, password. Jetons : access (audience, court), refresh (rotation), id_token (identité, jamais pour l'API). Validation JWT : signature, alg attendu, iss, aud, exp/nbf, typ, et les claims métier. BFF : le jeton reste côté serveur. Token Exchange : délégation nommée entre services. IDOR : contrôle d'accès par objet, toujours.
  21. ISO 27001, SOC 2, RGPD, NIS2, DORA, SecNumCloud : nature, cible, et comment tu produis les preuves.
    Réponse attendue
    ISO 27001 : système de management, certifiable, annexe A ; SOC 2 : rapport d'audit sur des critères (sécurité, disponibilité), pour les clients US ; RGPD : loi, données personnelles, obligations (base légale, minimisation, droits) ; NIS2 : directive, entités essentielles, gestion des risques et notification d'incident ; DORA : finance, résilience TIC, tests, prestataires ; SecNumCloud : qualification d'hébergeur. Preuves : scripts qui collectent depuis les systèmes, datés et signés, pas de captures manuelles.
  22. Les quinze questions DevSecOps de la section 42.5.
    Réponse attendue
    Se préparer avec les réponses courtes de la section : SAST/DAST/SCA, secrets, supply chain, Kubernetes, zero trust, conformité, incident de sécurité, priorisation des CVE, revue de code, DevSecOps sans ralentir.
  23. OWASP Top 10 : pour chaque catégorie, le motif vulnérable, la correction Spring et le test.
    Réponse attendue
    A01 contrôle d'accès : findById → findByIdAndOrg, test 403. A02 crypto : mot de passe en clair → Argon2id/Transit, test. A03 injection : concaténation → paramètres nommés, test Semgrep. A04 conception : pas de rate limit → Bucket4j, test 429. A05 configuration : Actuator exposé → exposure minimale, test 404. A06 composants : dépendance vulnérable → Renovate, SCA. A07 authentification : jeton non validé → resource server, tests 401. A08 intégrité : image non signée → Kyverno. A09 journalisation : pas d'événement → security_event, test. A10 SSRF : URL libre → allowlist, test 400.
  24. X.509 : les sept champs et leurs pièges ; validation et révocation ; les sept erreurs TLS fréquentes ; cérémonie de clés et HSM.
    Réponse attendue
    Champs : subject, issuer, validité (notBefore/notAfter), SAN (le seul nom vérifié), key usage / extended key usage, basic constraints (CA, pathlen), AKI/SKI (chaînage) ; pièges : CN sans SAN, EKU absent, pathlen. Validation : chaîne jusqu'à une racine de confiance, dates, nom, révocation (CRL, OCSP, stapling ; certificats courts en pratique). Erreurs TLS : hostname mismatch, chaîne incomplète, expiré, horloge décalée, CA inconnue, protocole/cipher, SNI absent. Cérémonie : hors ligne, témoins, journal signé, clé en HSM ou chiffrée et scellée.
