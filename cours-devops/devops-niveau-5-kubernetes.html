25.1 Pourquoi un orchestrateurBon à savoir

Docker Compose pilote un hôte. Dès qu'il faut plusieurs machines, le redémarrage automatique sur un autre nœud, la mise à l'échelle, les déploiements progressifs, la découverte de services et la gestion de la capacité, il faut un orchestrateur. Kubernetes (Google, 2014, CNCF) a gagné : toutes les offres cloud et sur site en proposent, et l'écosystème (Helm, ArgoCD, Prometheus, Istio, cert-manager) est devenu la plateforme standard.

Dans un cluster managé (EKS, AKS, GKE), le control plane est géré et invisible ; tu ne vois que les nœuds. Sur site : kubeadm, RKE2, k3s (léger, un binaire), OpenShift (Red Hat, opinionated, très présent dans les grands comptes français).

25.3 Le modèle déclaratif et la réconciliationPar cœur

Tu envoies à l'API un objet décrivant l'état désiré (spec). Un contrôleur observe en boucle l'état réel (status) et agit pour le rapprocher du désiré. Si un Pod meurt, le ReplicaSet en crée un autre ; si un nœud disparaît, le scheduler replace les Pods ailleurs. Rien n'est « lancé », tout est « déclaré ». C'est exactement le principe GitOps du niveau 3, appliqué au cluster lui-même.

Deployment (je veux 3 réplicas de l'image X)
   └── ReplicaSet (maintient 3 Pods identiques ; un nouveau ReplicaSet par version)
         └── Pod × 3 (un ou plusieurs conteneurs qui partagent réseau et volumes)
               └── conteneur(s)

Le piège numéro un : les images et les SCC

Avec restricted-v2, OpenShift lance le conteneur avec un UID aléatoire dans une plage propre au projet (par exemple 1000680000), et le groupe 0 (root). Une image qui écrit dans un répertoire appartenant à un utilisateur fixe, ou qui suppose USER 1000 avec des droits sur ses fichiers, échoue avec « permission denied ». Règles pour une image qui tourne partout, OpenShift compris :

# Dockerfile compatible UID arbitraire
FROM registry.access.redhat.com/ubi9/openjdk-21-runtime   # ou eclipse-temurin ; les images UBI sont certifiées Red Hat
WORKDIR /app
COPY --chown=1001:0 target/app.jar app.jar
RUN chgrp -R 0 /app && chmod -R g=u /app                  # le groupe root a les mêmes droits que le propriétaire
USER 1001                                                 # non root, numérique ; OpenShift remplacera l'UID, gardera le groupe 0
EXPOSE 8080                                               # jamais de port < 1024
ENTRYPOINT ["java", "-jar", "app.jar"]
# Test local de la contrainte : docker run --user 1000680000:0 --read-only --tmpfs /tmp image

Ne pas répondre à l'erreur par add-scc-to-user anyuid : c'est la version OpenShift de « désactiver la sécurité ». Autres points : pas de hostPath, pas de privileged, capabilities retirées, seccomp par défaut ; les charts Helm du marché qui fixent runAsUser ou fsGroup doivent être ajustés (valeurs vides pour laisser OpenShift choisir).

Ce qu'OpenShift apporte à ce parcours

  • Sortie de VMware (chapitre 7.4) : OpenShift Virtualization (KubeVirt) fait tourner des VM à côté des conteneurs sur le même cluster, avec le Migration Toolkit for Virtualization pour migrer depuis vSphere ; c'est l'argument majeur de Red Hat en 2025-2026.
  • Sécurité par défaut (niveau 7) : SCC, images UBI, Compliance Operator (profils CIS, ANSSI, PCI), Advanced Cluster Security (ex StackRox) pour la posture et l'exécution, chiffrement etcd, FIPS ; une bonne partie du chapitre 39 est livrée en standard.
  • Plateforme interne (niveau 8) : console développeur, catalogue, quotas par projet, Pipelines et GitOps intégrés : un IDP « en boîte », à compléter par Backstage (opérateur Red Hat Developer Hub, basé sur Backstage).
  • Multi-clusters (niveau 9) : Advanced Cluster Management pour la flotte, Quay comme registre d'entreprise, Ansible Automation Platform pour ce qui n'est pas Kubernetes.
En entretien — « Vous connaissez OpenShift ? » Réponse : c'est Kubernetes avec des opinions : Routes, projets, SCC et UID arbitraire, RHCOS et MachineConfig, opérateurs pour tout, monitoring et GitOps intégrés, mises à jour par canaux, abonnement par cœur. Le piège classique : les images qui supposent un UID fixe ; la mauvaise réponse : anyuid. Et le contexte 2026 : OpenShift Virtualization pour sortir de VMware. Cite oc get co et oc adm must-gather comme premiers réflexes.
Techno de nichePour sortir du lot — kwok (Kubernetes WithOut Kubelet)

Simule des milliers de nœuds et de Pods sans kubelet ni conteneur : le control plane est réel, les nœuds sont factices. Idéal pour tester le scheduling, les opérateurs, l'autoscaling et les politiques à l'échelle sur un poste.

Pourquoi ça différencie : Tester à 5 000 nœuds gratuitement, c'est un argument qui frappe quand on parle de plateformes à l'échelle.

À essayer en une heure : docker run --rm -it -p 8080:8080 registry.k8s.io/kwok/cluster:v0.6.0-k8s.v1.31.0, puis créer 1 000 nœuds et observer le comportement de tes politiques Kyverno et du scheduler.

En entretien — « Que se passe-t-il quand tu fais kubectl apply d'un Deployment ? » kubectl envoie l'objet à l'API ; authN, authZ (RBAC), admission (validation, mutation) ; écriture dans etcd ; le contrôleur Deployment crée un ReplicaSet ; le contrôleur ReplicaSet crée les Pods ; le scheduler leur assigne un nœud ; le kubelet du nœud demande au runtime de lancer les conteneurs et au CNI de connecter le Pod ; les Endpoints du Service se mettent à jour. Cette chaîne vaut un entretien à elle seule.
Exercice 25.1

Le control plane tombe entièrement pendant 10 minutes. Les applications qui tournaient continuent-elles de servir du trafic ? Que ne peut-on plus faire ?

Corrigé
Oui : les kubelets et les conteneurs continuent, kube-proxy garde ses règles. On ne peut plus déployer, mettre à l'échelle, replanifier un Pod mort, ni obtenir de nouveaux Endpoints ; les Pods qui crashent ne sont pas remplacés tant que le control plane est absent (le kubelet redémarre les conteneurs localement, mais un nœud perdu n'est pas compensé).
Exercice 25.2

Pourquoi dit-on que « Docker a été retiré de Kubernetes » alors que les images Docker continuent de fonctionner ?

Corrigé
Kubernetes parle au runtime via l'interface CRI ; Docker Engine ne l'implémentait pas directement (il fallait un adaptateur, dockershim, retiré en 1.24). containerd, qui est le composant que Docker utilise lui-même, implémente CRI. Les images sont au format OCI, indépendant de Docker.
Exercice 25.3

Un Service api renvoie « connection refused » depuis le front, alors que kubectl get pods montre trois Pods Running. Donne, dans l'ordre, les quatre commandes qui localisent le problème et ce que chacune peut révéler.

Corrigé
kubectl get endpointslices -l kubernetes.io/service-name=api : vide → sélecteur du Service qui ne correspond pas aux labels des Pods, ou Pods non prêts. kubectl describe svc api : targetPort contre le port du conteneur. kubectl get pods -o wide avec la colonne READY : 0/1 → readiness en échec, voir describe pod. kubectl debug netshoot : curl POD_IP:8080 direct puis curl api:80 → distingue application, Service et NetworkPolicy.
Exercice 25.4

Ton cluster kubeadm a un an ; ce matin kubectl répond x509: certificate has expired. Que fais-tu, et comment éviter que ça se reproduise ?

Corrigé
Sur le control plane : kubeadm certs check-expiration, kubeadm certs renew all, redémarrer les static pods (déplacer et remettre leurs manifests dans /etc/kubernetes/manifests) et le kubelet, régénérer le kubeconfig admin. Les applications ont continué de tourner ; seuls l'API et les contrôleurs étaient touchés. Prévention : alerte à 30 jours sur l'expiration (métriques de l'API server, cert-manager pour les certificats applicatifs), mise à jour du cluster au moins une fois par an (kubeadm renouvelle à chaque upgrade), ou cluster managé.

Une image qui fonctionne sur kind échoue sur OpenShift avec « permission denied » en écrivant dans /app/tmp. Trois causes possibles et la correction propre.

Corrigé

Exercice 25.6

Route edge, passthrough, reencrypt : où le TLS se termine dans chaque cas, et lequel choisis-tu pour une API qui exige mTLS interne ?

Corrigé
Edge : le routeur termine le TLS, HTTP en clair jusqu'au Pod (simple, certificat au routeur). Passthrough : le routeur ne déchiffre rien, le Pod termine le TLS (nécessaire pour mTLS de bout en bout ou SNI applicatif). Reencrypt : le routeur termine puis rechiffre vers le Pod avec un certificat interne (inspection au routeur, chiffrement partout). Pour du mTLS interne exigé : passthrough, ou reencrypt si c'est le mesh qui assure le mTLS derrière.

26.2 Les points qui font la différencePar cœur

  • Probes : startup protège les applications lentes (Java) ; liveness redémarre le conteneur s'il est bloqué (ne jamais y mettre une dépendance externe : une base en panne redémarrerait toute l'application en boucle) ; readiness retire le Pod du Service quand il ne peut pas servir (base injoignable, préchauffage). Spring Boot expose les deux nativement.
  • Ressources : requests = ce que le scheduler réserve ; limits = le plafond (mémoire : OOMKill ; CPU : throttling). Pratique courante : limite mémoire = requête mémoire (classe QoS Guaranteed pour la mémoire, prévisible), pas de limite CPU ou une limite large (le throttling CPU dégrade la latence des JVM sans bénéfice). Toujours des requests : sans elles, le scheduler ne peut rien garantir.
  • Arrêt propre : SIGTERM → l'application arrête d'accepter, finit les requêtes, ferme ; preStop compense le délai de propagation du retrait des Endpoints ; terminationGracePeriodSeconds puis SIGKILL.
  • Sécurité : non root, lecture seule, pas de capabilities, seccomp, pas de token de compte de service monté si inutile. C'est le profil restricted des Pod Security Standards (niveau 7).
  • Répartition : topologySpreadConstraints sur nœud et zone ; PodDisruptionBudget pour qu'une maintenance de nœud ne retire jamais plus d'un Pod à la fois.

26.6 Jobs, CronJobs, DaemonSetsBon à savoir

Job : un Pod jusqu'à succès (migrations de schéma, import), avec backoffLimit et ttlSecondsAfterFinished. CronJob : planification (0 2 * * *), concurrencyPolicy: Forbid, startingDeadlineSeconds. En entretien — « Différence entre liveness et readiness ? » et « pourquoi ne pas mettre de limite CPU ? » sont les deux questions les plus posées. Liveness : « suis-je vivant ? » → redémarrage, sans dépendance externe. Readiness : « puis-je servir ? » → retrait du trafic. CPU : la limite provoque du throttling CFS qui augmente la latence même sous la limite moyenne ; les requests suffisent à partager équitablement ; la limite mémoire, elle, est obligatoire.
Exercice 26.1

Pendant chaque rolling update, les utilisateurs voient quelques erreurs 502 pendant une à deux secondes. Le Deployment a readiness et liveness correctes. Cause et correction ?

Corrigé
À l'arrêt d'un Pod, le retrait de ses Endpoints et le SIGTERM sont envoyés en parallèle ; l'ingress peut encore router vers un Pod déjà en train de s'arrêter. Ajouter preStop: sleep 5 (le Pod reste vivant mais est retiré des Endpoints), et vérifier que l'application arrête d'accepter les connexions proprement (server.shutdown=graceful, terminationGracePeriodSeconds suffisant).

Un Pod est en Pending depuis 5 minutes. Les quatre causes les plus fréquentes et la commande qui les révèle.

Corrigé
kubectl describe pod, section Events : « Insufficient cpu/memory » (requests trop grandes ou cluster plein), « didn't match node selector/affinity » ou taint non tolérée, volume PersistentVolumeClaim non lié (« pod has unbound immediate PersistentVolumeClaims »), quota du namespace dépassé (kubectl describe quota).

Exercice 26.4

Un Job de migration doit tourner avec un sidecar Vault Agent qui fournit les identifiants de base. Avec un sidecar classique, le Job ne se termine jamais. Pourquoi, et quelle est la solution moderne ?

Corrigé
Le Job attend que tous ses conteneurs se terminent ; le sidecar tourne indéfiniment. 27.1 Le stockagePar cœur

Pod ──volumeMount──► PersistentVolumeClaim (demande : 20Gi, ReadWriteOnce, classe gp3)
                          │ liaison (binding)
                     PersistentVolume (le disque réel : EBS, disque Azure, NFS, Ceph...)
                          │ créé dynamiquement par
                     StorageClass (provisioner CSI, paramètres, politique de rétention, expansion)
  • Modes d'accès : ReadWriteOnce (un nœud : disques bloc cloud), ReadWriteMany (plusieurs nœuds : NFS, EFS, CephFS), ReadWriteOncePod.
  • CSI (Container Storage Interface) : le standard des pilotes de stockage ; chaque cloud et chaque baie en fournit un. Snapshots de volumes via VolumeSnapshot.
  • reclaimPolicy : Delete (le disque part avec le PVC : dangereux pour une base) ou Retain.
  • Volumes éphémères : emptyDir (durée de vie du Pod, peut être en mémoire), configMap, secret, projected, downwardAPI.
  • Un volume RWO est attaché à un nœud : un Pod ne peut pas migrer plus vite que le détachement/rattachement (30 s à plusieurs minutes dans le cloud). C'est la première raison pour laquelle les applications à état sont plus délicates.

27.2 StatefulSetPar cœur

Un Deployment produit des Pods interchangeables aux noms aléatoires. Un StatefulSet donne à chacun une identité stable (db-0, db-1), un volume propre qui le suit (volumeClaimTemplates), un DNS stable via un Service headless (db-0.db.crisisshield.svc), et un ordre de création/arrêt. Nécessaire pour les bases, Kafka, Elasticsearch, tout ce qui a des rôles (primaire/réplica) et un état local.

apiVersion: apps/v1
kind: StatefulSet
metadata: {name: db, namespace: crisisshield}
spec:
  serviceName: db
  replicas: 2
  selector: {matchLabels: {app.kubernetes.io/name: db}}
  template:
    metadata: {labels: {app.kubernetes.io/name: db}}
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          volumeMounts: [{name: data, mountPath: /var/lib/postgresql/data}]
          resources: {requests: {cpu: 500m, memory: 1Gi}, limits: {memory: 1Gi}}
  volumeClaimTemplates:
    - metadata: {name: data}
      spec: {accessModes: [ReadWriteOnce], storageClassName: standard, resources: {requests: {storage: 10Gi}}}

Ce StatefulSet ne fait pas de réplication PostgreSQL : deux Pods, deux bases indépendantes. Mettre en place la réplication, la bascule, les sauvegardes, c'est précisément le travail d'un opérateur.

27.3 Le pattern Operator et les CRDImportant

Kubernetes est extensible : une CustomResourceDefinition ajoute un type d'objet (kind: Cluster du groupe postgresql.cnpg.io), et un opérateur est un contrôleur qui réconcilie ces objets en encodant le savoir-faire d'exploitation : créer les Pods dans le bon ordre, configurer la réplication, promouvoir un réplica en cas de panne, sauvegarder vers S3, restaurer à un instant précis, mettre à jour la version mineure sans coupure.

# CloudNativePG : une base PostgreSQL haute disponibilité en 15 lignes
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata: {name: db, namespace: crisisshield}
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:16.4
  storage: {size: 20Gi, storageClass: gp3}
  postgresql:
    parameters: {max_connections: "200", shared_buffers: 256MB}
  bootstrap:
    initdb: {database: crisis, owner: crisis}     # le secret db-app est généré
  backup:
    barmanObjectStore:
      destinationPath: s3://crisisshield-backups/db
      s3Credentials: {accessKeyId: {name: backup-creds, key: id}, secretAccessKey: {name: backup-creds, key: key}}
      wal: {compression: gzip}
    retentionPolicy: 30d
---
apiVersion: postgresql.cnpg.io/v1
kind: ScheduledBackup
metadata: {name: db-daily, namespace: crisisshield}
spec: {schedule: "0 0 2 * * *", cluster: {name: db}}

L'opérateur crée les Services db-rw (primaire), db-ro (réplicas), db-r (tous). Une bascule prend quelques secondes. Autres opérateurs de référence : Strimzi (Kafka), Prometheus Operator, cert-manager, ECK (Elasticsearch), Redis Operator, Keycloak Operator. Un StatefulSet à 3 réplicas est supprimé par erreur. Les données sont-elles perdues ? Et si c'était le namespace ?

Corrigé

28.1 Helm : le gestionnaire de paquetsImportant

Un chart = des templates de manifests + un fichier values.yaml de paramètres + des métadonnées. Une release = un chart installé avec des valeurs dans un namespace, versionnée (Helm garde l'historique dans des Secrets et permet le rollback). Les charts tiers (ingress-nginx, cert-manager, Prometheus, ArgoCD, Keycloak...) évitent de réécrire des centaines de lignes.

helm repo add bitnami https://charts.bitnami.com/bitnami ; helm repo update
helm search repo postgresql ; helm show values bitnami/postgresql > values-default.yaml
helm install db bitnami/postgresql -n crisisshield --create-namespace -f values.yaml --version 15.5.20
helm upgrade --install db bitnami/postgresql -n crisisshield -f values.yaml --atomic --timeout 5m
helm list -A ; helm history db -n crisisshield ; helm rollback db 2 -n crisisshield
helm template db bitnami/postgresql -f values.yaml > rendered.yaml      # voir ce qui sera appliqué
helm diff upgrade db bitnami/postgresql -f values.yaml                  # plugin helm-diff : indispensable
helm uninstall db -n crisisshield
# Charts OCI (registres d'images) : helm install x oci://ghcr.io/org/charts/x --version 1.2.3

Règles : toujours épingler --version, toujours helm diff avant upgrade, --atomic pour rollback automatique en cas d'échec, lire les values par défaut (elles activent parfois des choses que tu ne veux pas), et scanner les manifests rendus (Trivy config, Kyverno CLI).

29.1 ArgoCDPar cœur

ArgoCD tourne dans le cluster, observe un dépôt Git (manifests, Kustomize, Helm, Jsonnet), compare avec l'état du cluster, affiche Synced/OutOfSync et Healthy/Degraded, et synchronise (manuellement ou automatiquement). Interface web très appréciée en mission pour visualiser l'état d'une application.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: crisisshield-prod
  namespace: argocd
  finalizers: [resources-finalizer.argocd.argoproj.io]   # supprimer l'Application supprime ses ressources
spec:
  project: crisisshield
  source:
    repoURL: https://gitlab.example/crisisshield/config.git
    targetRevision: main
    path: envs/prod                     # kustomize détecté automatiquement
  destination: {server: https://kubernetes.default.svc, namespace: crisisshield}
  syncPolicy:
    automated: {prune: true, selfHeal: true}     # supprime ce qui n'est plus dans Git ; corrige la dérive
    syncOptions: [CreateNamespace=true, ServerSideApply=true]
    retry: {limit: 3, backoff: {duration: 30s, factor: 2}}
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers: [/spec/replicas]     # géré par le HPA, pas par Git
---
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata: {name: crisisshield, namespace: argocd}
spec:
  sourceRepos: [https://gitlab.example/crisisshield/*]
  destinations: [{server: https://kubernetes.default.svc, namespace: crisisshield*}]
  clusterResourceWhitelist: []          # aucune ressource cluster (pas de ClusterRole, pas de CRD)
  namespaceResourceBlacklist: [{group: "", kind: ResourceQuota}]
  roles:
    - name: developers
      policies: ["p, proj:crisisshield:developers, applications, sync, crisisshield/*, allow"]
      groups: [crisisshield-developers]
  • AppProject : le périmètre de sécurité. Sans lui, une Application peut déployer n'importe quoi n'importe où.

  • App of Apps : une Application racine qui déploie d'autres Applications ; ou mieux, ApplicationSet avec des générateurs (liste d'environnements, répertoires Git, clusters) pour engendrer N applications à partir d'un modèle.
  • Notifications vers Slack/Teams ; Image Updater pour écrire automatiquement le nouveau tag en staging ; Argo Rollouts pour canary et blue/green analysés par métriques (chapitre 31 et niveau 6).
  • Sécurité d'ArgoCD lui-même : SSO (OIDC vers Keycloak, Entra ID), RBAC par projet, pas de compte admin local, accès Git en lecture seule par deploy token, interface non exposée publiquement.

Service mesh

En 30 secondes

  2. Sidecar hier, ambient et eBPF demain ; Istio, Linkerd, Cilium.
  3. Pas de mesh pour trois services ; oui quand mTLS partout, dizaines de services polyglottes, canary fin.
À la fin de ce chapitre, tu sauras
  • Expliquer ce qu'un mesh apporte (mTLS, observabilité, trafic) et ce qu'il coûte
  • Comparer Istio, Linkerd et Cilium mesh
  • Décider si un projet en a besoin

30.1 Le problème que le mesh résoutBon à savoir

Avec des dizaines de microservices, chacun doit : chiffrer ses appels (mTLS), vérifier l'identité de l'appelant, retenter, respecter des timeouts, couper le circuit quand un service est en panne, exposer des métriques de trafic, propager les traces. Coder cela dans chaque service (Resilience4j, Spring Cloud) fonctionne mais dépend de chaque langage et de chaque équipe. Le mesh sort ces fonctions de l'application et les place dans l'infrastructure réseau.

30.2 Comment ça marcheBon à savoir

  • Sidecar (modèle historique) : un proxy (Envoy pour Istio, un micro-proxy Rust pour Linkerd) injecté dans chaque Pod, intercepte tout le trafic entrant et sortant. Coût : mémoire et CPU par Pod, latence de quelques ms, complexité au démarrage/arrêt.
  • Ambient / sans sidecar : Istio ambient (un proxy par nœud pour L4 et mTLS, un « waypoint » optionnel pour L7) et Cilium (eBPF dans le noyau) suppriment le sidecar. C'est la direction du marché.
  • Control plane (istiod) distribue les certificats (rotation automatique, identité SPIFFE), la configuration de routage et les politiques.
# Istio : mTLS strict sur le namespace, et une politique d'autorisation
apiVersion: security.istio.io/v1

apiVersion: security.istio.io/v1
kind: AuthorizationPolicy

---
# Routage pondéré (canary) et résilience

kind: VirtualService
metadata: {name: api, namespace: crisisshield}

  hosts: [api]

      retries: {attempts: 3, perTryTimeout: 2s, retryOn: "5xx,reset"}

  host: api

    outlierDetection: {consecutive5xxErrors: 5, interval: 30s, baseEjectionTime: 60s}   # circuit breaker
    connectionPool: {tcp: {maxConnections: 100}}

30.3 Ce qu'on obtientBon à savoir

  • Sécurité : mTLS partout sans toucher au code, identité par ServiceAccount (SPIFFE), politiques d'autorisation L4/L7 (« seul l'API peut appeler la base », « seul GET sur /public »). C'est le socle réseau du zero trust (niveau 7).
  • Observabilité : métriques RED (requêtes, erreurs, durée) pour chaque service sans instrumentation, traces (si l'application propage les en-têtes), topologie visuelle avec Kiali.
  • Trafic : canary pondéré, mirroring, injection de fautes (chaos), retries, timeouts, circuit breaking, rate limiting, egress contrôlé.

Un mesh n'est pas nécessaire pour une application à trois services. Il devient pertinent quand : mTLS exigé partout (conformité), dizaines de services polyglottes, besoin de canary fin sans modifier les apps, observabilité réseau uniforme. Techno de nichePour sortir du lot — Kmesh

Un service mesh eBPF sans sidecar ni proxy par nœud pour le trafic L4 (compatible avec le control plane Istio), avec une latence quasi nulle ; à connaître aux côtés d'Istio ambient et de Cilium, en surveillant sa maturité.

Pourquoi ça différencie : Comprendre le mouvement « sans sidecar » et ses trois implémentations te place dans les discussions d'architecture réseau avancées.

À essayer en une heure : Helm Kmesh sur un cluster kind avec un noyau récent ; compare la latence p99 de CrisisShield avec Istio sidecar, Istio ambient, Cilium et Kmesh dans un tableau.

En entretien — « Vous utiliseriez un service mesh ? » Réponse : d'abord ce qu'il apporte (mTLS, autorisation par identité, résilience, métriques sans code), puis le coût (complexité, ressources), puis le critère (nombre de services, exigence de chiffrement, équipe capable de l'opérer), et la tendance sans sidecar. Le lien avec ton profil : le mesh est l'outil qui implémente le zero trust réseau ; sache le dire.
Exercice 30.1

Avec mTLS STRICT activé, un Job de migration Flyway lancé par Helm échoue à joindre la base. Pourquoi ?

Corrigé
Le Job n'a pas de sidecar (souvent exclu, ou le sidecar n'est pas prêt quand le conteneur démarre, ou le Job se termine sans arrêter le sidecar). En mode sidecar : annoter pour l'injection et gérer la fin (holdApplicationUntilProxyStarts, appel à /quitquitquit), ou exclure le Job du mTLS strict avec une PeerAuthentication en PERMISSIVE ciblée. En mode ambient, le problème disparaît.
Exercice 30.2

Un mesh fournit des retries automatiques. Quel risque pour une API de création de paiement, et comment le maîtriser ?

Corrigé
Un retry sur un POST non idempotent peut créer deux paiements. Limiter les retries aux méthodes idempotentes (retryOn ciblé, pas sur les POST), ou rendre l'API idempotente avec une clé d'idempotence, ce qui est de toute façon une bonne pratique.

31.1 Mise à l'échelle des PodsPar cœur

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: api, namespace: crisisshield}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: api}
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: {name: cpu, target: {type: Utilization, averageUtilization: 70}}   # % des requests
    - type: Pods
      pods: {metric: {name: http_requests_per_second}, target: {type: AverageValue, averageValue: "200"}}
  behavior:
    scaleUp:   {stabilizationWindowSeconds: 0,   policies: [{type: Percent, value: 100, periodSeconds: 60}]}
    scaleDown: {stabilizationWindowSeconds: 300, policies: [{type: Pods, value: 2, periodSeconds: 60}]}
  • HPA : ajuste les réplicas sur le CPU/mémoire (metrics-server) ou des métriques custom (Prometheus Adapter : requêtes par seconde, longueur de file). Le CPU en % des requests : d'où l'importance de requests réalistes. Montée rapide, descente lente.
  • VPA : ajuste les requests/limits d'un Pod à partir de l'usage observé ; en mode Off, il ne fait que recommander : parfait pour calibrer. Ne pas combiner HPA et VPA sur la même métrique.
  • KEDA : mise à l'échelle événementielle, y compris à zéro : longueur d'une file SQS/Kafka, requêtes HTTP, cron, métrique Prometheus. Indispensable pour les workers et les consommateurs Kafka (un Pod par partition en charge).
  • Une JVM ne réagit pas bien à des variations rapides (préchauffage) : réplicas minimum suffisants, startup probe, et éviter de scaler sur la mémoire (une JVM garde son tas).

31.2 Mise à l'échelle des nœudsImportant

  • Cluster Autoscaler : ajoute un nœud quand des Pods sont Pending faute de ressources, retire un nœud sous-utilisé après en avoir déplacé les Pods. Fonctionne par groupes de nœuds (ASG) homogènes.
  • Karpenter (AWS, aussi Azure) : provisionne directement l'instance la plus adaptée aux Pods en attente (taille, famille, Spot/à la demande, architecture), sans groupes prédéfinis, en secondes ; consolide en continu pour réduire le coût. Devenu le standard sur EKS.
  • Modes sans nœuds : EKS Auto Mode, GKE Autopilot, AKS Automatic : le fournisseur gère les nœuds, tu payes les Pods.
  • Impact FinOps : un cluster tourne rarement au-delà de 50 % d'utilisation ; Karpenter + Spot + consolidation + VPA pour calibrer sont les quatre leviers.
# Karpenter : un NodePool qui préfère Spot et ARM, limité en taille
apiVersion: karpenter.sh/v1
kind: NodePool
metadata: {name: default}
spec:
  template:
    spec:
      requirements:
        - {key: karpenter.sh/capacity-type, operator: In, values: [spot, on-demand]}
        - {key: kubernetes.io/arch, operator: In, values: [arm64, amd64]}
        - {key: karpenter.k8s.aws/instance-category, operator: In, values: [c, m, r]}
      nodeClassRef: {group: karpenter.k8s.aws, kind: EC2NodeClass, name: default}
      expireAfter: 720h
  limits: {cpu: "200", memory: 800Gi}
  disruption: {consolidationPolicy: WhenEmptyOrUnderutilized, consolidateAfter: 1m}

Le HPA oscille : 3 → 8 → 3 → 8 réplicas toutes les cinq minutes. Causes et corrections ?
