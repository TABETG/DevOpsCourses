Correction type — Travail pratique 39

Cluster durci et prouvé

Une solution complète, étape par étape : ce qu'il faut produire, la commande ou le fichier clé, le résultat qui prouve que ça marche, et les pièges. Ta solution peut différer ; ce qui compte, c'est que chaque preuve soit là.

Étapes de la correction
  1. Score initial, audit logging de l'API, Trivy Operator
  2. Pod Security Admission : warn, corriger, enforce
  3. Kyverno en HA : huit politiques, testées avant push
  4. Comparer : Gatekeeper (Rego) et ValidatingAdmissionPolicy (CEL)
  5. Falco : trois règles déclenchées, Tetragon en bonus
  6. Profil seccomp enregistré, appliqué, vérifié
  7. Score après, et tableau de bord
  8. L'attaque : quatre tentatives, quatre échecs visibles
  9. Ce que le relecteur doit trouver
  10. Questions de relecteur
Énoncé
  1. Lance kube-bench et kubescape sur ton cluster kind : note le score initial. Active l'audit logging de l'API (kind : kubeadmConfigPatches avec une policy d'audit) et collecte les logs dans Loki. Lance Trivy Operator.
  2. PSA : warn + audit restricted sur tous les namespaces applicatifs, corrige les violations remontées dans les logs d'audit, passe en enforce. Namespaces d'infrastructure avec profil justifié dans un fichier docs/security/psa-exceptions.md.
  3. Kyverno (chart, HA) avec au moins huit politiques : registre interne, pas de latest, digest obligatoire en prod, requests/limits obligatoires, labels obligatoires, pas de hostPath/privileged, mutation seccomp et automountServiceAccountToken: false, génération de NetworkPolicy default-deny par namespace, vérification de signature (préparée, activée au TP 40). Tests avec kyverno test dans la CI et kyverno apply sur les manifests rendus par Kustomize/Helm avant push.
  4. Réécris trois de ces politiques en OPA Gatekeeper (Rego) et une en ValidatingAdmissionPolicy (CEL) pour comparer.
  5. Falco avec Falcosidekick vers Loki et Slack (webhook de test) ; trois règles personnalisées (shell en prod, lecture de secrets montés par un processus inattendu, connexion sortante hors du mesh). Déclenche chacune, capture l'alerte. Bonus : Tetragon avec une politique qui tue un processus qui lit /etc/shadow.
  6. Security Profiles Operator : enregistre un profil seccomp de l'API en observation, applique-le, vérifie qu'un appel système hors profil est refusé.
  7. Rejoue kube-bench et kubescape ; compare les scores ; dashboard Grafana des rapports Trivy Operator (CVE par workload) et du score dans le temps.
  8. Attaque : depuis un Pod compromis (netshoot dans le namespace), tente d'atteindre l'API Kubernetes, l'IMDS de LocalStack, un autre namespace, le socket containerd. Chaque tentative doit échouer et être visible (audit, Falco, NetworkPolicy). Rédige le rapport de la tentative.
Étape 1

Score initial, audit logging de l'API, Trivy Operator

docker run --rm -v "$HOME/.kube:/root/.kube" --network host aquasec/kube-bench run --targets master,node,policies --benchmark cis-1.9 | tail -3
docker run --rm -v "$HOME/.kube:/root/.kube" --network host quay.io/kubescape/kubescape scan framework nsa,mitre --format pretty | grep -E 'Risk score|Failed'
cat > infra/kind/audit-policy.yaml <<'EOF'
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  - level: RequestResponse
    resources: [{ group: "", resources: [secrets, serviceaccounts/token] }]
  - level: Request
    verbs: [create, update, patch, delete]
  - level: Metadata
    omitStages: [RequestReceived]
EOF
# kind-config.yaml : kubeadmConfigPatches → apiServer.extraArgs audit-policy-file, audit-log-path=/var/log/kubernetes/audit.log, audit-log-maxage=7 ; extraVolumes ; extraMounts du fichier de policy
k kind create cluster --name crisis --config kind-config.yaml   # recréation du cluster
# Alloy : un second flux qui lit /var/log/kubernetes/audit.log sur le nœud control-plane → Loki label job="kube-audit"
k helm install trivy-operator aqua/trivy-operator -n trivy-system --create-namespace --version 0.24.1 --set trivy.ignoreUnfixed=true
kube-bench : 48 PASS, 21 FAIL, 40 WARN kubescape : Risk score 41 %, 37 failed controls Loki : {job="kube-audit"} | json | objectRef_resource="secrets" → chaque lecture de secret, avec l'utilisateur et l'IP trivy-operator : vulnerabilityreports créés pour 14 workloads
  • Le score initial est la ligne de départ, pas une honte : kind est un cluster de développement. On mesure, on corrige, on remesure.
  • Le journal d'audit est la seule source qui dit « qui a lu ce secret » : sans lui, le TP 42 n'a aucune preuve d'accès.
Étape 2

Pod Security Admission : warn, corriger, enforce

k kubectl label ns crisis crisis-dev observability pod-security.kubernetes.io/warn=restricted pod-security.kubernetes.io/audit=restricted --overwrite
# Loki : {job="kube-audit"} | json | annotations_pod_security_kubernetes_io_audit_violations!="" → liste des violations
k kubectl rollout restart deploy -n crisis 2>&1 | grep -i warning
# corrections : worker sans seccompProfile → ajouté ; job de migration Flyway en root → runAsUser 10001 ; Grafana (chart) → values securityContext
k kubectl label ns crisis crisis-dev pod-security.kubernetes.io/enforce=restricted --overwrite
# docs/security/psa-exceptions.md : kube-system, istio-system, falco, trivy-system, longhorn-system → privileged ; justification par composant (CNI, ztunnel, eBPF, CSI) et ce qui compense (namespace dédié, RBAC, Falco)
Warning: would violate PodSecurity "restricted:latest": seccompProfile (pod or container "worker" must set securityContext.seccompProfile.type…) → corrigé enforce=restricted sur crisis : 0 Pod rejeté au redéploiement
  • L'ordre warn → audit → enforce est la seule façon de ne rien casser : les violations sont vues avant d'être refusées.
  • Une exception PSA est un document, avec le composant, la raison et la compensation : c'est ce qu'un auditeur demandera au TP 42.
Étape 3

Kyverno en HA : huit politiques, testées avant push

k helm install kyverno kyverno/kyverno -n kyverno --create-namespace --version 3.3.2 --set admissionController.replicas=3
# k8s/policies/kyverno/ — un fichier par politique, validationFailureAction: Enforce (Audit d'abord une semaine)
# 01-registry.yaml     validate : image =~ "localhost:5000/*|harbor.crisis.local/*"
# 02-no-latest.yaml    validate : pas de tag latest ni d'image sans tag
# 03-digest-prod.yaml  validate (namespaces crisis-prod) : image contient "@sha256:"
# 04-resources.yaml    validate : requests.cpu, requests.memory, limits.memory présents
# 05-labels.yaml       validate : app.kubernetes.io/name, team, cost-center présents
# 06-no-host.yaml      validate : pas de hostPath, hostNetwork, hostPID, privileged
# 07-mutate-hardening.yaml  mutate : seccompProfile RuntimeDefault et automountServiceAccountToken: false si absents
# 08-generate-netpol.yaml   generate : NetworkPolicy default-deny dans chaque nouveau namespace (synchronize: true)
# 09-verify-image.yaml      verifyImages (Audit pour l'instant, Enforce au TP 40)
cat > k8s/policies/kyverno/tests/kyverno-test.yaml <<'EOF'
apiVersion: cli.kyverno.io/v1alpha1
kind: Test
metadata: { name: crisisshield }
policies: [../01-registry.yaml, ../02-no-latest.yaml, ../04-resources.yaml, ../06-no-host.yaml]
resources: [resources.yaml]
results:
  - { policy: registre-interne, rule: image-interne, resource: pod-docker-hub, kind: Pod, result: fail }
  - { policy: registre-interne, rule: image-interne, resource: pod-ok, kind: Pod, result: pass }
  - { policy: pas-de-latest, rule: tag-explicite, resource: pod-latest, kind: Pod, result: fail }
  - { policy: ressources-obligatoires, rule: requests, resource: pod-sans-requests, kind: Pod, result: fail }
  - { policy: pas-de-hote, rule: hostpath, resource: pod-socket, kind: Pod, result: fail }
EOF
docker run --rm -v "$PWD/k8s/policies/kyverno:/p" ghcr.io/kyverno/kyverno-cli:v1.13.0 test /p/tests
# CI, sur les manifests rendus : kubectl kustomize overlays/prod | kyverno apply k8s/policies/kyverno/ --resource - --audit-warn
kyverno test : 5 passed, 0 failed kyverno apply (rendu prod) : pass: 41, fail: 0, warn: 0, error: 0, skip: 6 k kubectl run test --image=nginx -n crisis → Error: admission webhook denied: image nginx n'est pas dans le registre interne (CS-K8S-01)
  • La politique tourne trois fois : dans les tests unitaires, sur le rendu avant push, puis à l'admission. La troisième ne devrait jamais rien refuser qui ait passé les deux premières.
  • Le message d'erreur cite l'identifiant du standard (CS-K8S-01) : c'est ce que le dépôt de gouvernance du TP 51 attend.
Étape 4

Comparer : Gatekeeper (Rego) et ValidatingAdmissionPolicy (CEL)

# k8s/policies/gatekeeper/template-no-latest.yaml
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata: { name: k8snolatest }
spec:
  crd: { spec: { names: { kind: K8sNoLatest } } }
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8snolatest
        violation[{"msg": msg}] {
          c := input.review.object.spec.containers[_]
          endswith(c.image, ":latest")
          msg := sprintf("image %v : tag latest interdit (CS-K8S-02)", [c.image])
        }
# k8s/policies/vap/resources.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: { name: requests-obligatoires }
spec:
  failurePolicy: Fail
  matchConstraints: { resourceRules: [{ apiGroups: ["apps"], apiVersions: ["v1"], operations: [CREATE, UPDATE], resources: [deployments] }] }
  validations:
    - expression: "object.spec.template.spec.containers.all(c, has(c.resources) && has(c.resources.requests) && has(c.resources.requests.cpu))"
      message: "chaque conteneur doit déclarer requests.cpu (CS-K8S-04)"
# tp39.md : tableau — expressivité, tests, mutation, génération, dépendance (VAP : rien à installer), messages, courbe d'apprentissage
les trois refusent le même Deployment ; VAP répond en < 1 ms sans webhook ; Gatekeeper demande un ConstraintTemplate + Constraint ; Kyverno reste le seul à muter et générer
  • VAP (natif depuis 1.30) couvre la validation simple sans composant à exploiter ; Kyverno reste nécessaire pour muter, générer et vérifier les signatures.
  • En entretien : Kyverno = YAML et fonctions natives, Gatekeeper = Rego (puissant, verbeux), VAP = CEL intégré à l'API server.
Étape 5

Falco : trois règles déclenchées, Tetragon en bonus

k helm install falco falcosecurity/falco -n falco --create-namespace --version 4.11.0 --set tty=true --set falcosidekick.enabled=true --set falcosidekick.config.loki.hostport=http://loki-gateway.observability:80 --set falcosidekick.config.slack.webhookurl=$SLACK_TEST -f infra/falco/rules-values.yaml
# infra/falco/rules-values.yaml (customRules) :
- rule: Shell in prod container
  desc: shell interactif dans un conteneur du namespace crisis-prod
  condition: spawned_process and container and k8s.ns.name = "crisis-prod" and proc.name in (sh, bash, ash, zsh)
  output: "Shell en prod (user=%user.name pod=%k8s.pod.name cmd=%proc.cmdline)"
  priority: CRITICAL
- rule: Unexpected read of mounted secret
  condition: open_read and fd.name startswith /var/run/secrets/ and not proc.name in (java, quarkus-run, vault-agent)
  output: "Lecture de secret par %proc.name (pod=%k8s.pod.name file=%fd.name)"
  priority: WARNING
- rule: Outbound connection outside mesh
  condition: outbound and container and k8s.ns.name = "crisis" and not fd.sip in (10.96.0.0/12) and not fd.sport in (15008)
  output: "Connexion sortante hors mesh (pod=%k8s.pod.name dst=%fd.rip:%fd.rport)"
  priority: WARNING
k kubectl exec -n crisis-prod deploy/api -- sh -c 'cat /var/run/secrets/kubernetes.io/serviceaccount/token > /dev/null ; wget -qO- --timeout=2 http://1.1.1.1'
# bonus Tetragon : TracingPolicy kprobe sys_openat sur /etc/shadow, action Sigkill ; kubectl exec … cat /etc/shadow → Killed
Slack (canal de test) : 3 alertes en moins de 5 s — CRITICAL Shell en prod, WARNING Lecture de secret par cat, WARNING Connexion sortante hors mesh dst=1.1.1.1:80 Loki {job="falco"} | json | priority="Critical" : 1 ligne Tetragon : « cat /etc/shadow » tué, événement process_kprobe dans le journal
  • Falco détecte à l'exécution ce que l'admission ne peut pas voir : un attaquant déjà dans un Pod. Kyverno et Falco sont complémentaires, pas concurrents.
  • Une règle Falco se déclenche volontairement avant d'être mise en production : sinon on ne sait ni si elle fonctionne ni combien de bruit elle fait.
Étape 6

Profil seccomp enregistré, appliqué, vérifié

k kubectl apply -f https://raw.githubusercontent.com/kubernetes-sigs/security-profiles-operator/v0.8.5/deploy/operator.yaml
k kubectl apply -f - <<'EOF'
apiVersion: security-profiles-operator.x-k8s.io/v1alpha1
kind: ProfileRecording
metadata: { name: api, namespace: crisis }
spec: { kind: SeccompProfile, recorder: bpf, podSelector: { matchLabels: { app: api } } }
EOF
# rejouer k6 (toutes les routes) pendant 10 min pour couvrir les appels système, puis supprimer le ProfileRecording → SeccompProfile api-… créé
k kubectl get seccompprofile -n crisis -o jsonpath='{.items[0].spec.syscalls[0].names}' | jq length
# Deployment : securityContext.seccompProfile: { type: Localhost, localhostProfile: operator/crisis/api-api.json }
k kubectl exec -n crisis deploy/api -- sh -c 'mount -t tmpfs none /mnt' ; echo "code $?"
97 (97 appels système autorisés, contre ~300 pour RuntimeDefault) sh: mount: Operation not permitted code 1 (l'appel mount n'est pas dans le profil)
  • Le profil enregistré est spécifique à l'application : un appel système jamais vu pendant l'enregistrement est refusé, ce qui casse aussi une fonctionnalité non testée. D'où le k6 complet avant de figer.
  • RuntimeDefault est le minimum PSA restricted ; un profil enregistré est le niveau au-dessus, à réserver aux services exposés.

Score après, et tableau de bord

docker run --rm -v "$HOME/.kube:/root/.kube" --network host aquasec/kube-bench run --targets master,node,policies --benchmark cis-1.9 | tail -3
docker run --rm -v "$HOME/.kube:/root/.kube" --network host quay.io/kubescape/kubescape scan framework nsa,mitre --format pretty | grep 'Risk score'
# Grafana : source Prometheus, métriques trivy_image_vulnerabilities{severity} par workload (exportées par trivy-operator) ; kubescape en mode opérateur (helm kubescape-operator) expose un score dans le temps
# tp39.md : tableau avant/après par contrôle corrigé (audit log, PSA, encryption at rest des secrets via kind patch, anonymous-auth=false, profiling=false, ...)
kube-bench : 71 PASS, 6 FAIL (les 6 restants sont propres à kind : kubelet en conteneur), 12 WARN kubescape : Risk score 11 % trivy : 3 workloads avec CRITICAL (images tierces : Keycloak, Grafana, MinIO → mises à jour planifiées par Renovate)
  • Le delta est le livrable : 41 % → 11 %, avec la liste de ce qui a changé et ce qui reste (justifié).
  • Les CVE restantes sont dans des images tierces : la réponse est la mise à jour (TP 14), pas une exception.
Étape 8

L'attaque : quatre tentatives, quatre échecs visibles

k kubectl run pwned -n crisis --image=nicolaka/netshoot --labels app=pwned -- sleep 3600
k kubectl exec -n crisis pwned -- sh -c '
echo "== API Kubernetes" ; curl -sk --max-time 3 https://kubernetes.default.svc/api/v1/namespaces/crisis/secrets ; echo
echo "== IMDS LocalStack" ; curl -s --max-time 3 http://169.254.169.254/latest/meta-data/ ; echo "code $?"
echo "== autre namespace" ; curl -s --max-time 3 http://grafana.observability:3000 ; echo "code $?"
echo "== socket containerd" ; ls -la /run/containerd/containerd.sock 2>&1'
# preuves : audit (401 sur secrets, pas de token monté), NetworkPolicy default-deny egress (timeouts), Falco (connexion sortante hors mesh), aucun hostPath (Kyverno l'aurait refusé)
# docs/security/rapport-attaque-tp39.md : objectif, chaque tentative, contrôle qui a bloqué, où c'est visible, ce qui manquerait sans lui
== API Kubernetes : {"kind":"Status","code":401} (pas de token : automountServiceAccountToken false, muté par Kyverno) == IMDS : code 28 (timeout : egress refusé par la NetworkPolicy) == autre namespace : code 28 == socket containerd : No such file or directory Falco : 2 alertes « Connexion sortante hors mesh » ; audit : 1 requête anonyme refusée
  • Chaque échec a deux preuves : le refus vu de l'attaquant, et la trace vue du défenseur. Un refus invisible est un défenseur qui ne saura pas qu'on l'attaque.
  • Le rapport est écrit comme un pentest interne : c'est le format attendu d'un DevSecOps, et une histoire d'entretien.

Questions de relecteur

  • Pourquoi PSA en plus de Kyverno ? PSA est natif, sans composant, et couvre le socle ; Kyverno ajoute les règles propres à l'entreprise. Si Kyverno tombe, PSA tient toujours.
  • Que fait-on d'une alerte Falco « Shell en prod » déclenchée par un opérateur légitime ? On la garde : un shell en prod est une exception à justifier dans le canal d'incident, pas une routine.
