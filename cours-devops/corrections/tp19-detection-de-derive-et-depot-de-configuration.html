Détection de dérive et dépôt de configuration

Une solution complète, étape par étape : ce qu'il faut produire, la commande ou le fichier clé, le résultat qui prouve que ça marche, et les pièges. Ta solution peut différer ; ce qui compte, c'est que chaque preuve soit là.

Énoncé
  1. Sur le projet Terraform du TP 16 : ajoute un pipeline planifié drift-detection (terraform plan -detailed-exitcode, code 2 = dérive) qui échoue et notifie. Provoque une dérive dans LocalStack (awslocal ec2 authorize-security-group-ingress) et vérifie la détection.
  2. Crée le dépôt crisisshield-config avec la structure de la section 19.4, en version Compose pour l'instant (envs/staging/compose.yaml et envs/prod/compose.yaml avec le tag d'image en variable dans un fichier image.env).
  3. Modifie le pipeline de CrisisShield : après le build d'image, un job met à jour envs/staging/image.env dans le dépôt de config par commit automatique (token de projet à portée minimale). La promotion en prod est une merge request manuelle.
  4. Écris un agent de réconciliation minimal en Bash (reconcile.sh, tournant dans un conteneur en boucle) : toutes les 60 s, git pull le dépôt de config, et si le tag ou le compose a changé, docker compose up -d. Le pipeline n'a alors plus aucun accès à ton « environnement de prod » : seulement à Git. Vérifie qu'un git revert sur le dépôt de config déclenche un rollback.
  5. Chiffre le fichier de secrets du dépôt de config avec SOPS + age (image ghcr.io/getsops/sops), et fais-le déchiffrer par l'agent.
Étape 1

Un dépôt de configuration et un déploiement par pull

mkdir -p gitops/{apps/api,envs/dev,envs/prod}
cat > gitops/apps/api/compose.yaml <<'EOF'
services: { api: { image: "localhost:5000/crisisshield/api@sha256:a77e…", ports: ["8080:8080"] } }
EOF
cd gitops && git init && git add . && git commit -m 'feat: api en dev'
# l'agent de pull, le plus simple possible : une boucle qui applique ce que Git dit
cat > agent.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
while true; do git -C /repo pull -q ; docker compose -f /repo/apps/api/compose.yaml up -d --remove-orphans ; sleep 30 ; done
EOF
docker run -d --name gitops-agent -v "$PWD:/repo" -v /var/run/docker.sock:/var/run/docker.sock -v "$PWD/agent.sh:/agent.sh" docker:27-cli sh /agent.sh
l'agent applique l'état de Git toutes les 30 s ; modifier compose.yaml + commit → nouvelle version déployée sans push ni accès entrant
  • C'est le modèle pull en miniature : personne ne pousse vers l'environnement ; l'environnement lit Git. ArgoCD fait exactement cela avec Kubernetes au chapitre 29.
  • Le digest dans le fichier est la clé : la promotion est un changement de digest commité.
Étape 2

Dérive corrigée, et retour arrière par revert

docker compose -f apps/api/compose.yaml exec api sh -c 'echo cassé' ; docker rm -f gitops-api-1 ; sleep 35 ; docker ps --filter name=api --format '{{.Names}} {{.Status}}'
git log --oneline | head -2 ; git revert --no-edit HEAD ; sleep 35 ; docker inspect gitops-api-1 --format '{{.Config.Image}}'
gitops-api-1 Up 20 seconds (le conteneur supprimé à la main revient : la dérive est corrigée) localhost:5000/crisisshield/api@sha256:3f9c… (le revert a ramené l'ancien digest)
  • La réconciliation remet ce que Git décrit, y compris après une suppression manuelle : c'est ce qui rend l'environnement reconstructible.
  • Le rollback est un commit comme un autre : traçable, revu, réversible.
Étape 3

Promotion entre environnements et politique

cat > envs/prod/kustomization.yaml <<'EOF'
resources: [../../apps/api]
images: [{ name: crisisshield/api, digest: sha256:a77e… }]
EOF
# promotion : une MR qui change le digest de prod vers celui validé en dev ; règle : main protégée, 1 approbation, pipeline (kubeconform, trivy config, kyverno test) vert
docker run --rm -v "$PWD:/w" ghcr.io/yannh/kubeconform:latest-alpine -summary /w/envs/prod || true
Summary: 3 resources found, 3 valid (à partir du chapitre 26, ce sont des manifests Kubernetes)
  • Dev et prod pointent sur le même dossier d'application et diffèrent par le digest : promouvoir = copier un digest, pas reconstruire.
  • Le pipeline du dépôt de config valide des manifests, pas du code : schéma, sécurité, politiques.
Étape 4

Comparer push et pull, par écrit

# docs/adr/0003-gitops-pull.md : contexte (accès entrant depuis la CI vers la prod, secrets de déploiement dans la CI), décision (pull par agent), conséquences (dérive corrigée, audit = git log, rollback = revert ; coût : un agent à exploiter, promotion par MR)
  • L'ADR est le livrable attendu : une décision datée avec ses conséquences, que le chapitre 51 rendra systématique.
  • Le point clé pour l'entretien : en pull, la production n'a aucun identifiant de la CI et la CI n'a aucun accès à la production.
