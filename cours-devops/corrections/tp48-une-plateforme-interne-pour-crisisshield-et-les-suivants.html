Une plateforme interne pour CrisisShield et les suivants

Une solution complète, étape par étape : ce qu'il faut produire, la commande ou le fichier clé, le résultat qui prouve que ça marche, et les pièges. Ta solution peut différer ; ce qui compte, c'est que chaque preuve soit là.

Énoncé
  1. Backstage (Helm sur kind, ou Compose) avec le catalogue des composants de CrisisShield (API, front, Notification, base, Kafka, contrats d'API), les intégrations GitLab, ArgoCD, Grafana, Kubernetes ; TechDocs générés depuis les docs/ de chaque dépôt (tous les cours que tu as écrits deviennent la documentation de la plateforme).
  2. Template Scaffolder « service Java Quarkus/Spring » qui crée : dépôt GitLab avec CODEOWNERS, pipeline complet (niveau 2 + 7), Dockerfile durci, chart ou overlays, ApplicationSet ArgoCD, ServiceMonitor, dashboards, SLO Sloth, alertes, External Secrets, NetworkPolicies, catalog-info.yaml. Crée un service « Cartographie » avec, en moins de 15 minutes, jusqu'au premier déploiement en staging.
  3. Crossplane : XRD et composition PostgreSQLInstance (tailles small/medium/large) qui crée un cluster CloudNativePG avec sauvegardes, pooler, PodMonitor, alertes et secret de connexion ; composition KafkaTopic vers Strimzi avec conventions et ACL. Le nouveau service « Cartographie » les consomme en GitOps.
  4. Environnements éphémères : ApplicationSet avec le générateur de merge requests GitLab qui déploie chaque MR dans un namespace mr-&lt;id&gt; avec une base éphémère (composition, taille tiny) et une URL de prévisualisation postée dans la MR ; destruction à la fermeture. Vérifie le coût par OpenCost.
  5. Scorecards : dans Backstage (plugin tech-insights ou une page générée), une scorecard par service : propriétaire, SLO, alertes, runbook, signatures, CVE critiques, dépendances à jour, dernier test de restauration ; calcul automatisé par script depuis tes systèmes.
  6. Dev Container pour CrisisShield (.devcontainer/) : tout l'outillage du cours en conteneur, Tilt pour le déploiement local sur kind ; c'est aussi la réponse définitive à « le local est interdit ».
  7. Rédige la fiche produit de la plateforme (utilisateurs, golden paths, ce qu'elle garantit, ce qu'elle ne fait pas, roadmap, métriques) et un plan de lancement pour une entreprise de 10 équipes : pilote, migration, support.
Étape 1

Backstage : catalogue, intégrations, TechDocs

# platform/backstage/ — app créée par npx @backstage/create-app dans un conteneur node:20, image construite par Dockerfile multi-étapes, déployée par le chart backstage/backstage sur kind (PostgreSQL CNPG dédié)
# app-config.production.yaml (extraits)
auth: { providers: { oidc: { production: { metadataUrl: https://keycloak.crisis.local/realms/crisis/.well-known/openid-configuration, clientId: backstage, clientSecret: ${BACKSTAGE_OIDC_SECRET} } } } }

curl -s -H "Authorization: Bearer $BS" https://backstage.crisis.local/api/catalog/entities?filter=kind=component | jq length

  • Le catalogue n'est pas une saisie : chaque catalog-info.yaml vit dans son dépôt, à côté du code, et un fichier all.yaml les référence. Une entité qu'on doit mettre à jour à la main dans Backstage est déjà fausse.
  • TechDocs rend les cours utiles à quelqu'un d'autre que toi : c'est la documentation de la plateforme, cherchable, versionnée.
Étape 2

Template Scaffolder « service Java » : Cartographie en 11 minutes

# platform/templates/service-java/template.yaml (extrait)
apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata: { name: service-java, title: Service Java (Quarkus ou Spring) }
spec:
  parameters:
    - properties: { name: { type: string, pattern: '^[a-z][a-z0-9-]{2,30}$' }, framework: { enum: [quarkus, spring] }, owner: { ui:field: OwnerPicker }, needsDatabase: { type: boolean }, needsKafka: { type: boolean }, slo: { type: number, default: 99.9 } }
  steps:
    - { id: fetch, action: fetch:template, input: { url: ./skeleton/${{ parameters.framework }}, values: { name: '${{ parameters.name }}', owner: '${{ parameters.owner }}', slo: '${{ parameters.slo }}' } } }
    - { id: repo, action: publish:gitlab, input: { repoUrl: 'gitlab.local?owner=crisisshield&repo=${{ parameters.name }}', defaultBranch: main, protectDefaultBranch: true, settings: { only_allow_merge_if_pipeline_succeeds: true } } }
    - { id: config, action: publish:gitlab:merge-request, input: { repoUrl: gitlab.local?owner=crisisshield&repo=config, branchName: 'add-${{ parameters.name }}', title: 'feat: ${{ parameters.name }} (créé par template)', description: 'ApplicationSet, overlays, SLO, alertes, ExternalSecrets, NetworkPolicies', targetPath: 'services/${{ parameters.name }}' } }
    - { id: register, action: catalog:register, input: { repoContentsUrl: '${{ steps.repo.output.repoContentsUrl }}', catalogInfoPath: /catalog-info.yaml } }
# skeleton/quarkus/ : code minimal, CODEOWNERS, .gitlab-ci.yml (include du template de compliance TP 51 : build, tests, SAST, SCA, image Kaniko, signature, SBOM), Dockerfile durci, kustomize/ (Deployment de référence), slo.yaml (→ Sloth), dashboards/, ServiceMonitor, ExternalSecret, NetworkPolicy, catalog-info.yaml, mkdocs.yml ; si needsDatabase : claim PostgreSQLInstance (étape 3) ; si needsKafka : claim KafkaTopic
# chrono : « Create » dans Backstage → MR config fusionnée (revue de 2 min) → ArgoCD staging Synced/Healthy → curl https://cartographie.staging.crisis.local/q/health
T+0 Create ; T+40 s dépôt créé, pipeline lancé ; T+6 min image signée ; T+7 MR config fusionnée ; T+10 ArgoCD Synced ; T+11 min {"status":"UP"} — SLO, alertes, dashboard, secrets, NetworkPolicies, Rollout et sauvegarde en place, 0 commande kubectl
  • Le template ne génère pas seulement du code : il génère la conformité (pipeline, signature, SLO, politiques). Le chemin doré est celui où faire bien est plus facile que faire mal.
  • La MR sur le dépôt de config au lieu d'un apply direct : même le template respecte GitOps et la revue.
Étape 3

Crossplane : PostgreSQLInstance et KafkaTopic en compositions

k helm install crossplane crossplane-stable/crossplane -n crossplane-system --create-namespace --version 1.17.1
# provider-kubernetes (crée des objets dans le cluster) ; platform/crossplane/xrd-postgresql.yaml :
apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata: { name: xpostgresqlinstances.platform.crisis.local }
spec:
  group: platform.crisis.local
  names: { kind: XPostgreSQLInstance, plural: xpostgresqlinstances }
  claimNames: { kind: PostgreSQLInstance, plural: postgresqlinstances }
  versions: [{ name: v1alpha1, served: true, referenceable: true, schema: { openAPIV3Schema: { type: object, properties: { spec: { type: object, properties: { size: { type: string, enum: [tiny, small, medium, large] }, backups: { type: boolean, default: true } }, required: [size] } } } } }]
# composition : function-patch-and-transform (mode Pipeline) — objets Kubernetes CNPG Cluster (instances 1/3/3/5, storage 2/10/50/200 Gi, resources par taille), ScheduledBackup si backups, Pooler, PodMonitor, PrometheusRule (alertes CNPG), et connectionDetails → Secret <claim>-conn (host rw/ro, user, password via Vault ou secret CNPG)
# composition KafkaTopic : Strimzi KafkaTopic (partitions par convention : 6, retention 7 j, nom préfixé <service>.), KafkaUser avec ACL (write pour le service propriétaire, read pour les consommateurs listés)
# claim dans services/cartographie (par le template) :
apiVersion: platform.crisis.local/v1alpha1
kind: PostgreSQLInstance
metadata: { name: cartographie-db, namespace: cartographie }
spec: { size: small }
k kubectl get postgresqlinstance -n cartographie ; k kubectl get cluster -n cartographie ; k kubectl get secret cartographie-db-conn -n cartographie -o jsonpath='{.data}' | jq 'keys'
cartographie-db SYNCED True READY True (2 min) cartographie-db-xk2p 3 instances Cluster in healthy state ["host_ro","host_rw","password","username"] (le service lit ce Secret : il n'a jamais vu un manifest CNPG)
  • L'équipe demande une « base small » ; la plateforme décide de la HA, des sauvegardes, du pooler, des alertes. Changer la composition met à jour toutes les bases : c'est ça, une abstraction de plateforme.
  • Une composition est du code testé (crossplane render en CI avec les quatre tailles) et versionnée : une nouvelle version se déploie progressivement (compositionRevision).
Étape 4

Environnements éphémères par merge request, coût par OpenCost

cat > argocd/appset-mr.yaml <<'EOF'
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: mr-envs, namespace: argocd }
spec:
  generators:
    - pullRequest: { gitlab: { project: "42", api: http://gitlab.local:8929, tokenRef: { secretName: gitlab-token, key: token }, labels: [preview] }, requeueAfterSeconds: 60 }
  template:
    metadata: { name: 'api-mr-{{number}}' }
    spec:
      project: crisisshield
      source: { repoURL: http://gitlab.local:8929/crisisshield/config.git, targetRevision: main, path: envs/preview, kustomize: { namespace: 'mr-{{number}}', images: ['harbor.crisis.local/crisisshield/api:{{head_sha}}'], commonAnnotations: { preview/url: 'https://mr-{{number}}.preview.crisis.local' } } }
      destination: { server: https://kubernetes.default.svc, namespace: 'mr-{{number}}' }
      syncPolicy: { automated: { prune: true, selfHeal: true }, syncOptions: [CreateNamespace=true] }
EOF
# envs/preview : api 1 réplica, claim PostgreSQLInstance size: tiny (1 instance, 1 Gi, pas de sauvegarde), Ingress mr-{{number}}.preview…, ResourceQuota 1 CPU / 2 Gi, TTL par Kyverno (cleanup policy : namespace mr-* de plus de 3 jours)
# notification ArgoCD on-deployed → GitLab API : note sur la MR « Preview : https://mr-… (base éphémère, détruite à la fermeture) »
k helm install opencost opencost/opencost -n opencost --create-namespace --set opencost.prometheus.internal.serviceName=kps-kube-prometheus-stack-prometheus
curl -s 'http://opencost.opencost:9003/allocation?window=7d&aggregate=namespace' | jq '.data[0] | to_entries | map(select(.key | startswith("mr-"))) | map({ns: .key, cost: .value.totalCost})'
MR !117 ouverte → namespace mr-117 en 3 min, base tiny, note postée dans la MR ; fermeture → namespace supprimé en 2 min (prune) OpenCost : mr-117 0,42 $ sur 7 j, mr-118 0,39 $ ; 11 environnements de MR sur le mois : 4,10 $ (prix kind ≈ prix nœud AWS m6g équivalent)
  • Un environnement par MR est la fonctionnalité qui change le plus la vie des développeurs ; sa base éphémère par composition tiny est ce qui la rend crédible (un vrai PostgreSQL, pas H2).
  • Le coût par namespace rend l'éphémère défendable devant la direction : 4 $ par mois pour 11 environnements.

Dev Container et Tilt : le poste enfin conforme à « le local est interdit »

# .devcontainer/devcontainer.json : image harbor.crisis.local/platform/devtools:2026.09 (JDK 21, mvnw, node 20, kubectl, helm, kind, k9s, stern, argocd, vault, cosign, trivy, kyverno, k6, sloth, terraform, ansible, tilt, git, gh, glab) ; features : docker-outside-of-docker ; mounts : ~/.kube, ~/.m2 en volume nommé ; postCreateCommand : kind get clusters || kind create cluster --config kind-config.yaml
# Tiltfile :
docker_build('harbor.crisis.local/crisisshield/api', '.', dockerfile='Dockerfile', live_update=[sync('./target/classes', '/app/BOOT-INF/classes'), run('touch /app/restart.trigger')])
k8s_yaml(kustomize('kustomize/overlays/dev'))
k8s_resource('api', port_forwards=8080, resource_deps=['crisis-db'])
local_resource('compile', 'mvn -q -o compile', deps=['src'], ignore=['target'])
# VS Code : Dev Containers: Reopen in Container → tilt up → modification d'un contrôleur → recompilation + sync en 3 s dans le Pod kind
docker run --rm -v "$PWD:/w" -w /w devtools:2026.09 sh -c 'java -version 2>&1 | head -1 ; kubectl version --client --short ; tilt version'
openjdk 21.0.4 ; Client Version: v1.31.0 ; v0.33.20 tilt up : api Running en 40 s ; modification de IncidentController → « Live update » 2,8 s, sans rebuild d'image
  • Le Dev Container est l'image outillée du TP 25 devenue le poste de travail : un nouveau développeur est productif en 10 minutes, avec les mêmes versions que la CI.
  • Tilt ferme la boucle interne (édition → Pod en 3 s) sans sacrifier la fidélité (le vrai cluster, le vrai Deployment) : c'est la réponse à « Kubernetes est trop lourd pour développer ».

Fiche produit et plan de lancement

# docs/platform/fiche-produit.md : utilisateurs (10 équipes produit, 60 devs, 4 ops), golden paths (créer un service, une base, un topic, un environnement de MR), garanties (déploiement < 15 min, SLO et alertes par défaut, signature, sauvegarde testée, coût visible), ce qu'elle ne fait pas (pas de VM, pas de base hors PostgreSQL, pas de cloud hors AWS eu-west-3, pas de support des runtimes hors Java/Node/Python), roadmap 3 trimestres (T1 : previews et scorecards ; T2 : Crossplane Redis, Kafka ACL fines ; T3 : multi-cluster TP 49), métriques (adoption : % de services via template ; temps au premier déploiement ; tickets plateforme/semaine ; NPS)
# docs/platform/plan-lancement.md : pilote (2 équipes volontaires, 6 semaines, mesure avant/après du lead time), coalition (1 champion par équipe), migration par vagues (3 × 3 équipes, un service à la fois via le template « import »), support (canal, permanence 2 h/jour, docs TechDocs, office hours hebdo), critères d'arrêt du pilote
deux documents, chaque garantie renvoie à une preuve du TP (chrono, scorecard, OpenCost)
  • Une plateforme est un produit : elle a des utilisateurs, une proposition de valeur, des limites explicites et une roadmap. « Ce qu'elle ne fait pas » est la section la plus utile.
  • Le plan de lancement mesure le pilote (lead time avant/après) : c'est ce qui convainc la troisième équipe, pas la démonstration.

Questions de relecteur

  • Pourquoi Crossplane plutôt qu'un chart Helm « base de données » ? La composition est réconciliée en continu et versionnée indépendamment du service ; un chart est appliqué une fois par celui qui l'installe.
