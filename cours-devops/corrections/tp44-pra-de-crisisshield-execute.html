Correction type — Travail pratique 44

PRA de CrisisShield, exécuté

Une solution complète, étape par étape : ce qu'il faut produire, la commande ou le fichier clé, le résultat qui prouve que ça marche, et les pièges. Ta solution peut différer ; ce qui compte, c'est que chaque preuve soit là.

Énoncé
  1. Définis RTO/RPO pour trois services (API/base, notifications, reporting) avec justification métier et coût estimé par stratégie ; choisis.
  2. Sauvegardes : Velero sur kind (vers MinIO) pour les ressources et volumes ; CloudNativePG vers un second MinIO « hors site » avec Object Lock ; snapshots Raft de Vault ; export Keycloak ; state Terraform versionné dans un bucket verrouillé. Script restore-test.sh planifié chaque nuit en CI : restaure la base de la veille dans un namespace isolé, lance les tests d'intégration, mesure et publie la durée (métrique Prometheus backup_restore_test_duration_seconds + alerte si absent depuis 26 h).
  3. Simule un ransomware : avec un compte « compromis » (ServiceAccount de l'API), tente de supprimer les sauvegardes ; le refus doit être prouvé.
  4. Second cluster kind = « région secondaire » : même dépôt de config, ApplicationSet ArgoCD qui cible les deux clusters, réplication CloudNativePG entre clusters (réplica cluster), MirrorMaker 2 pour Kafka, Vault en réplication (performance replication est Enterprise ; utilise des snapshots restaurés ou un second Vault avec les mêmes secrets synchronisés par External Secrets depuis un backend commun).
  5. Bascule réelle : script failover.sh (promotion de la base, activation des workloads, bascule DNS simulée par un CoreDNS local ou le fichier hosts), chronométré ; boucle curl pendant la bascule pour mesurer le RTO réel ; insertion continue de données pour mesurer le RPO réel. Puis failback.
  6. Avec compte AWS (optionnel, quelques euros) : réplication S3 inter-région et Aurora Global Database sur l'infra du niveau 4 ; test de bascule managée.
  7. Rédige le PRA (structure 44.5), le rapport de test avec RTO/RPO mesurés contre objectifs, et le post-mortem du test.
Étape 1

RTO/RPO par service, justifiés et chiffrés

# docs/pra.md §1
# | Service | RTO | RPO | Justification métier | Stratégie | Coût/mois estimé |
# | API + base | 15 min | 1 min | une crise en cours ne peut pas attendre ; perdre plus d'une minute de déclarations est inacceptable | warm standby : réplica CNPG continu dans un second cluster, ArgoCD prêt, bascule scriptée | +70 $ (cluster secondaire réduit + stockage) |
# | Notifications | 30 min | 5 min | les notifications en retard sont rejouées depuis l'outbox | pilot light : MirrorMaker 2 + workloads à 0 réplica | +15 $ |
# | Reporting | 24 h | 24 h | rapports régénérables depuis la base | backup/restore | +2 $ (stockage) |
# alternatives chiffrées : multi-site actif-actif pour l'API (+220 $, complexité de l'écriture multi-primaire) → refusé ; backup/restore seul pour l'API (RTO 2 h) → refusé par le métier
tableau signé « métier » fictif, trois stratégies différentes pour trois exigences différentes
  • Un seul RTO pour tout est le signe qu'on n'a pas discuté avec le métier : le reporting n'a pas besoin du même niveau que la déclaration d'incident.
  • Le coût de chaque stratégie est ce qui rend la décision honnête : le RTO de 15 min vaut 70 $, pas 220.

  • Cinq sources de vérité, cinq sauvegardes : oublier Vault ou Keycloak, c'est restaurer une base que plus personne ne peut ouvrir.
  • Object Lock COMPLIANCE : même l'administrateur du bucket ne peut pas supprimer avant 30 jours. C'est la seule réponse technique au ransomware.
Étape 3

restore-test.sh chaque nuit, mesuré, alerté

#!/usr/bin/env bash
set -euo pipefail
NS=restore-test-$(date +%Y%m%d); T0=$(date +%s)
kubectl create ns $NS
kubectl apply -n $NS -f - <<EOF
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata: { name: restored }
spec:
  instances: 1
  imageName: ghcr.io/cloudnative-pg/postgresql:16.4
  storage: { size: 5Gi }
  bootstrap: { recovery: { source: crisis-db, recoveryTarget: { targetTime: "$(date -u -d 'yesterday 23:59' +'%Y-%m-%d %H:%M:%S+00')" } } }
  externalClusters: [{ name: crisis-db, barmanObjectStore: { destinationPath: s3://crisis-backups-offsite/, endpointURL: http://minio-offsite:9000, s3Credentials: { accessKeyId: { name: minio-offsite, key: ACCESS_KEY_ID }, secretAccessKey: { name: minio-offsite, key: ACCESS_SECRET_KEY } } } }]
EOF
kubectl wait -n $NS cluster/restored --for=jsonpath='{.status.phase}'="Cluster in healthy state" --timeout=15m
kubectl run -n $NS it --rm -i --restart=Never --image=harbor.crisis.local/crisisshield/api-tests@sha256:… --env="DB_HOST=restored-rw.$NS" -- ./mvnw -q verify -Dtest='*IT'   # tests d'intégration sur la base restaurée
ROWS=$(kubectl exec -n $NS restored-1 -- psql -U postgres -d crisis -tAc 'select count(*) from incident')
D=$(( $(date +%s) - T0 ))
cat <<EOF | curl -s --data-binary @- http://pushgateway.observability:9091/metrics/job/restore-test
backup_restore_test_duration_seconds $D
backup_restore_test_rows $ROWS
backup_restore_test_success 1
EOF
kubectl delete ns $NS
# PrometheusRule : (time() - push_time_seconds{job="restore-test"}) > 26*3600 → alerte BackupRestoreTestMissing (ticket) ; backup_restore_test_success != 1 → page
# .gitlab-ci.yml : job restore-test, rules: schedule (nightly 3 h), image outillée
2026-09-22 03:00 : restauration en 6 min 40 s, 100 412 lignes, 44 tests IT verts, namespace supprimé Grafana : backup_restore_test_duration_seconds sur 30 jours (tendance : +20 s/jour avec la croissance des WAL)
  • Une sauvegarde est testée quand une restauration automatique a fait tourner les tests d'intégration dessus. Tout le reste est une supposition.
  • L'alerte d'absence (26 h) est plus importante que l'alerte d'échec : un job qui ne tourne plus ne produit pas d'erreur.
Étape 4

Ransomware simulé : le compte compromis ne peut rien supprimer

# hypothèse : l'attaquant a le ServiceAccount de l'API (jeton volé)
TOKEN=$(kubectl create token api -n crisis --duration=10m)
kubectl --token=$TOKEN auth can-i delete backups.postgresql.cnpg.io -n crisis ; kubectl --token=$TOKEN auth can-i delete backups.velero.io -n velero ; kubectl --token=$TOKEN get secret minio-offsite -n crisis 2>&1 | tail -1
# avec les identifiants MinIO de l'application (lecture des exports), tenter la suppression offsite :
docker run --rm --network host -e MC_HOST_off=http://api-app:$APPKEY@minio-offsite:9000 minio/mc rm --recursive --force off/crisis-backups-offsite/ 2>&1 | tail -1
# même avec les identifiants admin MinIO (pire cas) :
docker run --rm --network host -e MC_HOST_off=http://admin:$ADMIN@minio-offsite:9000 minio/mc rm --recursive --force off/crisis-backups-offsite/base/ 2>&1 | tail -1
# audit : Loki {job="kube-audit"} | json | user_username="system:serviceaccount:crisis:api" | verb="delete" ; alerte Falco ; MinIO audit webhook → Loki
no / no / Error from server (Forbidden) mc rm (app) : Access Denied mc rm (admin) : Object is WORM protected and cannot be overwritten (Object Lock COMPLIANCE) audit : 3 requêtes delete refusées (403) tracées avec l'identité du compte, alerte « tentative de suppression de sauvegarde » envoyée
  • Le refus est prouvé à trois niveaux : RBAC (le compte ne peut pas), identifiants (l'application n'a pas ceux du bucket), stockage (même l'admin ne peut pas). La défense en profondeur se démontre, elle ne se déclare pas.
  • La tentative refusée déclenche une alerte : un ransomware qui échoue à supprimer les sauvegardes est aussi un signal d'intrusion à traiter.
Étape 5

Région secondaire : second cluster, ArgoCD multi-cluster, réplications

k kind create cluster --name crisis-dr --config kind-config.yaml
k argocd cluster add kind-crisis-dr --name dr
cat > argocd/appset-multiregion.yaml <<'EOF'
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: crisisshield, namespace: argocd }
spec:
  generators: [{ clusters: { selector: { matchLabels: { role: workload } } } }]
  template:
    metadata: { name: 'crisisshield-{{name}}' }
    spec: { project: crisisshield, source: { repoURL: https://gitlab.local/crisisshield/config.git, targetRevision: main, path: 'envs/prod/{{metadata.labels.region}}' }, destination: { server: '{{server}}', namespace: crisis }, syncPolicy: { automated: { prune: true, selfHeal: true } } }
EOF
# envs/prod/primary : api 3 réplicas ; envs/prod/secondary : api 1 réplica, worker 0 (pilot light), même digest
# CNPG réplica : sur crisis-dr, Cluster crisis-db avec spec.replica: { enabled: true, source: primary } et externalClusters → connection vers crisis-db-rw du cluster primaire (via un Service LoadBalancer kind + MetalLB, ou un tunnel) ; TLS et mot de passe de réplication depuis Vault
# Kafka : Strimzi KafkaMirrorMaker2 primary → dr, topics incidents.*, offsets synchronisés, groupes de consommateurs répliqués
# Vault : second Vault sur crisis-dr, restauré depuis le snapshot Raft toutes les 6 h par CronJob (pas de replication en édition communautaire) ; ou External Secrets des deux clusters pointant sur un Vault externe au cluster
k --context kind-crisis-dr kubectl get cluster crisis-db -n crisis -o jsonpath='{.status.phase} {.status.replicaCluster}' ; k --context kind-crisis-dr kubectl exec -n crisis crisis-db-1 -- psql -U postgres -tAc 'select now() - pg_last_xact_replay_timestamp()'
ArgoCD : crisisshield-primary Synced/Healthy, crisisshield-dr Synced/Healthy CNPG dr : Cluster in healthy state (Replica Cluster) replay lag : 00:00:00.83 MirrorMaker2 : 3 topics répliqués, lag 0 ; Vault dr : dernier snapshot restauré il y a 2 h
  • Le second cluster est décrit par le même dépôt Git avec un dossier différent : la reprise n'est pas un environnement « à part », c'est le même code avec une autre échelle.
  • La réplication CNPG entre clusters est une vraie réplication physique continue : le RPO d'une minute est mesurable (replay lag), pas estimé.
Étape 6

Bascule réelle, chronométrée, puis failback

# scripts/failover.sh
#!/usr/bin/env bash
set -euo pipefail
T0=$(date +%s)
kubectl --context kind-crisis-dr patch cluster crisis-db -n crisis --type merge -p '{"spec":{"replica":{"enabled":false}}}'   # promotion
kubectl --context kind-crisis-dr wait cluster/crisis-db -n crisis --for=jsonpath='{.status.replicaCluster}'=false --timeout=3m
git -C config commit --allow-empty -m 'dr: activation secondaire' && sed -i 's/replicas: 1/replicas: 3/; s/worker: 0/worker: 2/' config/envs/prod/secondary/*.yaml && git -C config commit -am 'dr: échelle nominale' && git -C config push
argocd app sync crisisshield-dr --timeout 120
kubectl --context kind-crisis-dr -n kube-system patch cm coredns --type merge -p "$(cat dns/api-to-dr.yaml)" && kubectl --context kind-crisis-dr -n kube-system rollout restart deploy coredns   # « bascule DNS » : api.crisis.local → ingress du cluster dr (hosts sur le poste : idem)
echo "RTO : $(( $(date +%s) - T0 )) s"
# pendant la bascule, depuis un troisième conteneur :
docker run --rm --network host alpine sh -c 'while true; do printf "%s %s\n" "$(date +%T)" "$(wget -qO- --timeout=2 https://api.crisis.local/actuator/health 2>/dev/null || echo DOWN)"; sleep 1; done' > /tmp/probe.log &
docker run --rm --network host alpine sh -c 'i=0; while true; do i=$((i+1)); wget -qO- --post-data="{\"title\":\"rpo-$i\"}" --header="Content-Type: application/json" https://api.crisis.local/api/incidents >/dev/null 2>&1 && echo $i >> /tmp/inserted; sleep 0.5; done' &
./scripts/failover.sh ; grep -c DOWN /tmp/probe.log ; kubectl --context kind-crisis-dr exec -n crisis crisis-db-1 -- psql -U postgres -d crisis -tAc "select count(*) from incident where title like 'rpo-%'" ; tail -1 /tmp/inserted
# failback : scripts/failback.sh — resynchroniser l'ancien primaire en réplica du dr (spec.replica enabled, bootstrap pg_basebackup), attendre lag 0, promouvoir dans le sens inverse pendant une fenêtre, DNS retour
RTO : 214 s (promotion 40 s, sync ArgoCD 95 s, DNS + readiness 79 s) → objectif 15 min tenu probe : 231 lignes DOWN (≈ 3 min 51 s) RPO : 412 incidents insérés côté client, 410 présents dans la base dr → 2 perdus (1 s de réplication + le dernier commit non rejoué) → objectif 1 min tenu failback : 11 min (resynchronisation 6 min), 0 perte
  • Le RTO et le RPO sont mesurés par des boucles indépendantes, pas lus dans un document : c'est ce qui rend le rapport crédible.
  • Le failback est souvent plus long et plus risqué que le failover : il se teste aussi, et l'ancien primaire ne redevient jamais primaire sans resynchronisation complète.

Questions de relecteur

  • Pourquoi tester la restauration dans un namespace isolé et jamais en place ? Une restauration ratée en place détruit ce qu'il restait ; isolée, elle ne coûte qu'un namespace.
