Blue/green et feature flag sur CrisisShield

Une solution complète, étape par étape : ce qu'il faut produire, la commande ou le fichier clé, le résultat qui prouve que ça marche, et les pièges. Ta solution peut différer ; ce qui compte, c'est que chaque preuve soit là.

Énoncé
  1. Dans le Compose de production du TP 9, déclare api-blue et api-green (même image, tag paramétré par variables BLUE_TAG et GREEN_TAG), et le proxy avec un fichier d'upstream monté.
  2. Écris scripts/switch.sh (section 15.2) et scripts/rollback.sh. Chronomètre la bascule et le retour arrière : objectif sous 30 secondes.
  3. Branche le pipeline : le déploiement prod sur tag déploie sur la couleur inactive, lance les smoke tests, bascule, puis un job manuel rollback reste disponible pendant 24 h.
  4. Ajoute une migration Flyway qui introduit une colonne priority_level en respectant expand/contract, sur trois releases (v1.2.0 expand, v1.3.0 lecture, v1.4.0 contract). Prouve avec le blue/green que les deux versions coexistent sans erreur pendant la bascule (un script curl en boucle qui compte les codes ≠ 200).
  5. Implémente un feature flag (OpenFeature + flagd dans le Compose, ou une table avec un endpoint d'administration) devant une fonctionnalité de CrisisShield, active-le pour un utilisateur, puis pour tous, sans redéployer.
Étape 1

Un déploiement bleu/vert avec Compose et nginx

# deux services api-blue, api-green ; nginx upstream sur un fichier de config rechargeable
cat > nginx/upstream.conf <<'EOF'
upstream api { server api-blue:8080; }
EOF
docker compose up -d --scale api-green=1 api-green   # nouvelle version à côté
curl -sf localhost:8080/health -H 'Host: green.local' || docker compose exec proxy wget -qO- http://api-green:8080/actuator/health
sed -i 's/api-blue/api-green/' nginx/upstream.conf && docker compose exec proxy nginx -s reload
for i in $(seq 20); do curl -s localhost/api/version; done | sort | uniq -c
20 1.1.0 (bascule instantanée, aucune requête perdue)
  • La bascule est un rechargement de configuration, réversible en une seconde : remettre api-blue et recharger.
  • Le vert est vérifié avant de recevoir du trafic : c'est la différence avec un simple redémarrage.
Étape 2

Canary pondéré

cat > nginx/upstream.conf <<'EOF'
upstream api { server api-blue:8080 weight=9; server api-green:8080 weight=1; }
EOF
docker compose exec proxy nginx -s reload
for i in $(seq 100); do curl -s localhost/api/version; done | sort | uniq -c
91 1.0.0 9 1.1.0
  • 10 % du trafic sur la nouvelle version ; on regarde le taux d'erreur et la latence du canary avant d'augmenter à 50 puis 100.
  • Sans métriques comparées (chapitre 35), un canary est un déploiement lent, pas un déploiement sûr.
Étape 3

Feature flag : déployer sans activer

// Spring : @Value("${features.export-csv:false}") boolean exportCsv ; ou un client OpenFeature/Flipt
// endpoint /api/incidents/export renvoie 404 si le flag est faux
docker compose exec api sh -c 'wget -qO- localhost:8080/api/incidents/export' ; echo
# activer sans redéployer : variable d'environnement rechargée (Spring Cloud Config) ou Flipt : flipt flag enable export-csv
docker compose exec api sh -c 'wget -qO- localhost:8080/api/incidents/export | head -c 80'
404 id,titre,zone,priorite … (activé pour tous, ou pour un groupe d'utilisateurs)
  • Le code est en production depuis des jours quand la fonctionnalité s'allume : le déploiement n'est plus l'événement.
  • Un flag est une dette : date de suppression dans le ticket, sinon le code se remplit de branches mortes.
Étape 4

Rollback en une commande, et migration compatible

# rollback : image précédente par digest
docker compose exec proxy sh -c "sed -i 's/api-green/api-blue/' /etc/nginx/upstream.conf && nginx -s reload"
# ou avec Compose : docker compose up -d api --no-deps (image: api@sha256:ancien)
# migration : Flyway V12__add_zone_code.sql (ADD COLUMN NULL) déployée avant le code qui l'utilise ; le code v1.0.0 tourne encore avec le schéma v12
retour à 1.0.0 en 1 s ; le schéma v12 reste, compatible avec 1.0.0
  • Un rollback n'est possible que si le schéma est compatible N-1 : expand avant contract (chapitre 47).
  • Testé en staging à chaque déploiement, pas découvert le jour où il faut.
Étape 5

Runbook de déploiement

# docs/runbooks/deploiement.md : préconditions (pipeline vert, budget d'erreur, fenêtre), étapes (canary 10 %, 15 min, seuils, 50 %, 100 %), critères d'arrêt (5xx > 1 %, p95 > 300 ms), commande de rollback, qui prévenir, post-déploiement (smoke test, annotation Grafana)
  • Un runbook est ce qu'un collègue exécute à 3 h sans toi : commandes exactes, seuils chiffrés, une seule décision par étape.
  • Il devient le pipeline d'Argo Rollouts au niveau 5 : les seuils sont les mêmes.
