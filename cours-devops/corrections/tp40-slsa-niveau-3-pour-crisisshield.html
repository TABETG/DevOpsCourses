SLSA niveau 3 pour CrisisShield

Une solution complète, étape par étape : ce qu'il faut produire, la commande ou le fichier clé, le résultat qui prouve que ça marche, et les pièges. Ta solution peut différer ; ce qui compte, c'est que chaque preuve soit là.

Énoncé
  1. Pipeline : build sur runner éphémère sans socket Docker (Kaniko ou BuildKit rootless), image de job épinglée par digest, id_tokens pour Sigstore et Vault, aucun secret statique. Signature keyless de l'image, attestation SBOM (CycloneDX) et provenance SLSA (GitLab la génère pour les artefacts ; pour l'image, produis un prédicat in-toto avec les informations du job). Signe aussi le chart Helm (OCI) et l'archive du front.
  2. Rekor : retrouve tes signatures dans le journal public (rekor-cli search) et explique en trois lignes ce que ça implique (transparence, mais aussi exposition des noms de projets). Déploie ensuite un Sigstore privé minimal (Fulcio + Rekor + Keycloak comme OIDC) sur kind ou en Compose, et bascule dessus.
  3. Active la politique Kyverno de vérification de signature et d'attestation (l'image doit être signée par le job main et porter un SBOM attesté). Tente de déployer une image non signée, une image signée par une autre branche, une image signée sans SBOM : les trois doivent être refusées, avec message clair.
  4. Reproductibilité : rends le build de l'image déterministe (SOURCE_DATE_EPOCH, versions épinglées, tri des fichiers) et prouve qu'un second build du même commit donne le même digest. Documente ce qui a dû changer.
  5. Dépendances : le proxy Nexus n'autorise que les artefacts signés et une liste de groupes ; ajoute un paquet typosquatté fictif à ton pom.xml et vérifie le refus. Vérification PGP des artefacts Maven en CI.
  6. Évalue ton pipeline avec la checklist SLSA (site officiel) et l'OpenSSF Scorecard sur le dépôt ; note le niveau atteint et ce qui manque pour L3 complet.
Étape 1

Build éphémère sans socket, images de job par digest, jetons d'identité

# .gitlab-ci.yml (extrait)
build-image:
  stage: package
  image: { name: gcr.io/kaniko-project/executor@sha256:0f6ac… , entrypoint: [""] }
  id_tokens: { SIGSTORE_ID_TOKEN: { aud: sigstore }, VAULT_ID_TOKEN: { aud: https://vault.crisis.local } }
  variables: { SOURCE_DATE_EPOCH: $CI_COMMIT_TIMESTAMP_EPOCH }
  script:
    - export VAULT_TOKEN=$(vault write -field=token auth/jwt/login role=ci-main jwt=$VAULT_ID_TOKEN)
    - echo "{\"auths\":{\"$CI_REGISTRY\":{\"auth\":\"$(vault kv get -field=auth kv/ci/registry)\"}}}" > /kaniko/.docker/config.json
    - /kaniko/executor --context $CI_PROJECT_DIR --dockerfile Dockerfile --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA --reproducible --digest-file /tmp/digest --cache=true --cache-repo $CI_REGISTRY_IMAGE/cache
    - echo "IMAGE_DIGEST=$(cat /tmp/digest)" >> build.env
  artifacts: { reports: { dotenv: build.env } }
# runner : executor kubernetes, un Pod par job, pas de socket ; ou docker executor sans volume docker.sock
docker compose -f compose.gitlab.yaml exec runner cat /etc/gitlab-runner/config.toml | grep -c docker.sock
0 (aucun socket monté) IMAGE_DIGEST=sha256:9c4d… (l'image est construite sans démon Docker, dans un conteneur non privilégié)
  • Kaniko exécute le Dockerfile en espace utilisateur : le job n'a plus le contrôle de l'hôte, ce qui est la condition « build isolé » de SLSA L3.
  • L'image de job épinglée par digest ferme la porte du « Kaniko modifié sur Docker Hub » : le pipeline lui-même a une chaîne d'approvisionnement.
Étape 2

Signature keyless, attestations SBOM et provenance, chart et front

sign:
  image: { name: gcr.io/projectsigstore/cosign@sha256:…, entrypoint: [""] }
  id_tokens: { SIGSTORE_ID_TOKEN: { aud: sigstore } }
  script:
    - cosign sign --yes $CI_REGISTRY_IMAGE@$IMAGE_DIGEST
    - syft $CI_REGISTRY_IMAGE@$IMAGE_DIGEST -o cyclonedx-json > sbom.cdx.json
    - cosign attest --yes --type cyclonedx --predicate sbom.cdx.json $CI_REGISTRY_IMAGE@$IMAGE_DIGEST
    - |
      cat > provenance.json <<EOF
      { "buildDefinition": { "buildType": "https://gitlab.com/ci/v1", "externalParameters": { "repository": "$CI_PROJECT_URL", "ref": "$CI_COMMIT_REF_NAME", "commit": "$CI_COMMIT_SHA" }, "internalParameters": { "job": "$CI_JOB_ID", "runner": "$CI_RUNNER_DESCRIPTION" } },
        "runDetails": { "builder": { "id": "https://gitlab.local/-/runners/$CI_RUNNER_ID" }, "metadata": { "invocationId": "$CI_PIPELINE_URL", "startedOn": "$CI_JOB_STARTED_AT" } } }
      EOF
    - cosign attest --yes --type slsaprovenance1 --predicate provenance.json $CI_REGISTRY_IMAGE@$IMAGE_DIGEST
    - helm package charts/crisisshield && helm push crisisshield-*.tgz oci://$CI_REGISTRY/crisisshield/charts && cosign sign --yes $CI_REGISTRY/crisisshield/charts/crisisshield@$(crane digest …)
    - cosign sign-blob --yes --bundle web.bundle web-dist.tar.gz
cosign verify --certificate-identity-regexp='^https://gitlab.local/crisisshield/api//\.gitlab-ci\.yml@refs/heads/main$' --certificate-oidc-issuer=https://gitlab.local $CI_REGISTRY_IMAGE@$IMAGE_DIGEST | jq '.[0].optional.Subject'
Pushing signature to: … ; Pushing attestation (cyclonedx) ; Pushing attestation (slsaprovenance1) "https://gitlab.local/crisisshield/api//.gitlab-ci.yml@refs/heads/main" (l'identité signataire est le pipeline de main, pas une personne ni une clé)
  • Keyless : Fulcio émet un certificat de 10 minutes lié à l'identité OIDC du job ; il n'y a aucune clé à protéger ni à faire tourner. La vérification porte sur qui a signé (quel dépôt, quelle branche).
  • La provenance dit d'où vient l'artefact ; le SBOM dit ce qu'il contient ; la signature dit qu'ils n'ont pas bougé. Les trois sont des attestations distinctes sur le même digest.
Étape 3

Rekor public, puis Sigstore privé

docker run --rm ghcr.io/sigstore/rekor-cli search --email gael@… 2>/dev/null | head -3   # ou --sha $IMAGE_DIGEST
docker run --rm ghcr.io/sigstore/rekor-cli get --uuid 24296fb2… | jq '.Body.HashedRekordObj.signature.publicKey' | base64 -d | openssl x509 -noout -subject -ext subjectAltName
# tp40.md — trois lignes : le journal public prouve l'existence de la signature à une date (non répudiation) ; il expose le nom du dépôt, la branche et l'e-mail ; pour un projet privé, on héberge son propre journal.
# infra/sigstore/compose.yaml : fulcio (ghcr.io/sigstore/fulcio), rekor-server + trillian + mysql, ctlog, timestamp-authority ; Keycloak comme OIDC (client sigstore, aud sigstore)
docker compose -f infra/sigstore/compose.yaml up -d
cosign initialize --mirror https://tuf.crisis.local --root root.json   # racine TUF privée générée avec le tuf CLI
cosign sign --yes --fulcio-url=https://fulcio.crisis.local --rekor-url=https://rekor.crisis.local --oidc-issuer=https://keycloak.crisis.local/realms/crisis $CI_REGISTRY_IMAGE@$IMAGE_DIGEST
curl -s https://rekor.crisis.local/api/v1/log | jq .treeSize
rekor public : 2 entrées trouvées, SAN = URI:https://gitlab.local/crisisshield/api//.gitlab-ci.yml@refs/heads/main rekor privé : treeSize 3 (les signatures suivantes vont dans le journal interne ; le public n'en voit plus)
  • La transparence est une propriété de sécurité (une signature frauduleuse serait visible de tous), mais aussi une fuite d'information : nom des projets, cadence de release, e-mails. En entreprise, Sigstore privé ou TSA privée.
  • La racine TUF privée est un nouveau secret racine, à traiter comme la CA du TP 41 (cérémonie, hors ligne).
Étape 4

Kyverno : signature et attestation obligatoires, trois refus

cat > k8s/policies/kyverno/09-verify-image.yaml <<'EOF'
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: image-signee-et-attestee }
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30
  rules:
    - name: signature-du-pipeline-main
      match: { any: [{ resources: { kinds: [Pod], namespaces: [crisis, crisis-prod] } }] }
      verifyImages:
        - imageReferences: ["harbor.crisis.local/crisisshield/*"]
          mutateDigest: true
          required: true
          attestors:
            - entries:
                - keyless:
                    subject: "https://gitlab.local/crisisshield/*//.gitlab-ci.yml@refs/heads/main"
                    issuer: https://gitlab.local
                    rekor: { url: https://rekor.crisis.local }
                    ctlog: { ignoreSCT: false }
          attestations:
            - type: https://cyclonedx.org/bom
              attestors: [{ entries: [{ keyless: { subject: "https://gitlab.local/crisisshield/*//.gitlab-ci.yml@refs/heads/main", issuer: https://gitlab.local, rekor: { url: https://rekor.crisis.local } } }] }]
              conditions: [{ all: [{ key: "{{ components | length(@) }}", operator: GreaterThan, value: 10 }] }]
EOF
k kubectl apply -f k8s/policies/kyverno/09-verify-image.yaml
k kubectl run t1 -n crisis --image=harbor.crisis.local/crisisshield/api:unsigned 2>&1 | tail -1
k kubectl run t2 -n crisis --image=harbor.crisis.local/crisisshield/api:feature-xyz 2>&1 | tail -1    # signée par la branche feature
k kubectl run t3 -n crisis --image=harbor.crisis.local/crisisshield/api:nosbom 2>&1 | tail -1         # signée par main, sans attestation
t1 : image-signee-et-attestee: no matching signatures t2 : subject mismatch: expected https://gitlab.local/crisisshield/*//.gitlab-ci.yml@refs/heads/main, got …@refs/heads/feature-xyz t3 : attestation type https://cyclonedx.org/bom not found (et l'image de main signée avec SBOM : Pod créé, image mutée en @sha256:…)
  • Trois refus, trois messages différents : on sait immédiatement ce qui manque. Un message générique « denied » coûte une heure de débogage à 3 h.
  • mutateDigest réécrit le tag en digest à l'admission : même un tag qui bouge ne peut plus tromper le cluster.
Étape 5

Build reproductible : même commit, même digest

# Dockerfile : FROM eclipse-temurin:21-jre-alpine@sha256:… ; ARG SOURCE_DATE_EPOCH ; COPY --chmod=644 ; RUN … && find /app -exec touch -d @$SOURCE_DATE_EPOCH {} +
# pom.xml : <project.build.outputTimestamp>${git.commit.time}</project.build.outputTimestamp> (maven-jar-plugin ≥ 3.2 trie et horodate les entrées)
# Kaniko : --reproducible (retire les horodatages des couches) ; versions apk épinglées ; pas de apt-get update sans snapshot
/kaniko/executor … --reproducible --digest-file /tmp/d1 ; /kaniko/executor … --reproducible --digest-file /tmp/d2 ; diff /tmp/d1 /tmp/d2 && echo identique
# avant correction, pour comprendre : docker run --rm -v "$PWD:/w" quay.io/reproducible-builds/diffoscope a.tar b.tar | head
identique (sha256:9c4d… dans les deux builds, sur deux runners) avant : diffoscope montre les mtime des entrées du jar et un fichier /var/cache/apk différent
  • Ce qui a dû changer, documenté : horodatage du jar, ordre des fichiers, cache apk supprimé, image de base par digest, --reproducible. C'est la liste que le chapitre demande.
  • Un build reproductible permet à un tiers de vérifier qu'une image vient bien de ce code : c'est l'argument SLSA L4 et la réponse à « et si le runner était compromis ? ».
Étape 6

Dépendances : Nexus sous contrôle, typosquat refusé, PGP vérifié

# Nexus : maven-proxy → Routing rule « allow » sur ^/org/springframework/.*, ^/org/apache/.*, ^/fr/crisisshield/.*, … ; tout le reste bloqué ; Content selector + Cleanup ; « Maven Central (signed only) » via un proxy avec vérification des .asc (plugin pgpverify en CI)
# pom.xml : <dependency><groupId>org.springfrarnework</groupId><artifactId>spring-core</artifactId><version>6.1.13</version></dependency>
./mvnw -q -s .mvn/settings.xml dependency:resolve 2>&1 | grep -m1 -E 'Could not find|403'
# vérification PGP en CI :
./mvnw -q org.simplify4u.plugins:pgpverify-maven-plugin:1.18.1:check -Dpgpverify.keysMapLocation=pgp-keys-map.list -Dpgpverify.failNoSignature=true
[ERROR] Could not find artifact org.springfrarnework:spring-core:jar:6.1.13 (groupe hors liste : Nexus renvoie 404/403, rien n'est téléchargé) pgpverify : 188 artifacts verified, 0 missing signature, 0 wrong key
  • La liste de groupes autorisés transforme un typosquat en erreur de build : on ne compte pas sur la vigilance du développeur.
  • pgp-keys-map.list fige quelle clé signe quel groupe : un artefact signé par une autre clé, même valide, est refusé.

Checklist SLSA et Scorecard

Questions de relecteur

  • Que protège la signature keyless que ne protège pas une signature par clé ? L'identité : on sait quel pipeline a signé, et une clé volée ne suffit plus.
