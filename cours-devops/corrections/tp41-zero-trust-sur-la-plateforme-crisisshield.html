Zero trust sur la plateforme CrisisShield

Une solution complète, étape par étape : ce qu'il faut produire, la commande ou le fichier clé, le résultat qui prouve que ça marche, et les pièges. Ta solution peut différer ; ce qui compte, c'est que chaque preuve soit là.

Énoncé
  1. PKI : CA racine hors ligne (openssl dans un conteneur sans réseau, clé chiffrée stockée hors du poste ; documente la cérémonie), intermédiaire Vault PKI du TP 38 signée par la racine, trust-manager pour distribuer la racine dans tous les namespaces, certificats internes de 24 h via cert-manager pour l'API, le worker, Keycloak, Grafana. Alerte à 14 jours sur toute expiration (cert-manager metrics). Rotation de l'intermédiaire selon l'exercice 41.1, exécutée réellement.
  2. Identité des charges : déploie SPIRE (serveur + agents) ; l'API obtient un SVID X.509 ; PostgreSQL (CloudNativePG) authentifie l'API par certificat client (auth cert) à la place du mot de passe dynamique, ou en complément ; Vault accepte l'auth par certificat SPIFFE. Compare avec l'identité fournie par le mesh du TP 30.
  3. Humains : Keycloak comme IdP unique avec passkeys/WebAuthn obligatoires pour le groupe admin ; fédération vers GitLab, ArgoCD, Grafana, Vault, Kubernetes (OIDC sur l'API server via kind config). Désactive un compte et vérifie la perte d'accès partout.
  4. Accès admin JIT : Teleport (Compose ou Helm, édition communautaire) ou Boundary devant kubectl et la base ; demande d'accès de 30 minutes approuvée, session enregistrée et rejouable. Supprime tout kubeconfig admin permanent.
  5. Authentification des humains : realm Keycloak crisis en code (export JSON versionné, appliqué par keycloak-config-cli), politique de mots de passe NIST avec vérification des mots de passe compromis, passkeys (WebAuthn) obligatoires pour le groupe admin et proposées aux opérateurs, détection de force brute activée, flow de récupération de compte revu (second facteur exigé), événements exportés vers Loki, brokering vers un fournisseur externe (Google ou Entra ID de test).
  6. Application : passe l'API en serveur de ressources Spring Security (émetteur et audience vérifiés, conversion des rôles, contrôle d'accès par objet), le front React derrière un BFF Spring Cloud Gateway avec cookie de session HttpOnly (variante : SPA directe avec oidc-client-ts et PKCE, à comparer). Refresh rotation et back-channel logout configurés et testés. Le service Notification (Quarkus) authentifie Incidents par Token Exchange et mTLS.
  7. Tests de sécurité automatisés, tous en CI : jeton expiré, alg: none, HS256 avec clé publique, mauvais émetteur, mauvaise audience, id_token utilisé comme access token, rôle insuffisant, IDOR entre organisations, refresh token rejoué après rotation, clé d'API révoquée. Chaque cas attend 401 ou 403 et un événement journalisé. Testcontainers Keycloak pour les tests d'intégration.
  8. Partenaires : une clé d'API hachée, préfixée et à quota pour un partenaire fictif, un webhook sortant signé HMAC avec horodatage, et la vérification côté récepteur.
  9. Keycloak as code : export du realm en JSON versionné, appliqué par keycloak-config-cli dans le pipeline GitOps ; MFA admin, brute force, journal d'événements vers Loki.
  10. Écris le document d'architecture zero trust de CrisisShield (2 pages, schéma) : identités, segmentation, chiffrement, accès, journalisation, et le reste à faire.
  11. PKI au quotidien : sur ta PKI du TP 41, émets un certificat de service avec tous les SAN nécessaires, vérifie la chaîne avec openssl verify, active l'OCSP stapling sur l'Ingress, convertis en PKCS#12 pour un client Java et charge-le par SSL bundle Spring ; reproduis et corrige les cinq erreurs du tableau 41.9 ; construis l'inventaire des certificats du cluster (cert-manager + un scan des endpoints) avec une alerte à 30 et 14 jours ; rédige et exécute la cérémonie de la racine hors ligne avec un journal signé.

# docs/security/ceremonie-racine.md : date, participants (2 détenteurs), lieu, conteneur --network none, génération, division de la passphrase (age + 2 destinataires), copies sur 2 supports scellés, vérification des empreintes, journal signé par les deux (cosign sign-blob du PV)

# alerte (PrometheusRule) : certmanager_certificate_expiration_timestamp_seconds - time() < 14*86400 → warning ; < 30 j info
# rotation de l'intermédiaire (exercice 41.1) : nouvelle CSR → signée par la racine hors ligne → set-signed → les nouveaux certificats sortent de la nouvelle intermédiaire ; l'ancienne reste dans le bundle jusqu'à expiration des feuilles (24 h), puis retirée
sha256 Fingerprint=3A:9F:… notBefore=Sep 22 2026 notAfter=Sep 20 2036 configmap crisis-root présent dans 6 namespaces (label trust=crisis) crisis api-tls 2026-09-23T10:52:00Z True (idem worker, keycloak, grafana) rotation : chaîne api → int-2 → root vérifiée par openssl verify ; 0 erreur TLS pendant les 24 h de recouvrement
  • Des certificats de 24 h rendent la révocation presque inutile : un certificat volé meurt avant qu'on ait fini de s'inquiéter. C'est l'argument contre les certificats d'un an.
  • La rotation de l'intermédiaire est jouée, pas lue : la seule preuve que le bundle, les issuers et les clients la supportent.

Humains : Keycloak IdP unique, passkeys, fédération, désactivation

# realm crisis : Authentication → flow « browser-passkey » : Username form → WebAuthn Passwordless (REQUIRED pour le groupe admins via conditional flow « Condition - user role ») ; OTP pour les autres
# clients OIDC : gitlab, argocd, grafana, vault, kubernetes ; mappers : groups (claim groups), audience
# kind-config : apiServer.extraArgs oidc-issuer-url=https://keycloak.crisis.local/realms/crisis, oidc-client-id=kubernetes, oidc-username-claim=email, oidc-groups-claim=groups, oidc-ca-file=/etc/kubernetes/pki/crisis-root.crt
k kubectl oidc-login setup --oidc-issuer-url=https://keycloak.crisis.local/realms/crisis --oidc-client-id=kubernetes   # plugin krew oidc-login, dans l'image outillée
# ClusterRoleBinding : Group crisis-admins → cluster-admin ; crisis-devs → view sur crisis-dev
# désactivation : Keycloak → Users → alice → Enabled: off ; puis :
for u in https://gitlab.local https://argocd.crisis.local https://grafana.crisis.local https://vault.crisis.local ; do echo "$u $(curl -sk -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $ALICE_TOKEN" $u/api/user 2>/dev/null)"; done
k kubectl --user=alice get pods -n crisis-dev 2>&1 | tail -1
gitlab 401, argocd 401, grafana 401, vault 403, kubectl : error: You must be logged in (le jeton refresh d'alice est refusé : session Keycloak révoquée) (les jetons d'accès déjà émis restent valables jusqu'à leur expiration : 5 minutes — d'où des jetons courts)
  • Un seul IdP = une seule désactivation : c'est le contrôle A.5.18 de l'ISO 27001 (TP 42), prouvé par la boucle curl.
  • La fenêtre de 5 minutes entre désactivation et perte effective est le compromis des jetons sans état ; pour la réduire : jetons plus courts, ou back-channel logout (étape 6).

// Notification (Quarkus) : quarkus.oidc-client.grant.type=exchange ; appelle Incidents avec le jeton échangé (aud=crisis-api, sub=utilisateur d'origine, azp=notification) ; mTLS via le SVID SPIRE

# back-channel logout : déconnexion depuis Keycloak (admin → sessions → logout) puis :
curl -sk -b "SESSION=$COOKIE" https://bff.crisis.local/api/me -o /dev/null -w '%{http_code}'
# tp41.md : tableau BFF contre SPA+PKCE — jeton jamais dans le navigateur / une brique de plus ; XSS ne vole rien / XSS vole le jeton ; CSRF à gérer / pas de cookie
refresh rejoué : "invalid_grant" (et Keycloak révoque toute la session : détection de vol) après back-channel logout : 401 (la session BFF a été invalidée sans attendre l'expiration) Notification → Incidents : 200 avec un jeton dont azp=notification et sub=alice (délégation tracée)
  • Le BFF garde le jeton côté serveur : un XSS dans le front React ne peut pas l'exfiltrer. C'est la recommandation OAuth 2.1 pour les applications navigateur, et la réponse d'entretien attendue.
  • Token Exchange, pas propagation du jeton utilisateur : l'audience change, le service appelant est nommé, la chaîne d'appel est lisible dans les journaux.

Partenaires : clé d'API hachée, webhook signé HMAC

// ApiKeyService : clé = "cs_live_" + 32 octets aléatoires base62 ; stockage : prefix (8 premiers caractères, pour la recherche), hash Argon2id, quota (1 000/jour), scopes, expiration, révocation

// webhook sortant : X-Crisis-Signature: t=1758536400,v1=hex(HMAC-SHA256(secret, t + "." + body)) ; X-Crisis-Delivery: uuid ; retry avec backoff, dead-letter
// récepteur (exemple Python fourni au partenaire) : rejeter si |now - t| > 300 s ; comparer avec hmac.compare_digest
curl -s -H "X-Api-Key: cs_live_aB3…" https://api.crisis.local/partner/incidents | jq length ; for i in $(seq 1001); do curl -s -o /dev/null -w '%{http_code}\n' -H "X-Api-Key: cs_live_aB3…" https://api.crisis.local/partner/incidents; done | sort | uniq -c

  • La clé n'est jamais stockée : seul son hash l'est ; le préfixe permet la recherche et l'identification dans un log sans révéler la clé.
  • L'horodatage dans la signature HMAC ferme le rejeu ; l'identifiant de livraison rend le récepteur idempotent.

# docs/security/zero-trust.md (2 pages, schéma Mermaid)
# 1. Identités : humains (Keycloak, passkeys, groupes), charges (SPIRE SVID, ServiceAccount), machines (Teleport, jetons GitLab), partenaires (clés hachées)

document relu par un pair, chaque contrôle renvoie au TP qui le prouve
  • Zero trust n'est pas un produit : le document liste des contrôles, chacun avec sa preuve. Une case « à faire » honnête vaut mieux qu'une case cochée sans preuve.
  • C'est le document que tu présenteras à un RSSI en entretien : sache le dérouler en 5 minutes.

  • Que fait-on si la racine hors ligne est perdue ? Rien n'est perdu tant que l'intermédiaire est valide ; on prépare une nouvelle racine, on la distribue par trust-manager, on migre à la prochaine rotation. D'où deux copies scellées.
